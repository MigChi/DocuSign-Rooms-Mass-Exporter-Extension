# DocuSign Rooms Mass Exporter — Architecture & Design Case Study

## Overview

A Chrome extension (Manifest V3) that bulk-exports documents from a DocuSign Rooms account to a local folder structure — one folder per room, containing that room's documents. The project started as a small working extension and was redesigned to reliably handle **10,000+ rooms**, a scale where naive approaches (single-tab, fixed delays, no persistence) become impractical — the original design projected to **55-70 hours** of runtime.

This document walks through the problem in the order it was actually solved: what each step addressed, which options were considered, why the chosen option won, and where an earlier decision was later reversed as new requirements surfaced. For what the extension actually does today and how to use it, see the top-level [`README.md`](../README.md) — this document is the reasoning behind it, not a user guide.

## Starting Point: Auditing the Existing Extension

The original extension used a single worker tab, processed rooms strictly sequentially, and relied on fixed `sleep()` delays (~11.5 seconds of pure dead time per room, not counting page load) to wait for DOM state to settle before clicking the next button. Its download-renaming trick — intercepting `chrome.downloads.onDeterminingFilename` to route each ZIP into `Docusign Rooms/<Room Name>/<Room Name>.zip` — was sound, but it depended on tracking exactly **one** active room globally, which meant the whole design could never be parallelized without a rework.

Doing the math on 10,000 rooms against that sequential design (~20-25s/room including page load) put the runtime at 55-70 hours — the actual number that motivated everything below.

| 6 | Min/max bounds + adaptive concurrency suggestion | **Partial.** The min/max bounds landed in [Decision 17](#decision-17-user-configurable-worker-tab-count-bounded-not-unlimited) (1-8, manually set by the user via the panel) - the *adaptive* half (suggesting a value from measured per-room timing, not just accepting whatever manual number is entered) is still not started, and still depends on real timing data from step 5, which now exists to build against |

In short: everything through persistence is implemented and has been exercised in live testing against a real account, including the multi-tab worker pool, which started with a hardcoded tab count as a deliberately small first pass (Decision 2) and later became user-configurable within safe bounds (Decision 17). What's left: a full per-room (not just per-worker) status view in the panel at very large scale, and the automatic timing-based suggestion half of step 6 - manual, bounded control exists now, but nothing yet recommends a value for you. Two things happened outside the original six-step plan, added afterward once real usage surfaced the need: [Decision 13](#decision-13-automated-testing-strategy) added an automated test suite covering the project's pure logic, and [Decision 24](#decision-24-moving-the-panel-out-of-the-page--a-detached-window) moved the control panel out of the Docusign page entirely, into a standalone window - both real-scale runs (an 8000-room production scan and download) confirmed the core pipeline works end to end and surfaced the bugs that Decisions 20-24 fixed.

## High-Risk Areas — Read This Before Touching These

The Decision log below is organized chronologically - the right place to understand *why* something works the way it does, but the wrong place to quickly answer "is this specific function dangerous to change?" without reading dozens of entries. This section exists for that second question: a small, cross-referenced map of the parts of this codebase that have needed real fixes more than once, why, and what to specifically double-check before touching them again. Every claim below is grounded in a real Decision number, not a general impression - if a fix here doesn't hold up, the corresponding Decision is where to verify it.

### `content/scan.js`'s room scan (`autoScrollAndCollectRooms()`)

**Historical context - nine real, separate fixes to the original DOM-scrolling implementation, all before it was replaced entirely (Decision 46):** [Decision 33](#decision-33-two-ways-a-scan-could-silently-hang-forever-found-by-auditing-the-scan-relay-end-to-end) (uncaught-throw and closed-tab hangs), [Decision 35](#decision-35-a-scroll-count-cap-can-never-be-high-enough---removed-entirely-in-favor-of-the-signal-that-actually-means-done) (the scroll-count cap that cut real scans short), [Decision 36](#decision-36-the-os-lock-screen-can-still-interrupt-a-scan-even-when-disabled---asked-the-browser-to-prevent-it-directly-and-fixed-a-silent-empty-result-gap-it-exposed) (a silent 0-room "success" when the sort dropdown was wrong), [Decision 37](#decision-37-a-real-tab-crash-aw-snap-on-a-large-account---dom-trimming-checkpointed-progress-a-stall-watchdog-and-a-resource-leak-found-along-the-way) (the tab crashing outright from unbounded DOM growth - the fix that started this whole thread), [Decision 38](#decision-38-a-second-distinct-way-a-scan-could-silently-report-0-rooms-as-a-success) (a second, distinct way to silently report 0 rooms as success), [Decision 39](#decision-39-a-research-grounded-audit---a-real-stale-dom-read-bug-a-documented-storage-race-and-a-reusable-high-risk-areas-map) (a room read mid-render, before its own name/date content painted in, silently and permanently dropped from the export), [Decision 40](#decision-40-we-cannot-tolerate-a-room-being-glossed-over---closing-the-rest-of-the-stale-dom-gap-and-proving-not-just-claiming-neither-side-loses-one-silently) (the same class of bug's second variant), [Decision 41](#decision-41-a-third-way-to-silently-report-0-rooms---found-by-reading-real-filesystem-evidence-not-assumption-plus-a-deliberate-revision-of-decision-13s-testing-boundary) (a *third*, distinct way to silently report 0 rooms as a success), and [Decision 42](#decision-42-a-scan-side-activity-log---periodic-aggregate-reporting-plus-an-audit-that-found-a-second-real-bug-along-the-way) (a scan-side Activity Log). **Every one of these was a symptom of the same underlying cause:** DOM-scrolling a virtualized, infinite-scroll page this project doesn't control and can't inspect outside of live testing, where "the real page didn't do what was assumed" bugs surface constantly and each fix only ever closed the specific variant already found.

**As of Decision 46, this is no longer DOM automation at all** - it reads directly from Docusign's own internal Rooms API (confirmed live via captured Network tab evidence), the same endpoint the page's own infinite scroll calls, without ever triggering that rendering pipeline. This didn't just fix the crash Decision 37 partially mitigated - it structurally eliminated entire *classes* of the bugs listed above: there is no more DOM to scroll (Decisions 35/37's whole category), no sort-dropdown UI state to trust (Decision 36), and no such thing as a "mid-render" JSON API response the way a virtualized DOM row could be caught incomplete (Decisions 39/40's entire mechanism). The scroll-vs-stall ambiguity Decision 41 fought (did the scan finish, or just stall?) is gone too - `nextUri` is either present (more data) or empty (structurally, definitively done), with nothing in between.

**What's actually risky now is different, not smaller - a new failure mode replaced the old ones:** this is an **undocumented, internal, unofficial API**. Docusign has made no commitment it stays stable, and every field name, query parameter, and the CSRF-header mechanism itself were learned entirely from one live capture, not documentation.

**Before changing anything here, verify:**
- Any change to the request URL/query parameters is backed by a *new* real capture (DevTools Network tab), not guessed at from what "should" work by analogy to the confirmed-working request.
- `fetchRoomsPage()`'s shape validation (`Array.isArray(data?.rooms)`) still runs before anything downstream trusts the response - an internal API changing its response shape without warning is a real, live risk category this project has no control over, and the whole point of that check is turning a silent wrong result into a loud, clear failure instead.
- The CSRF header logic (`X-DocuSign-Rooms-CSRF-Token`, `X-XSRF-TOKEN`, both read via `parseCookieValue()`) still matches what a real request actually needs - if Docusign ever changes their CSRF scheme, this is the first thing that will start failing, and the error message should already surface that clearly (see `fetchRoomsPage()`'s own specific handling of the confirmed-live `{"message":"Could not validate CSRF token."}` shape).
- `tests/scan.test.js` mocks `fetch()` directly against the exact confirmed response shape - if Docusign's real response ever drifts from what these tests assume, the tests would keep passing against a stale mock while the real extension silently breaks. There is no way to catch that class of drift from inside this codebase alone; it can only be caught by noticing a real scan failing live and re-capturing fresh evidence, the same way this whole rewrite started.

**Tested with real `node:test` coverage** (`tests/scan.test.js`) - simpler to test than the old DOM version ever was, since the whole surface is now `fetch()` and a `document.cookie` string, neither of which needs a DOM stub.

**One accuracy pitfall specific to the new checkpoint/reminder logic, found during a post-implementation audit and fixed before commit:** any number reported to the user about "what's saved so far" must come from the actual in-range count last handed to `onCheckpoint()` (`lastCheckpointInRangeCount`), never from `collected.length` or anything derived from it - `collected` counts every room scanned regardless of date range, while the checkpoint CSV only ever contains in-range rooms. Since the scan pages ascending from position 0, an account with years of history outside a narrow requested range can cross a 1,000-room *scanned* boundary while the checkpoint CSV itself is still empty or far smaller than that number.

### `findCurrentRoomForDownload()` (`background.js`)

Matches a completed Chrome download back to the room that triggered it. **Corrected repeatedly within [Decision 2](#decision-2-parallelism-model--work-queue-not-divide-and-conquer)** - a tab-ID-based lookup that turned out unreliable (downloads open in a new browsing context via a `target="_blank"` form submit, so `DownloadItem.tabId` never matches the worker tab), then a URL-pattern fallback whose first regex only matched `/rooms/<id>/` and silently missed every real case (the actual download URL uses `/transaction/<id>/`). Its own resulting pattern (`/\/(?:rooms|transaction)\/(\d+)/i`) is now trusted and *reused* by later code (`matchVerifiedDownloads()` in Decision 26, the `Unassigned` catch-all in Decision 27) specifically *because* it was already hard-won here - those later decisions deliberately avoided refactoring this function itself again, to not risk a fourth regression in code with this history.

**Before changing anything here, verify:** any new matching logic is tested against a *real* captured `DownloadItem` (referrer is empty for real Docusign downloads - confirmed live, don't assume otherwise), and that both `rooms` and `transaction` URL segments are still checked, not just one.

### The `STATE.scanning` / `STATE.running` stuck-forever pattern (`background.js`, cross-cutting)

Not one function - a recurring *class* of bug that has independently hit both flags, multiple times, in different disguises: an unguarded `chrome.tabs.query()`/`chrome.tabs.create()` throw ([Decision 33](#decision-33-two-ways-a-scan-could-silently-hang-forever-found-by-auditing-the-scan-relay-end-to-end), and the analogous `DS_START_QUEUE`/`runQueue()` fixes before it), a tab crashing without closing or navigating (Decision 37's `chrome.alarms` watchdog), a promise that never settles instead of rejecting (Decision 34's `withTimeout()`), and - the same pattern one layer further out - a *user-initiated* action (Stop) that only ever messaged a possibly-dead tab and hoped, with nothing guaranteeing `STATE.scanning` ever came back down if that tab happened to be the crashed one ([Decision 45](#decision-45-a-second-real-tab-crash---a-silent-checkpoint-naming-bug-a-stuck-stop-button-and-a-watchdog-that-missed-a-2-hour-sleep)'s `forceResetStoppedScanIfStillActive()`). **The pattern to recognize:** any code path that sets one of these flags `true` needs a corresponding path that's *guaranteed* to set it back `false` - not just the happy path, but every throw, every timeout, every way the browser itself can silently take away what the code was waiting on (a closed tab, a crashed tab, a navigated-away tab, a killed service worker) - and every explicit user action (Stop, Pause) that implicitly promises to end that state but only actually does so if whatever it's messaging is still alive to respond.

**Before adding a new state transition here, verify:** for every way this specific operation can end - success, thrown error, timeout, the underlying tab disappearing in any of the three ways above - is there a code path that resets the flag and tells the panel what happened? If the honest answer is "I'm not sure this can fail," that's the exact reasoning that produced several of the bugs listed above; check anyway.

**A related, distinct failure shape found in [Decision 43](#decision-43-a-standalone-audit---closing-a-known-but-unfixed-risk-and-an-alarm-that-never-stops-ringing) - not "stuck forever," but "silently does the wrong thing":** any deliberately non-persisted `STATE.scan*` field (`scanMode`, `scanDateRangeLabel`, etc. - see `STATE`'s own comment for why scanning is intentionally never resumable) resets to its initial value if the service worker restarts mid-scan, but the *content script* driving that scan has no idea this happened and will still eventually deliver a real result to a worker that's forgotten what it was for. A handler with a plain `else`/fallback branch for "whatever this field's live value turns out to be" can silently misinterpret that lost context as a *different*, valid case instead of the "we lost track" case it actually is (`DS_SCAN_COMPLETE`'s `mode` was exactly this). **Before adding a branch keyed off a non-persisted `STATE.scan*` field, verify:** does every branch account for the field's initial/default value meaning "we don't actually know," or does a catch-all `else` quietly treat "unknown" the same as one specific known case?

### `persistJob()` (`background.js`)

Writes the resumable job snapshot to `chrome.storage.local`, called from multiple, genuinely concurrent worker tabs. Originally designed around resuming from a saved queue *index* - unsafe once several tabs could claim rooms at once (a crash could land between "claimed" and "finished," silently dropping that room), reworked in Decision 6's own corrections to resume as "queue minus anything with a result" instead. Independently found and fixed this session for a second, more subtle concurrency issue: `chrome.storage.local` is documented by the Chromium extensions team as providing no ordering guarantee for concurrent `set()` calls to the same key, and multiple workers really do call this function at effectively the same moment - now serialized through a shared promise chain (`persistChain`) so writes to storage can never actually overlap, regardless of how many workers finish a room in the same instant.

**Before changing anything here, verify:** any new call site still goes through `persistJob()`/`clearPersistedJob()` directly (not a raw `chrome.storage.local.set()`/`.remove()` call) - bypassing these two functions means bypassing the serialization that makes concurrent writes safe.

### `cleanName()` (`content/utils.js`)

Every folder and file name in this codebase passes through this one function - which is exactly why a single gap in it ([Decision 23](#decision-23-the-second-real-scale-bug--trailing-periods-silently-breaking-folder-routing): a trailing period or space, common in business names ending "LLC." or "Inc.", silently rejected by Chrome's downloads API with no visible error) manifested as files scattered across the flat Downloads root instead of their organized folders, at real scale, with nothing wrong in the *calling* code at all.

**Before changing anything here, verify:** the change is checked against the specific real room names in this file's own test suite (`tests/utils.test.js`) that caused the original bug, not just a few made-up examples - Windows path-validity rules apply on every platform via Chrome's own cross-platform validation, not just on Windows.

### `computeFolderNames()` (`background.js`)

Disambiguates same-named rooms into distinct folders. Corrected once within Decision 2 (two different rooms, different IDs, sharing a display name - "Ponchak - Listing" - were silently merging into one folder) and rescoped again in [Decision 25](#decision-25-organizing-downloads-by-year) once downloads moved from a flat structure to year-based folders (collisions now need to be scoped per-year, not just per-name, since two same-named rooms in *different* years no longer actually share a folder).

**Before changing anything here, verify:** the change is tested against the exact "two different rooms, same cleaned name" scenario in `tests/background.test.js` - this is precisely the kind of bug that a small, clean-looking test dataset (one room per name) will never surface.

## Decision 1: Official API vs. Continued Browser Automation

**Problem:** Is there a faster way to get this data than clicking through the UI at all?

**Option considered:** DocuSign's real Rooms REST API (`GetRooms`, `GetDocuments`, per-document `base64Contents` retrieval — verified directly against DocuSign's published OpenAPI spec, not assumed from memory). This would return individual files per room (a good match for "one folder per room," no unzipping needed) and remove browser automation entirely.

**Why it was attractive:** no scrolling, no clicking, no DOM fragility, real pagination and filtering, dramatically faster in principle.

**The blocker:** creating the OAuth credentials (an "Integration Key") required for API access sits behind DocuSign's **Account Administrator** permission — a different privilege tier from being able to use the Rooms product day-to-day. Verified in practice: attempting to reach `admin.docusign.com` produced a sign-in loop rather than a dashboard, confirming no admin rights on the account, and no admin was readily reachable.

**Decision:** abandon the API path for now and invest in making browser automation itself fast, resilient, and observable. This is a real-world instance of **a technically superior solution being inaccessible due to organizational/permission constraints** — the right engineering response is to redesign within the actual constraints, not to look for a workaround around an access-control boundary.

## Decision 2: Parallelism Model — Work Queue, Not Divide-and-Conquer

**Problem:** how do multiple browser tabs process 10,000 independent rooms faster than one tab?

**Option initially proposed:** a binary-tree / divide-and-conquer split — two tabs start at the middle of the list, each spawning further splits.

**Why it doesn't fit:** divide-and-conquer earns its complexity reduction from a *recursive subproblem structure with a combine step* (mergesort's split + merge). Downloading room #4,317 has no relationship to room #8,921 and produces no result that needs combining — each room is an independent, variable-cost task. That's the definition of an **embarrassingly parallel** workload, not a divide-and-conquer one.

**Why a shared work queue wins concretely:** with a static split (e.g., two tabs, 5,000 rooms each), if one tab's half happens to contain heavier rooms, that tab runs long while the other sits idle after finishing early — total time is bounded by the *slowest* partition, not the average. A shared queue where any free worker claims the next unclaimed item guarantees no worker is ever idle while work remains; total time approaches `total_work / N`, the theoretical best case for N workers. This dominates static partitioning whenever task duration is variable, which it is here (rooms differ wildly in document count).

**Decision:** one shared queue (an array + a pointer) with a pool of N tabs each claiming work greedily — the classic **producer-consumer / bag-of-tasks** pattern.

**Implemented.** `STATE.pending` is the queue, `claimNextRoom()` is the pointer read/increment (see Decision 3 below for why it's safe), and `runWorker(tabId)` is one worker's whole lifetime — claim, process, repeat, until `pending` is exhausted or Stop ends it. `runQueue()` starts `WORKER_TAB_COUNT` (currently a hardcoded `3` — see [Decision 8](#decision-8-adaptive-concurrency--a-feedback-loop-not-a-formula)) of these concurrently via `Promise.all()` and doesn't resolve until every worker's loop has exited on its own.

**Correction, found in live testing immediately after this landed:** `processRoom()` originally navigated each worker tab with `active: false`, specifically to stop several tabs fighting over focus on every room. Live testing showed every room's DOM steps (Select All, Bulk Download, confirm) reporting success, but `chrome.downloads.onDeterminingFilename` never firing for any of them — empty `Download ID`, status permanently stuck at `Success/Attempted` in the report. The actual browser-level download was never registering at all. Hypothesized cause at the time: Chrome's protection against a page silently triggering multiple automatic downloads treating a background-tab-triggered download as the abuse pattern it exists to catch. Fixed by reverting to `active: true`.

**Second correction — the `active` hypothesis above was wrong, or at least not the real cause.** The exact same symptom (every row, empty `Download ID`, no folder ever created) persisted in the next live test *after* the `active: true` revert, with the files confirmed landing directly in the flat Downloads root instead of `Docusign Rooms/<Room Name>/`. That ruled out tab-focus state entirely and pointed at `onDeterminingFilename`'s matching logic itself. The actual cause, found by re-checking markup captured earlier in the project: the download-confirmation form is `<form id="formDownloadDocuments" method="post" target="_blank" ...>` - submitting it opens a **new browsing context** to receive the response, so the resulting `DownloadItem.tabId` belongs to that new (often instantly-closed) tab, never the worker tab that actually triggered it. `STATE.currentRooms[downloadItem.tabId]` was therefore never going to match, and since the listener's gate was `if (!currentRoom || ...) return;`, it bailed out before ever reaching the `looksLikeDocusign`/`looksLikeZip` fallback checks that existed specifically to catch a case like this. Fixed with `findCurrentRoomForDownload()`: try the tab-based lookup first, then fall back to parsing a room ID out of the download's own `referrer`/`url`/`finalUrl` (which points back to `.../rooms/<id>/documents`) and matching that against whichever rooms are currently in flight - correct regardless of which tab Chrome attributes the download to. A `console.warn` was added for the still-unmatched case, logging the download's actual identifying fields, in case the referrer/url fallback doesn't cover every real-world case either.

This is recorded as two separate corrections rather than editing the first one away, in keeping with this document's practice of showing wrong turns rather than erasing them - the `active: true` revert wasn't wrong to try given the evidence at the time (every symptom was consistent with it), it just wasn't the actual root cause once more evidence came in.

**Third correction — the diagnosis was right, the first fix's regex wasn't.** The `console.warn` added above did its job: a real captured `DownloadItem` showed `referrer: ''` (empty - the `target="_blank"` navigation doesn't appear to carry one over) and `url: 'https://rooms.docusign.com/transaction/2977525/documents/download'`. The room ID *was* right there in the URL - just under DocuSign's internal `/transaction/<id>/` path, not `/rooms/<id>/` like the room's own page and `documentsUrl` use. `findCurrentRoomForDownload()`'s regex only matched `rooms`, so it silently missed the ID in every real download despite being right next to it. Fixed by matching either segment: `/\/(?:rooms|transaction)\/(\d+)/i`. Both are confirmed (via this same captured evidence) to carry the identical numeric ID for a given room.

**Fourth correction, once folder routing was actually working — two different rooms with the same name were silently merged into one folder.** With the fix above landed, a live run confirmed 12 attempted downloads across the account but only 11 folders on disk. Row-by-row comparison of the report against room IDs found the cause: two distinct rooms (IDs `2977526` and `2977529`) both happened to be named "Ponchak - Listing", and folder naming was purely `cleanName(roomName)` — no room ID involved — so both targeted `Docusign Rooms/Ponchak - Listing/`, and the second one's files landed inside the first one's folder via `conflictAction: "uniquify"` instead of getting their own. That flag only disambiguates *filenames* within a folder; it was never going to create a second folder for a same-named room. Fixed by adding `computeFolderNames(queue)`, which counts room-name occurrences across the full run's queue once and returns a `roomId -> folderName` map, appending `(roomId)` to the name only for rooms whose name actually collides with another room's in that run — most rooms keep a plain, readable folder name. Computed once per run (in the `DS_START_QUEUE` handler and the startup resume block, both places `STATE.queue` gets set) rather than per-download, so it's O(n) instead of O(n²) at scale. Both places that had been building the folder path directly from `cleanName(roomName)` — `processRoom()`'s `result.downloadedFilename` and the `onDeterminingFilename` listener's actual `suggest({filename, ...})` call — were switched to read from `STATE.folderNames.get(roomId)` instead, so the reported filename in the CSV and the real folder Chrome creates can't drift apart.

**Fifth correction — a worker tab dying mid-run had no recovery, confirmed live by simply closing one.** Raised first as a theoretical gap while assessing whether the extension was actually ready for 10,000 rooms (see [Current Implementation Status](#current-implementation-status)): `ensureWorkerTabs()` only ever checks tab health once, at the very start of `runQueue()` - nothing re-checks afterward. If a worker tab dies mid-run (closed by the user, reclaimed by Chrome, a crash), every subsequent `chrome.tabs.update()` against it in `processRoom()` rejects near-instantly; the resulting error is caught and recorded as a `Failed` result, but `runWorker()`'s loop just claims the next room and tries again - and since `claimNextRoom()` pulls from one queue shared across all workers, a dead-tab worker can claim and instantly-fail through the remaining queue far faster than the healthy workers can do real 20-60s work, potentially mass-marking a large fraction of a big run "Failed" for a reason unrelated to those rooms. Confirmed directly: closing a worker tab mid-run left it permanently dead for the rest of that run, exactly as predicted. Fixed by moving the liveness check into `runWorker()`'s own loop, run before every claim (not after, and not just once) - `chrome.tabs.get(currentTabId)` is checked each iteration; if the tab is gone, a replacement is created (`active: false`, so it doesn't steal focus), `STATE.workerTabIds` is updated in place so the panel's "Worker N" labeling stays stable, and the loop continues with the new tab. If a replacement tab can't even be created, that worker exits cleanly (logged, not thrown) - the other workers keep going with one fewer.

## Decision 3: Concurrency Safety Without Explicit Locks

**Problem:** multiple tabs claiming from one shared queue is a textbook shared-resource race condition. How is that avoided without a mutex?

**Key insight:** a Chrome extension's background service worker is **single-threaded**, and Chrome serializes all incoming `chrome.runtime.sendMessage` calls through its `onMessage` dispatcher — no two tabs' messages are ever processed truly simultaneously. Additionally, tabs are separate execution contexts with no shared memory at all — the queue can *only* live in the one place that's inherently single-threaded. The "lock" is structural, not something that has to be built.

**The one way to reintroduce the race:** an `await` between reading the queue pointer and advancing it creates a gap where JS can switch to a different tab's claim request mid-operation, letting two tabs read the same pointer value before either increments it.

**Decision:** the claim function must read-and-increment the queue pointer as a single synchronous operation with zero `await` inside it. Everything expensive (navigation, clicking, waiting for a download) happens *after* the claim, fully in parallel across tabs — only the trivial, fast part needs to be a protected critical section.

**Implemented exactly as designed.** `claimNextRoom()` in `background.js` is a plain synchronous function - no `async`, no `await` anywhere in its body:

```js
function claimNextRoom() {
  if (STATE.index >= STATE.pending.length) return null;
  const room = STATE.pending[STATE.index];
  STATE.index++;
  return room;
}
```

Everything that actually takes time - `chrome.tabs.update`, waiting for the page to load, messaging the content script, waiting for the download to start - lives in `processRoom()`, called *after* the claim returns, once each worker already has its own room and nothing left to race over.

**A correctness issue this exposed in the persistence design (Decision 6):** the original resume model saved `STATE.index` and resumed by continuing the loop from that saved value - safe under single-tab, where only one room was ever claimed-but-unfinished at a time. Under concurrency, several tabs can each claim a room (advancing `index` past all of them) before any of them finish - if the service worker dies in that window, an index-based resume would treat all of those already-claimed rooms as done and silently skip them, not just fail to retry the one that was in flight. Fixed as part of building this decision, not as an afterthought - see the persistence-model note in [Decision 6](#decision-6-persistence--the-mv3-service-worker-lifecycle).

## Decision 4: Scope Reduction via Date-Range Filtering

**Problem:** not all 10,000 rooms are needed — only a target date range. Filtering during the scan can save both scan time (stop scrolling early) and total processing time (fewer rooms queued).

**A key sub-question that shaped the design:** can "is this room empty" be determined for free (e.g., a visible document count on the room card), or does it require opening the room (the same cost as processing it)? Confirmed: not free. This ruled out an upfront "filter out empty rooms" pass entirely — that check was pushed into the per-room worker logic instead (see Decision 7), where a short, targeted timeout distinguishes "nothing to select" from a real failure, without wasting a full processing cycle on it.

**DOM verification (not assumed):** inspected the actual rendered room list and found a real `<table>` structure with explicit `data-qa` attributes (`room-list-row`, `room-name` with a `title` attribute holding the untruncated name, `room-date`) — far more reliable than the original code's generic link-scraping-plus-DOM-climbing fallback chain.

**Decision:** sort the list oldest-first, then apply a three-way branch while scrolling — skip (before range), collect (inside range), stop entirely (past range, since the list is sorted, everything after is guaranteed out of range too) — with a small consecutive-miss buffer before actually stopping, to tolerate any lazy-load ordering noise.

**Correction (later, once real per-room markup was captured):** "confirmed: not free" was correct for the *scan* phase — the list page genuinely has no per-room document count visible without opening each room. It does not hold for the *processing* phase. Once a room's Documents page is actually open (which the pipeline does for every queued room regardless), `[data-qa="group-name"]` renders its document count directly in text — `"Room Docs (0)"` for an empty room, `"Room Docs (11)"` for a room with 11 documents — present whether the room is empty or not. The original per-room code never checked this; it wasted a full 45-second timeout waiting for the Select All checkbox on every empty room, since that checkbox never renders at all when there's nothing to select. Fixed in `processCurrentRoom()`: wait on `group-name` instead (present in both states) and short-circuit immediately if the parsed count is `0`, before ever attempting Select All. Open caveat, not yet verified either way: this reads only the *first* `group-name` element on the page; a room with multiple document folders/groups would need the counts summed, and no multi-folder room has been inspected yet to confirm whether that's a real scenario in this account.

**Critical correction, this decision's central assumption was unverified until now:** the entire skip/collect/stop algorithm above depends on the list being sorted oldest-first. That was never actually enforced or checked at runtime — only assumed, based on one earlier snapshot that happened to show `"Created (Oldest)"` selected. A later markup capture of the same list showed the sort dropdown reading **`"Created (Newest)"`** instead, with rooms rendering newest-to-oldest. Under that ordering, the "stop once several rooms are found past `SCAN_DATE_END`" logic breaks completely: with `SCAN_DATE_END` far in the past relative to real (2026-dated) rooms, *every* room on initial page load is already "past the end date," tripping the stop condition on the very first tick, before scrolling even once — a silent, empty-result failure, not a crash. Since the sort direction is apparently not a fixed account property (it differed between two observed sessions), it cannot be assumed at all — it has to be checked every time. Fixed with a new `getSortLabel()` function reading `[data-qa="filter-sort-drop-down-button"] span[title]`, called at the top of `autoScrollAndCollectRooms()`: if it doesn't read exactly `"Created (Oldest)"`, the function stops immediately, reports the problem through `updateStatus`, and returns an empty array rather than proceeding on a false assumption. This is the same honesty principle applied earlier to empty-room detection ("likely empty" instead of a confident wrong assertion) — a loud, clear failure instead of a silent wrong one.

## Decision 5: Batch Scan-Then-Process vs. Streaming (a reversed decision)

**Initial idea:** overlap scanning and downloading — start feeding the queue as rooms are discovered, rather than waiting for the full scroll to finish, to reclaim the scan phase's wall-clock time.

**Why it was reversed:** once "resume after a long pause or crash" became a hard requirement, the streaming approach exposed a correctness problem — the Rooms list is *live* data, and if it's sorted by recent activity, any activity during a partial scan can reorder rooms underneath an in-progress scan, making "diff against a partial checkpoint" unreliable. Meanwhile, the time saved by overlapping (scanning is minutes; processing is hours) was a small fraction of total runtime.

**Decision:** scan once, in full, and save the result as a fixed, immutable list before any processing begins. Resumability is then trivial — track completed indices against a list that never changes — instead of needing reconciliation logic against a moving target. This is a case of **choosing correctness and simplicity over a marginal performance gain**, once the real requirements were fully known.

## Decision 6: Persistence & the MV3 Service Worker Lifecycle

**Problem discovered, not assumed upfront:** Manifest V3 background service workers are deliberately ephemeral — Chrome can terminate and restart them independent of any user action, resetting all in-memory state. This isn't a rare edge case for a job running many hours; it's close to guaranteed to happen at least once.

**Decision:** persist the scanned room list (once), the results/status per room (incrementally), and the queue position to `chrome.storage.local` — not just at the end, but as the run progresses — and have the service worker check for an in-progress job on startup before assuming a fresh run.

**Implemented, single-tab era.** `background.js` snapshots `{queue, index, results, paused, startedAt}` under one `chrome.storage.local` key (`persistJob()`), called at every point that changes resumable state: run start, after each room's result is recorded (success, failure, or the page-didn't-load case), and on pause/resume. (This field list is the original, single-tab version - the third correction below changes it once concurrency lands; `persistJob()` today saves only `{queue, results, paused, startedAt}`, no `index`.) Not called from `broadcastStatus()`, which fires roughly once a second while paused — that would be a lot of redundant writes for no benefit. A top-level async block at the bottom of `background.js` runs on every service-worker startup, checks for a job that was still `running` when memory was lost, and calls `runQueue()` directly to pick it back up.

One subtlety this exposed: `runQueue()`'s `for` loop used to force `STATE.index = 0` in its own initializer, which would have silently turned every resume into a full restart. Fixed by removing the initializer entirely (`for (; STATE.index < STATE.queue.length; STATE.index++)`) and requiring each call site to set `STATE.index` itself first — `DS_START_QUEUE` sets it to `0` for a genuinely new run, the startup resume block sets it to whatever was persisted. Similarly, `STATE.startedAt` is only set inside `runQueue()` if it's currently falsy, so a resumed run keeps its real original start time instead of the elapsed-time display silently resetting; `DS_START_QUEUE` explicitly nulls it first so a truly new run doesn't inherit a stale timestamp left over from an earlier run in the same service-worker lifetime.

Two limitations, both accepted rather than solved here: (1) there's no periodic self-wake (`chrome.alarms`) — resume only fires the next time *something* wakes the service worker: originally the panel's own status check whenever the user reopened a Docusign Rooms tab (true back when the panel auto-injected into every such page); since [Decision 24](#decision-24-moving-the-panel-out-of-the-page--a-detached-window) moved the panel to a standalone window that only opens on a toolbar click, it's more often a content script's `DS_ROOM_PAGE_INFO` message firing automatically on any room page. Either way: not instant on crash. (2) if the crash lands mid-room — after the download's already been clicked but before that room's result gets persisted — the resumed run reprocesses that same room from the top. `conflictAction: "uniquify"` on downloads means the worst case is a duplicate ZIP in its own folder, not overwritten or corrupted data, so this was judged an acceptable tradeoff against the complexity of tracking finer-grained per-room progress (e.g. "selected but not yet confirmed downloaded").

**A second, complementary resume path added afterward: CSV upload.** `chrome.storage.local` only survives inside the same browser profile — it's gone if the user clears browser data, reinstalls the extension, or moves to a different machine. The download report CSV, by contrast, is a real file already sitting in Downloads, independent of anything browser-internal. The panel's new "Upload CSV to Run/Resume" button reads that file back in (via a small hand-written `parseCsv()` in `content/utils.js`, since there's no CSV library and the format is simple enough not to need one), skips the live scan entirely since the room list is already known, and — if the CSV has a `Status` column, meaning it's a download report rather than a plain scan list — separates rows already marked `Downloaded` from everything else before queueing. This isn't a replacement for the `chrome.storage.local` path above; it's a fallback for exactly the cases that one can't cover, plus it doubles as a way to hand-edit and split a room list into smaller batches.

**Correction, found immediately by trying to actually use the feature above:** `createReport()` built its CSV from `STATE.results`, which only gets an entry once a room is *processed* — so a run stopped partway through produced a report covering only the rooms it had reached. Everything still sitting in the queue was simply absent from the file, not marked as pending. Re-uploading that report therefore could only ever resume rooms already touched, never the untouched remainder — which broke the CSV-upload resume path for precisely the scenario it exists for (an interrupted run). Fixed by having `createReport()` walk `STATE.queue` (the complete original list, restored in full on a resumed run too) instead of `STATE.results`, looking up each room's outcome by `roomId` and writing `Status: "Waiting"` for anything without one.

**Second correction, made alongside adding concurrency:** the CSV-upload path originally just *dropped* rows already marked `Downloaded` and queued the rest — which meant the resumed run's own new report only covered whatever it reprocessed, silently losing the record of everything that had already succeeded. `roomsFromCsvRows()` in `content.js` was replaced with `parseUploadedCsv()`, which splits parsed rows into `rooms` (still need work) and `priorResults` (already-`Downloaded`, carried over with their full original result data - reason, filename, download ID, timestamp). `DS_START_QUEUE` accepts this as an optional `priorResults` field and seeds `STATE.results` with it directly, so the resumed run's report - and its live progress counter - shows the true complete picture instead of restarting the count from zero against a shrunk total.

**Third correction, made alongside adding concurrency - the persistence model itself changed:** the original resume logic persisted `STATE.index` and resumed by continuing from that saved value, which was safe under single-tab (only one room was ever claimed-but-unfinished at a time, so a crash mid-room just meant reprocessing that one room - see the second limitation noted above). Once multiple tabs can claim concurrently, `index` can already be advanced past several rooms that were claimed but never finished at the moment of a crash - resuming from that saved index would treat all of them as done and silently drop them, not retry them, which is a worse failure mode than the single-tab version's "maybe a duplicate ZIP." Fixed by no longer persisting `index`/`pending` at all: `persistJob()` now saves only `queue` (the full list) and `results` (what's actually finished), and the startup resume block rebuilds `pending` as `queue` filtered down to rooms with no entry in `results` - "claimed but never finished" and "never reached at all" both naturally fall into that filter and get retried, no bookkeeping needed to tell them apart. See [Decision 3](#decision-3-concurrency-safety-without-explicit-locks) for where this was actually caught.

**Note on build order:** the [Final Build Plan](#final-build-plan-deliberately-risk-ordered) below originally sequenced persistence as step 4, after single-tab processing but before the multi-tab worker pool. In practice it was built and shipped ahead of the multi-tab step it was ordered after, once it became clear a crash losing an hours-long single-tab run was already a real, live problem worth fixing on its own — see [Current Implementation Status](#current-implementation-status) for where each step actually stands.

## Decision 7: Replacing Fixed Delays with Real Signals

**Problem:** the original ~11.5 seconds of fixed sleeps per room were pure guesswork, and guesswork scales badly across 10,000 iterations.

**Insight:** `chrome.downloads.onDeterminingFilename` (already used for the folder-renaming trick) fires the moment Chrome registers a new download — a real, already-available signal for "this room's download has started," rather than something to guess at with a timer. Navigating the tab away immediately after is safe, because Chrome's download manager operates independently of the originating tab once a download is underway — an assumption the *original* single-tab design already depended on implicitly.

**Two distinct wait categories identified:**
- Page becoming interactive after navigation — legitimately network-bound, needs a long timeout.
- A button appearing after a client-side click (e.g., the download button appearing after Select All) — a fast UI reaction, not a network wait, and doubles as the fast signal for "this room has nothing to select" if it *doesn't* appear quickly.

**Decision:** replace every fixed sleep with either a real event (with a timeout fallback, so a genuine failure doesn't hang a worker forever) or a short poll sized to what's actually being waited for.

**Critical correction, found during live single-room testing:** replacing the fixed `sleep(2500)` before the bulk-Download-button check with a real poll (per the decision above) did not fix the "Bulk download button was not found" failure every live room was hitting — because the poll was never the problem. The selector (`button[data-qa="Download"][data-dd-action-name="Bulk Action - Download"]`) was already correct, confirmed against captured markup. Diagnostic `console.log`s added to `selectAllDocuments()` revealed the real cause one layer down: `checkbox.click()` on the Select All input left `checkbox.checked` at `false` and left every `input[data-qa="document-checkbox"]` unchecked — the click was having *no effect at all* on the page's real state, so the bulk-actions toolbar (which only renders once something is selected) never appeared, and the wait was correctly timing out on a button that could genuinely never show up. Root cause: the site's custom checkbox component cancels the native click's default toggle unless the event is a real, trusted user click — `.click()` in a content script produces a synthetic event (`isTrusted: false`), which the page's own handler appears to reject silently (no error, no exception — the toggle is just reverted). This is also where `selectAllDocuments()` itself was quietly wrong independent of the trust issue: it returned `true` unconditionally the moment it found the checkbox element, never verifying the click actually changed anything — a case of the same "confident wrong assertion" failure mode this project had already corrected once for empty-room detection (Decision 4's earlier correction) and once for sort order, now showing up a third time in a different form. Fixed by making `selectAllDocuments()` `async` and self-verifying: it tries the native `checkbox.click()`, then a click on the associated `<label data-qa="select-all-docs-label">`, then a manually dispatched `MouseEvent`, checking after *each* attempt whether any real document checkbox actually shows as checked in the DOM — and only returns `true` once that's observably true, rather than assuming success from the absence of a thrown error.

**Follow-up, confirmed via console logging in live runs:** the native `checkbox.click()` attempt failed identically on two separate rooms, while `label.click()` succeeded both times — the label and input are markup siblings (not label-wrapping-input), and the page's actual click handler is bound to the `<label>`, not the `<input>`, which is why a click dispatched straight at the input never reached it. `selectAllDocuments()` was trimmed to try `label.click()` first (the manually dispatched `MouseEvent` remains only as a fallback for any room where the label element isn't found), removing a guaranteed-wasted ~400ms per room. Separately, the three fixed sleeps this Decision's original text flagged as guesswork were replaced in the same pass: the pre-processing `sleep(3500)` (redundant — `processCurrentRoom()` already polls for readiness itself) dropped to a small `sleep(500)` listener-attachment buffer; the post-processing `sleep(4500)` replaced with `waitForDownloadStart()`, a real poll against `chrome.downloads.onDeterminingFilename`'s output instead of a flat guess; the inter-room `sleep(2000)` dropped to `sleep(500)`. Confirmed faster in live testing. This closes out the "Real event-based waits" item that was sitting in the Planned list.

## Decision 8: Adaptive Concurrency — A Feedback Loop, Not a Formula

**Problem:** how many parallel tabs should run, and can that number be suggested automatically?

**Key realization:** average time-per-room can't be known before any rooms have actually completed — it depends on document counts, server load, and network conditions, none of which are predictable from the room count alone. This ruled out a one-shot calculation.

**Decision:** start conservative, measure real completion times from the first batch of processed rooms (made materially more accurate by Decision 7 removing artificial delay from that measurement), and use the *measured* rate to project remaining time and suggest — not silently apply — a concurrency change within fixed min/max bounds. The bounds themselves are set by practical limits (memory/CPU, avoiding load patterns that look like abuse to DocuSign's servers), not derived mathematically.

**Partially implemented, later, out of build order:** [Decision 17](#decision-17-user-configurable-worker-tab-count-bounded-not-unlimited) landed the bounds half of this plan (1-8, `clampWorkerTabCount()`) and manual user control via the panel - ahead of the *measured, suggested* half described above, which is still not built. The bounds' specific values (1-8) came from the same practical-limits reasoning as planned here, not from measured timing data, since that data still doesn't exist yet for this purpose.

## Decision 9: Code Organization — Why Not OOP

**Instinct considered:** convert the growing codebase to class-based OOP for better separation of concerns.

**The concrete, mechanical reason against it:** background.js, each tab's content.js instance, and the panel UI are separate JS realms connected only by `chrome.runtime.sendMessage`, which serializes all data through JSON — stripping any class instance down to a plain object with no methods on the receiving end. A class meant to represent "a worker and its behavior" can't actually span the boundary where the interesting behavior happens, because the platform itself cuts that object in half on every message. Additionally, the design has exactly one queue and one shared state object — OOP's main value (many independent instances with encapsulated state) doesn't apply to a singleton.

**Decision:** organize by splitting into focused files by concern (scan/filter logic, queue/claim logic, persistence, filename routing) using real ES modules in the MV3 service worker (`"type": "module"`, no bundler needed) and multiple shared-scope content script files — solving the actual "keep functions separated" need without fighting the platform's message-passing model.

**Correction, once `background.js` was actually built — the ES-module half of this plan didn't happen.** `manifest.json`'s `background` block never declares `"type": "module"`; `background.js` pulls in `content/utils.js` via `importScripts()`, the classic-script mechanism, not an ES `import`. This is deliberate, not an oversight: `content/utils.js` is written as plain global function declarations specifically so the identical file works unmodified as both a content script (loaded via `manifest.json`'s `content_scripts` array) and inside the service worker (loaded via `importScripts()`) — switching to real ES modules would have meant either two copies of that file or a build step to reconcile the two loading mechanisms, for a shared-utilities file with barely a hundred lines. `background.js` itself was also never split into separate scan/filter, queue/claim, persistence, and filename-routing files as planned above — `claimNextRoom()`, `processRoom()`, `persistJob()`, and the `onDeterminingFilename` listener all still live in the one file, organized by section rather than by separate loaded modules. The "split by concern" half of this decision landed only on the content-script side (`content/utils.js` / `content/scan.js` / `content/room.js`, see Decision 10) — `background.js` staying a single file hasn't caused a real problem yet, so splitting it further hasn't been worth doing for its own sake.

## Final Build Plan (Deliberately Risk-Ordered)

Rather than building all of the above simultaneously, the plan builds and tests in increasing order of risk, so a bug is always isolated to the one new layer just added:

1. **Scanning + filtering + list export**, tested alone — no download logic touched yet.
2. **Single-tab processing with event-driven waits** replacing fixed sleeps — verify speed and correct empty-room detection before adding concurrency.
3. **Full per-room lifecycle status + panel UI** (queued → in progress → done/failed/empty), still single tab.
4. **Persistence and resume**, tested by deliberately killing/reloading the extension mid-run.
5. **The worker-tab pool** (claim-based queue, per-tab filename routing) — introduced last, once everything underneath it is proven solid on one tab.
6. **Min/max bounds + adaptive concurrency suggestion**, which depends on real timing data from step 5.

A small, narrow-date-range dry run (a few dozen rooms) is run through the entire pipeline before trusting it against the full 10,000-room set.

## Build Step 1: Scanning + Filtering + List Export (Complete)

This section records Step 1's actual implementation decisions as they happened, separately from the pre-implementation planning above — kept in its original, in-the-moment voice (including the "in progress" framing of the notes within it) rather than rewritten in hindsight, since that's an honest record of the order things were actually found and fixed. See [Current Implementation Status](#current-implementation-status) above for where the step numbering actually stands today.

### Decision 10: Splitting content.js by Dependency, Not by File History

**Problem:** `content.js` originally held every scan/scroll/utility/room-page function in one file behind a single IIFE. Once real logic (date filtering, later a worker-tab pool) started landing, that made it hard to see which functions were actually related to which concern.

**Constraint carried over from the planning phase:** content scripts aren't real ES modules — every file listed in `manifest.json`'s `content_scripts` array shares one execution scope, in load order. No IIFE wrapper per file (it would hide top-level declarations from the other files); the only thing enforcing correctness is getting the array order right.

**Decision:** three files, grouped by actual call relationships rather than by where the code originally sat in the single file:
- `content/utils.js` — generic string/URL helpers with no DOM/page context (`sleep`, `cleanName`, `normalizeText`, `getRoomIdFromUrl`, `roomUrlToDocumentsUrl`). The deciding signal for what belongs here: functions called from *more than one* of the other groups (`normalizeText` and `cleanName` are each used by both the scan flow and the room-page flow) — a shared dependency shouldn't be owned by either consumer.
- `content/scan.js` — the Rooms-*list*-page flow: `getScrollContainer`, `getRoomCardsAndLinks`, `autoScrollAndCollectRooms`.
- `content/room.js` — Rooms-*page* concerns, currently just `getRoomNameFromPage`. Named ahead of need: the original plan was for Build Step 2 to move `clickElement`, `selectAllDocuments`, `findBulkDownloadButton`, `findFinalDownloadButton`, `waitForSelector`, and `processCurrentRoom` out of `content.js` into this same file later, since they're the same category of concern — avoiding a rename/re-split later for one function that would otherwise sit alone. **That move never happened, by deliberate choice, not oversight:** `content/room.js`'s own header comment records the decision explicitly — those functions are a pure reorganization with no functional benefit, so time went to the roadmap items that actually change behavior (date-range filtering, concurrency, folder-uniqueness) instead. They still live in `content.js` today.

Load order requirement: `utils.js` must load before `scan.js` and `room.js` (both depend on it); those two don't depend on each other, so their relative order doesn't matter; `content.js` still loads last.

### Decision 11: Replacing Two DOM Heuristics with DevTools-Confirmed Behavior

**Problem:** two functions in the original code (`getRoomCardsAndLinks` and `findBestScrollContainer`) were built on *guesses about DOM shape* rather than confirmed structure — the same category of fragility already flagged conceptually in Decision 4, now actually being resolved during implementation.

**`getRoomCardsAndLinks`:** the original climbed up from any `a[href]` via `.closest()` through a fallback chain of ancestor types and guessed the room name from the first line of the row's rendered text. Verified against the live page's actual markup instead: a real `<table>` with explicit `data-qa` attributes — `tr[data-qa="room-list-row"]` for each row, `strong[data-qa="room-name"]` (its `title` attribute holds the untruncated name; the extension previously risked failing on CSS-truncated names by reading rendered text instead), and `strong[data-qa="room-date"]`. Rewritten to query these directly. This also adds a `createdDate` field to each room record, which the still-pending date-range filter (Decision 4) depends on.

**`findBestScrollContainer`:** the original queried every `div`, `main`, `section`, `body`, and `html` on the page and picked whichever had the largest `scrollHeight - clientHeight`, on the theory that the room list was probably "the tallest scrollable thing." Verified instead of assumed: selected the Rooms-list container and the table's wrapper in DevTools and ran `getComputedStyle(el).overflowY` against each, plus `document.documentElement` and `document.body` directly. All four returned `"visible"` — confirming this page has **no internally-scrolling wrapper at all**; it's plain document/page scrolling. Replaced the entire heuristic with a one-line `getScrollContainer()` returning `document.scrollingElement || document.documentElement`, and removed the `try/catch` fallback around the scroll call in `autoScrollAndCollectRooms` — it existed only to hedge against the old heuristic possibly returning an element without a working `.scrollTo`, which is no longer a reachable failure mode now that the returned element is guaranteed to be the document's own scrolling element.

**Caveat recorded deliberately, not glossed over:** this is confirmed for the current page rendering at the row counts tested. If DocuSign later switches to a virtualized/windowed list for very long lists (rendering only on-screen rows inside a scrolling wrapper, a common technique at this kind of scale), this assumption would need re-verifying — the symptom to watch for is the scanned room count plateauing while more rooms are known to exist.

**Status (superseded below):** at this point Step 1 had the file split and the selector/scroll fixes in place, with the date-range logic, CSV export, and manifest wiring still outstanding. The date-range skip/collect/stop logic (Decision 4's design) was subsequently implemented by hand — including catching and fixing a real bug during review, where the streak counter was tripping on rooms that were merely too *early* rather than only rooms past the end date, which would have silently returned zero results on any account whose earliest rooms predate the configured start date.

### Decision 12: Closing Out Build Step 1 Under Time Pressure — CSV Export, Manifest Wiring

**Problem:** with a real deadline approaching, finishing the remaining Build Step 1 items by hand (CSV export of the scanned list, the manifest fix) would cost more time than was available, but abandoning the guided, human-typed approach silently would misrepresent how the codebase was actually built (see the process note below).

**Decision:** made explicitly, not by default — asked directly which of three modes to use (AI writes it, a boilerplate/logic hybrid split, or continuing fully guided at a faster pace) and went with full AI implementation for the remainder of Build Step 1, under human review, given the time constraint. This is recorded as a decision with a real tradeoff, not a neutral implementation detail.

**What this covered:**
- Fixed a bug introduced while manually wiring `manifest.json`'s `content_scripts` array by hand: the paths were written as `"utils.js"`, `"scan.js"`, `"room.js"` instead of `"content/utils.js"`, `"content/scan.js"`, `"content/room.js"` — the files live in the `content/` subfolder, so Chrome would have failed to load them.
- Added CSV export for the scanned/filtered room list. Content scripts have no access to `chrome.downloads` (confirmed in Decision 4's era of planning) — only the background service worker does — so this required a new message type, `DS_EXPORT_SCAN_LIST`, sent from `content.js` to `background.js`, which builds the CSV (reusing the existing `csvEscape`/`nowStamp` helpers already used by `createReport()`) and saves it to `Docusign Rooms/_Scan Lists/`.
- Added a dedicated "Scan & Export List (CSV)" button to the panel, deliberately kept **separate** from the existing Start button rather than merged into it — preserving the Build Step 1 philosophy of testing scanning/filtering/export in isolation, with zero risk to the already-working single-tab download flow (`DS_START_QUEUE` → `runQueue`), which needed no changes at all.

**Correction to the paragraph above, once real room-page markup was captured:** `selectAllDocuments()` did need a change after all. The original function only located the Select All *label's text span* (`[data-qa="select-all-docs-label-text"]`) and then guessed at a clickable ancestor via a fallback chain (`label.closest("label") || label.closest("[class*='select']") || label.parentElement?.parentElement?.parentElement || ...`) — the same category of DOM-shape guesswork already replaced with confirmed selectors in Decision 11. Verified against the room Documents page's actual markup: the checkbox itself carries its own `data-qa="select-all-docs"` attribute, directly clickable with no ancestor-climbing needed at all. Replaced the ~25-line guess-chain with a direct `document.querySelector('input[data-qa="select-all-docs"]')` lookup.

**Second correction:** the room's group header, `[data-qa="group-name"]`, was also captured in both an empty room (`"Room Docs (0)"`) and a populated one (`"Room Docs (11)"`) — present in *both* states, unlike the Select All checkbox, which never renders at all when a room is empty. This directly overturns Decision 4's "confirmed: not free" conclusion, but only for the *processing* phase, not the scan phase — the room list still has no visible document count, so scanning still can't skip empty rooms upfront. What it does fix: the original `processCurrentRoom()` waited on the Select All checkbox specifically, which meant every empty room burned the full 45-second timeout before failing. Fixed to wait on `group-name` instead (present either way) and short-circuit immediately if the parsed count is `0`. Caveat, not yet verified: this reads only the first `group-name` element on the page; a room with multiple document folders would need the counts summed, and no such room has been inspected yet.

**Third correction, closing out the last guesswork in single-room processing:** real markup for the post-Download confirmation modal was captured. Two findings: (1) its confirm button, `<button class="btn-action" type="submit">Download</button>` inside `<form id="formDownloadDocuments">`, carries no `data-qa` at all — unusual for this app, a sign this particular modal is an older jQuery-driven component (`ctv.documents.initDownload(...)`) bolted onto the otherwise React-based UI. The original `findFinalDownloadButton()` worked around the missing `data-qa` by scanning every visible button/link on the page for text matching "download" — functional by coincidence, fragile in principle, since any other visible "download"-labeled control anywhere on the page would collide with it. Replaced with a selector scoped to the form's own stable `id`: `#formDownloadDocuments button[type="submit"]`. (2) The original code also did `await sleep(3500)` after clicking Bulk Download, gambling the modal would be open by then, before ever checking for it — the same fixed-delay guesswork Decision 7 eliminated elsewhere. Replaced with `waitForSelector('#formDownloadDocuments button[type="submit"]', 10000)`, resolving the instant the modal actually appears instead of always waiting the full guessed amount. `findBulkDownloadButton()` needed no change — its existing selector matched the captured markup exactly, the one place in this whole pass where prior guesswork happened to already be correct.

**Fourth correction:** the full room detail page (Details tab, not just Documents) was captured, revealing `<strong data-qa="room-name">` as the room's own confirmed name element — the same fix pattern applied to `getRoomNameFromPage()`, replacing a 6-selector guessing chain (`[data-qa*='room-name']`, `[data-qa*='room-title']`, `h1`, three class-name heuristics) plus a `document.title`-scrubbing fallback with one direct, confirmed lookup. This had a side effect worth recording: `normalizeText()` in `content/utils.js` (documented in Decision 10 as shared by both the scan and room-page flows) was only ever called from two places — this function, and the text-matching branch of `findFinalDownloadButton()` removed in the correction above. With both callers gone, it became genuinely dead code and was deleted rather than left in `utils.js` unused. Decision 10's original text describing it as a shared dependency is left as-written above (an accurate record of the reasoning *at the time*); this note is the correction, not a rewrite of that history.

## Decision 13: Automated Testing Strategy

**Problem:** every fix in this project so far had been verified by live testing against a real DocuSign account — real, but slow, and it can't catch a regression until someone happens to click through the affected path again. Worth automating what can be, without pretending DOM automation and timing-dependent browser behavior can be unit tested the same way.

**Constraint discovered before any test could be written:** this machine had no Node.js, npm, or Homebrew installed at all — none of the usual JS testing tooling existed yet. Installing Node's official `.pkg` from nodejs.org needed `sudo`, which needs an interactive password prompt this environment's shell doesn't have; worked around with `osascript -e '... with administrator privileges'`, which triggers macOS's native GUI credential dialog instead of a terminal prompt. Installed: Node.js v24.19.0 (the current LTS release, "Krypton").

**What's actually testable vs. not:** `content/utils.js`'s string/URL/CSV helpers (`cleanName`, `getRoomIdFromUrl`, `roomUrlToDocumentsUrl`, `parseCsv`) and several of `background.js`'s functions (`computeFolderNames`, `csvEscape`, `nowStamp`, `claimNextRoom`, `findCurrentRoomForDownload`) are pure or close to it — no real DOM, no live `chrome.*` calls, no timing dependence. Everything else - `content.js`'s DOM-scraping and click-simulation logic, `background.js`'s tab orchestration and download-waiting - is fundamentally about *driving a real browser against a real page*, which a unit test can't meaningfully fake without testing the fake instead of the real risk. That code stays covered by live testing against the real account, as it always has been - automated testing here targets what changed this session for a reason (the pure-logic bugs: `computeFolderNames`' collision handling, `findCurrentRoomForDownload`'s URL matching), not blanket coverage for its own sake.

**Update:** this line was originally accurate but became a trap for later features - `content.js`'s per-feature helper functions (date-range labeling, worker-tab-count validation, activity-log formatting) got written *inside* `content.js`'s closure by default, since that's where they were used, silently falling into the "untestable DOM-heavy code" bucket even though they touched no DOM at all. [Decision 19](#decision-19-pre-real-run-review-pass) caught and fixed this - the actual boundary was never "which file," it was "does this function touch the DOM," and several functions had been on the wrong side of that line purely by accident of where they were first written.

**Why Node's built-in `node:test` instead of a framework (Jest/Vitest/Mocha):** zero dependencies to install, audit, or update — genuinely appropriate for a project this size, where the entire test surface is a handful of pure functions, not a reason to reach for tooling built for much larger test suites. `node --test` (glob: `node --test tests/**/*.test.js` — `node --test tests/` alone doesn't reliably recurse) needs no `node_modules` at all.

**The real obstacle: these files were never written to be `require()`-able.** `content/utils.js` and `background.js` are plain global function declarations by design (see `content/utils.js`'s own header comment and [Decision 9](#decision-9-code-organization--why-not-oop)) - the right shape for a content script / `importScripts()`-loaded service worker, but `module` and `require` don't exist in either of those real runtimes, and conversely `background.js`'s literal `importScripts("content/utils.js")` call throws immediately under Node (`importScripts` doesn't exist there either). Solved with a guard at each boundary rather than restructuring the files: `content/utils.js` gets an export tail — `if (typeof module !== "undefined" && module.exports) { module.exports = {...}; Object.assign(globalThis, module.exports); }` — that's a no-op in the browser (`module` is never defined there) and, under Node, both exports the functions *and* attaches them to `globalThis`, reproducing the same shared-global-scope behavior the browser gives content scripts for free via `manifest.json`'s load order. `background.js`'s `importScripts` call became `if (typeof importScripts === "function") { importScripts(...) } else if (typeof require === "function") { require("./content/utils.js") }`, and it gets its own export tail exposing `{ STATE, computeFolderNames, csvEscape, nowStamp, claimNextRoom, findCurrentRoomForDownload }`. None of this changes what ships to Chrome — both branches are permanently unreachable in that environment, confirmed by the fact the guards are already exactly how `content/utils.js` was written before any of this: the file already needed to detect "am I being loaded as a content script or via `importScripts()`" for reasons unrelated to testing (see its header comment) - this is the same category of guard, one more case added to it.

**`background.js`'s top-level side effects** (`chrome.runtime.onMessage.addListener(...)`, the two `chrome.downloads.*` listener registrations, and the startup-resume IIFE that calls `chrome.storage.local.get`) all run immediately the moment the file is loaded — including under `require()`. `tests/helpers/chrome-stub.js` provides a minimal fake `chrome` object (no-op `addListener`s, `storage.local.get` resolving to `{}` so the resume IIFE finds nothing and returns immediately) assigned to `global.chrome` before each `require()` - just enough that loading the file doesn't throw, not a behavioral mock of Chrome itself. `tests/helpers/load-background.js` clears both `background.js`'s and `content/utils.js`'s entries from Node's `require.cache` on every call, so each test gets a fresh, isolated `STATE` object instead of leaking mutations across tests through the module cache (`STATE` is exported by reference, and `claimNextRoom`/`findCurrentRoomForDownload` both read and write it directly rather than taking it as a parameter — correct for production, where there's exactly one `STATE`, but it means tests must reset it explicitly rather than relying on pure-function isolation).

**What's actually covered**, 24 tests across `tests/utils.test.js` and `tests/background.test.js`: `cleanName`'s character-stripping/whitespace-collapsing/length-capping/empty-fallback behavior; `getRoomIdFromUrl` and `roomUrlToDocumentsUrl`'s regex matching including the non-matching case; `parseCsv`'s quoted-field/embedded-comma/doubled-quote/CRLF handling; `csvEscape`'s null/undefined handling; `nowStamp`'s format; `claimNextRoom`'s ordering and its refusal to advance past `pending.length`; and, as direct regression tests for two of this session's real live-testing bugs, `computeFolderNames` given two same-named-but-different-ID rooms (the "Ponchak - Listing" incident, [Decision 2](#decision-2-parallelism-model--work-queue-not-divide-and-conquer)'s fourth correction) and `findCurrentRoomForDownload` given a `DownloadItem` shaped like the real captured one that exposed the `target="_blank"`/`/transaction/` bug (the same decision's second and third corrections). Run via `npm test` (or `node --test tests/**/*.test.js`) from inside `Docusign rooms download/`.

## Decision 14: Per-Worker-Tab Status Breakdown

**Problem:** the panel's live status, since the worker pool landed ([Decision 2](#decision-2-parallelism-model--work-queue-not-divide-and-conquer)), showed only an aggregate count and a flat list of room names ("Running: 3 active (Room A, Room B, Room C)") - real information, but not which *tab* had which room, or how long it had been stuck there, which matters once something is actually running slow and you want to know if it's one straggling worker or the whole pool.

**What was missing to build this:** `broadcastStatus()` and the `DS_GET_STATUS` handler already sent `currentRooms` (an array built from `STATE.currentRooms`, keyed internally by tab ID but flattened to an array on the wire) - tab identity was there in the *keys* of the source object but got dropped the moment `Object.values()` flattened it for the message. Worker *identity* (a stable "Worker 1/2/3" label, not Chrome's own meaningless-to-a-user tab ID) wasn't sent at all - `STATE.workerTabIds` existed only inside `background.js`.

**Decision:** send both pieces of missing information rather than reconstructing them client-side from something else. `processRoom()`'s `STATE.currentRooms[tabId] = {...}` now includes `tabId` (redundant with the object's own key, but the array shape sent over the wire needs it explicitly once flattened) and `claimedAt` (an ISO timestamp, for computing elapsed time). Both `broadcastStatus()` and `DS_GET_STATUS` now also send `workerTabIds: STATE.workerTabIds` - the tab-creation-order array already used internally, now exposed so the panel can label rows "Worker 1", "Worker 2", etc. consistently across updates instead of by raw tab ID.

**Panel side (`content.js`):** two new render functions, both driven off the same status payload both existing call sites (`DS_BULK_STATUS` listener and the initial `DS_GET_STATUS` fetch on panel load) already received - `renderWorkers(s)` builds one row per entry in `s.workerTabIds`, looking up that tab's current room (if any) in a `Map` built from `s.currentRooms`, and showing "Worker N: idle" for a tab between rooms or with no work left; `renderBreakdown(s)` tallies `s.results` by `.status` (`Downloaded`, `Failed`, `Download Error`, the transient `Success/Attempted`) plus a derived `Waiting` count (`total - results.length`) for rooms not yet reached - a result-by-outcome summary that previously required opening the final CSV report to see.

**Built with DOM APIs (`createElement`/`.textContent`), not `innerHTML`, deliberately:** room names reaching the panel have already been through `cleanName()` (see `background.js`'s `DS_ROOM_PAGE_INFO` handler), which happens to strip `<`/`>` among other characters - but that's a filename-safety guarantee, not a security one, and leaning on it as the only defense against a room name breaking out of an `innerHTML` string would be fragile against `cleanName()` ever changing for unrelated filename reasons. `.textContent` per row costs nothing extra here and doesn't depend on that staying true.

**Elapsed time is recomputed from `claimedAt` on every incoming status message, not a live client-side ticking clock.** `broadcastStatus()` already fires reasonably often while a run is active (every room claim, every pause-loop tick, every completion) - a `setInterval` in the panel for second-by-second accuracy would be real added complexity (a timer to create, clear on panel teardown, and reason about across the run's start/stop/pause transitions) for a gain barely visible to a person glancing at the panel.

**Scope, recorded explicitly rather than left ambiguous:** this is a per-*worker* breakdown (bounded by `WORKER_TAB_COUNT`, currently 3 rows), not the full per-*room* queued/in-progress/done/failed/empty breakdown originally scoped for [Build Step 3](#final-build-plan-deliberately-risk-ordered) - see the [Current Implementation Status](#current-implementation-status) table for why a full 10,000-row version is being treated as a separate, not-yet-scoped feature rather than a small extension of this one.

## Decision 15: Worker/Service-Worker Lifecycle Event Log

**Problem:** a live persistence test - deliberately terminating the service worker via `chrome://serviceworker-internals` (the reliable way to do this; the "service worker" link on `chrome://extensions` only opens an inspector, it doesn't kill anything) and then reopening a Rooms tab to see if the run picked back up - reported "it did not resume." With no visibility into *why*, the only options were re-guessing at the same three hypotheses [Decision 6](#decision-6-persistence--the-mv3-service-worker-lifecycle) already reasoned through (no persisted job, nothing pending, or a race with `STATE.running`) with no way to tell which one actually happened - and STATE itself, the only place that information could have lived, gets wiped by the very event (a service worker restart) most worth investigating.

**Decision:** add a lightweight lifecycle event log - not a general-purpose logging framework, specifically the handful of events needed to answer "did the service worker restart, did resume even attempt to run, and if not, why not" plus the worker-tab equivalent from [Decision 2](#decision-2-parallelism-model--work-queue-not-divide-and-conquer)'s fifth correction ("did a worker tab die, did it get replaced").

**Implemented.** `logWorkerEvent(type, detail)` appends a `{time, type, ...detail}` object to `STATE.workerEvents`, trimmed to the most recent `MAX_WORKER_EVENTS` (300) so a very long run can't grow it unboundedly, and `console.log`s it immediately (visible in the service worker console without needing the panel open at all). Persisted as part of `persistJob()`'s snapshot specifically so it survives a restart - the one event most worth seeing is also the one that wipes an in-memory-only log, so persisting anything less than this would have missed the exact case this was built for.

Events logged: `service_worker_started` (unconditionally, at the very top of the startup resume IIFE, before any of its early-return checks - this alone answers "did the service worker even restart" regardless of what happens next); `resume_skipped` with a `reason` string for each of the three ways resume can decline to run (no persisted job / persisted job has nothing pending / `STATE.running` already true); `run_resumed` with the pending/total counts when it does proceed; and, from the worker-tab recovery fix, `worker_tab_created`, `worker_tab_dead`, `worker_tab_replaced`, and `worker_tab_replace_failed`.

**Ordering matters and was easy to get backwards:** the startup IIFE now restores `STATE.workerEvents = job.workerEvents` *before* calling `logWorkerEvent("service_worker_started", ...)` - restoring after would have overwritten the freshly-logged entry with the (older) persisted array a few lines later, silently dropping the very event this was built to capture.

**Panel side:** `broadcastStatus()` and `DS_GET_STATUS` both send `STATE.workerEvents.slice(-20)` (recent-only; the full history stays in `STATE`/storage, the panel doesn't need the entire run's log in every message). Rendered in a collapsed-by-default `<details>` element ("Activity Log") so it doesn't add visual weight to the panel's default state, newest-first, each event turned into a short line by a `describeWorkerEvent()` switch (originally written as `content.js`'s own local `describeEvent()`, later moved to `content/utils.js` - see [Decision 19](#decision-19-pre-real-run-review-pass) - the event objects themselves stay plain/serializable, since they also have to survive a `chrome.storage.local` round-trip).

**What this does and doesn't fix:** this is diagnostic infrastructure, not a fix for the "did not resume" report that motivated it - that investigation is still open. What it changes is that the *next* time it's tested, the event log will show exactly which of the three `resume_skipped` reasons applied (or that `service_worker_started` never even fired at all, which would point at `chrome://serviceworker-internals`'s "Stop" not having actually terminated the worker) instead of it being an unanswerable "nothing happened."

**Tested for the parts that are pure/deterministic:** `logWorkerEvent`'s shape and trimming behavior, and the startup IIFE's three logged outcomes (no job / nothing pending / resumed) via a `storageLocalGet` override in the test helper - see `tests/background.test.js`. Not tested: the worker-tab replacement path itself, which needs real `chrome.tabs` behavior to mean anything (consistent with this project's whole testing scope - see [Decision 13](#decision-13-automated-testing-strategy)).

**Extended, once the panel's Activity Log proved useful in live testing - saved to a file too, not just shown live.** The panel truncates to the most recent 20 events and only exists while that specific tab is open; `chrome.storage.local`'s copy is cleared the moment a run's job is (`clearPersistedJob()`, right before the reports are written). Without a file, the history behind a given run's outcome couldn't be inspected after the fact - exactly the situation Decision 15 was built to avoid in the first place, just one step further down the pipeline. `createEventLogReport()` mirrors `createReport()`'s shape (same `csvEscape`/`nowStamp` helpers, same `chrome.downloads.download()` call, same `Docusign Rooms/_<category>/` folder convention - here `_Activity Logs/`) and is called from the same `runQueue()` completion point, right after `createReport()`, which already covers both a natural finish and an explicit Stop. Exports the *entire* accumulated `STATE.workerEvents`, not just what happened during this specific run - it's a lifecycle log of the service worker and its worker tabs, and slicing it to one run would lose the cross-restart picture that's the whole point. Each event's varying `detail` fields (different keys depending on `type`) are kept as one JSON-stringified column rather than forced into a fixed set of CSV columns most rows wouldn't use.

## Decision 16: Every content.js → background.js Message Needs Error Handling, Not Just Some

**Problem, found live:** "Scan & Export List (CSV)" got stuck on "Exporting CSV..." forever. The page console showed `content.js:724 Uncaught (in promise) Error: Extension context invalidated` - the same root cause as an earlier session's fix (reloading the extension orphans any content script already injected in an open tab; the orphaned instance's `chrome.runtime.sendMessage` calls can't reach the new background instance). That earlier fix added `.catch(() => {})` to `DS_STOP`/`DS_PAUSE`/`DS_RESUME`'s `sendMessage` calls - but missed `DS_START_QUEUE` (in `beginRun()`) and `DS_EXPORT_SCAN_LIST`, both of which use the two-argument `sendMessage(message, callback)` form instead of the one-argument promise form the fixed calls use. Same failure mode, inconsistently patched.

**The fix itself had a bug on the first attempt, caught immediately by checking Chrome's actual API contract rather than assuming the fix worked:** the instinct was to chain `.catch()` onto the existing two-argument calls directly - `chrome.runtime.sendMessage({...}, callback).catch(...)`. This is wrong: per Chrome's documented API contract, `sendMessage` returns `undefined` when a callback argument is supplied, and only returns a Promise when called with *no* callback. Chaining `.catch()` onto `undefined` throws a `TypeError` synchronously, on every single call - which would have made the Start button and CSV export both fail immediately, unconditionally, a strictly worse bug than the one being fixed. Caught before landing by checking the API contract against the already-correct `DS_STOP`/`DS_PAUSE`/`DS_RESUME` calls, which use the single-argument promise form specifically because that's what makes `.catch()` meaningful.

**Fixed correctly:** `DS_START_QUEUE`, `DS_EXPORT_SCAN_LIST`, and `DS_GET_STATUS` (the initial status fetch on panel load - same gap, not yet reported live but the same class of bug) were all converted to the single-argument `sendMessage(message).then(...).catch(...)` form, matching the pattern already proven correct elsewhere in the file. Every `chrome.runtime.sendMessage` call in `content.js` now has explicit error handling for a stale/invalidated context - none silently hang or throw an uncaught rejection anymore. The user-facing message on failure ("Could not reach the extension - reload this page and try again") turns a silent, indefinite hang into an actionable instruction.

## Decision 17: User-Configurable Worker Tab Count, Bounded Not Unlimited

**Problem:** `WORKER_TAB_COUNT` had been a hardcoded `3` since [Decision 2](#decision-2-parallelism-model--work-queue-not-divide-and-conquer) - a deliberate first-pass choice, not a permanent one, and the [Roadmap](../README.md#status) (since renamed to "Status") always scoped a follow-up. Asked directly whether to build this now: yes, on the reasoning that it's a small, additive change (one `STATE` field, one message field, one UI input) that doesn't touch any of the currently-tested pure logic, and it gives a real dial to help the ongoing 10k-scale investigation (dropping to 1 tab would help isolate whether tab count itself contributes to the worker-tab-death pattern under active investigation) rather than waiting on the fuller adaptive-suggestion feature in [Decision 8](#decision-8-adaptive-concurrency--a-feedback-loop-not-a-formula).

**Decision: bounded, not an open number field.** `MIN_WORKER_TAB_COUNT` (1) and `MAX_WORKER_TAB_COUNT` (8) cap what the panel's "Worker Tabs" input will accept - several 10k-scale risks (worker tabs dying, `chrome.storage.local`'s quota, DocuSign rate-limiting) are still open questions at the current default of 3; letting someone dial this to 20 before those are resolved would compound the exact risks being chased down, not help diagnose them. This is explicitly a stepping stone toward Decision 8's original plan (suggest a value from measured timing, don't just accept any manual number forever), not a replacement for it.

**Implemented.** `clampWorkerTabCount(value)` in `background.js` is the single source of truth for validation - coerces arbitrary input into `[MIN, MAX]`, rounding a non-integer to the nearest whole tab count. `STATE.workerTabCount` (default `DEFAULT_WORKER_TAB_COUNT`, 3) replaces the old constant everywhere it was read (`runQueue()`'s tab-count calculation). Set from `message.workerTabCount` in the `DS_START_QUEUE` handler, and persisted via `persistJob()` so a resumed run keeps using the same count it started with rather than silently reverting to the default - the startup resume IIFE restores it through the same `clampWorkerTabCount()` call, which also covers a job persisted by an older version of the extension that didn't have this field at all (missing input and invalid input get identical, deliberate treatment: fall back to the default, don't guess). `content.js` mirrors the same three bounds as local constants (content scripts and the service worker are separate JS contexts, per [Decision 9](#decision-9-code-organization--why-not-oop)'s reasoning) purely for the input's UI bounds - `clampWorkerTabCount()` on the `background.js` side re-validates regardless, so a mismatch between the two copies couldn't let an out-of-range value through even if it happened.

**A real bug, caught by the tests written for this feature, not found live:** the first version of `clampWorkerTabCount()` checked only `Number.isFinite(Number(value))` before clamping. `Number(null)` is `0` - a real finite number, which `Number.isFinite` accepts - so `clampWorkerTabCount(null)` clamped *up* to `MIN_WORKER_TAB_COUNT` (1) instead of falling back to the default, silently treating "no value was ever provided" the same as "the user asked for zero tabs." The equivalent gap existed in `content.js`'s `readWorkerTabCount()`, where an emptied `<input type="number">` has `.value === ""` (never `null`), and `Number("")` is *also* `0` for the same reason. Both fixed with an explicit check for `null`/`undefined`/`""` before the numeric coercion, returning the default directly rather than letting them fall through to be clamped as if they were real (if extreme) numbers. Caught while writing `tests/background.test.js`'s coverage for this function, before it ever reached live testing - the value of writing the fallback-behavior test *before* trusting the implementation matched its own doc comment.

**Tested:** `clampWorkerTabCount()`'s full behavior (in-range pass-through, clamping below `MIN` and above `MAX`, rounding non-integers, the `null`/`undefined`/non-numeric/`NaN`/`Infinity` fallback, and a numeric string as arrives from an HTML input) plus the startup resume path restoring `workerTabCount` from a persisted job, clamped, and falling back to the default for a job that predates this field. Not tested: the `content.js` UI input itself or the full `DS_START_QUEUE` message-handling path, consistent with this project's established testing scope (see [Decision 13](#decision-13-automated-testing-strategy)) - `readWorkerTabCount()`'s logic is simple enough, and mirrors the now-tested `clampWorkerTabCount()` closely enough, that the risk left uncovered here is small relative to the DOM-heavy code this project has consistently left to live testing instead.

## Decision 18: Date-Range Labels in Exported CSV Filenames

**Problem, raised directly by live testing across many test runs the same day:** every scan list, download report, and activity log export used only a raw timestamp for a filename (`Scan List 2026-08-11_16-43-05.csv`) - after several test runs in one session, the Downloads folder fills with files distinguishable only by generation time, not by what date range or account state they actually cover. Requested explicitly: make all three identifiable by filename alone, without opening them.

**Decision:** thread a human-readable date-range label through to all three exports rather than inventing a separate identifier - the scan's own From/To range is already the thing a user would think of a given export "as." `content.js`'s `formatDateRangeLabel(dateRange)` turns the panel's date inputs into `"2026-01-01 to 2026-03-01"`; `background.js`'s `labeledFilename(baseName, dateRangeLabel)` wraps it in parentheses and appends the existing timestamp (`"Scan List (2026-01-01 to 2026-03-01) 2026-08-11_16-43-05"`), used by all three export functions (`createReport()`, `createEventLogReport()`, and the `DS_EXPORT_SCAN_LIST` handler) so they share one naming convention instead of three ad hoc ones.

**Graceful degradation for CSV-upload-based runs, not an edge case bolted on afterward:** a run started by uploading a CSV (rather than a live scan) has no date range at all - the rooms came from a file, not a From/To scan. `beginRun()`'s `dateRangeLabel` parameter defaults to `null` and is simply omitted at that call site; `labeledFilename()` treats `null` as "no label" and falls back to the exact plain-timestamp filename these exports always used, rather than requiring every caller to fabricate a label that doesn't semantically exist. The alternative - inventing a label for the CSV-upload case too - would have implied a date range that was never actually scanned, which would have been actively misleading rather than merely incomplete.

**Persisted, not recomputed:** `STATE.runDateRangeLabel` is set once in the `DS_START_QUEUE` handler (from `message.dateRangeLabel`) and saved via `persistJob()`, so a run that gets interrupted and resumed after a service-worker restart still produces a report carrying its *original* run's label - not `null` (the resumed instance's fresh `STATE` would otherwise have no way to know what the original scan's range was) and not a fabricated new one. Restored in the startup resume IIFE the same way `workerTabCount` is, with the same fallback (a job persisted before this field existed, or one with no label at all, resolves to `null` - the plain-filename case, exactly as intended).

**Sanitized the same way every other filename-building path in this file already is:** `labeledFilename()` runs the label through `cleanName()` before using it, even though the only real producer of this string (`formatDateRangeLabel()`) only ever emits digits, hyphens, spaces, and the word "to" and could never contain a forbidden filesystem character. Defensive, not load-bearing for the expected case - consistent with how every other value that ends up in a `chrome.downloads.download()` path in this codebase is treated, not a special exception for this one.

**Tested:** `labeledFilename()`'s label-present and label-absent (`null`) shapes, and that a deliberately-adversarial label (forbidden filesystem characters) can't survive into the output despite not being a realistic input; the startup resume path restoring `runDateRangeLabel` from a persisted job and falling back to `null` for a job that predates this field. `formatDateRangeLabel()` itself was originally written inline inside `content.js` and left untested (there being no way to test it there) - moved to `content/utils.js` and given real coverage in [Decision 19](#decision-19-pre-real-run-review-pass), once that was recognized as an accident of where it was first written rather than a deliberate scope decision.

## Decision 19: Pre-Real-Run Review Pass

**Problem:** asked directly to go over the whole codebase - code, logic, documentation, tests - before committing to a real (larger than ~25-room) run, rather than continuing to find things one live-testing cycle at a time. A deliberate shift from the pattern used everywhere else in this log (fix what live testing surfaces) to reviewing code for correctness *before* it's exercised.

**A real, previously-undiscovered bug found this way, not live: `ensureWorkerTabs()` only ever grew the worker-tab pool, never shrank it.** The function's loop was `while (STATE.workerTabIds.length < count)` - nothing handled the case where more *alive* tabs already existed than the current run wanted. Combined with `DS_START_QUEUE` never resetting `STATE.workerTabIds` between runs (worker tabs are deliberately never auto-closed - see the `runQueue()` completion comment), this meant: start a run with Worker Tabs = 5, stop it (tabs stay open, by design), then start a *second* run in the same service-worker session with Worker Tabs = 2 - `ensureWorkerTabs(2)` would find all 5 previous tabs still alive, and since `5 < 2` is false, return all 5 unchanged. The second run would silently use 5 workers, not the 2 actually requested, with no error or indication anything was wrong. This is exactly the scenario the worker-tab-count feature was built partly *for* (dialing concurrency down to isolate the 10k-scale worker-tab-death investigation, per [Decision 17](#decision-17-user-configurable-worker-tab-count-bounded-not-unlimited)'s own stated motivation) - a bug that would have specifically undermined the feature's most likely real use. Fixed by adding a shrink step after the existing grow loop: `if (STATE.workerTabIds.length > count) { STATE.workerTabIds = STATE.workerTabIds.slice(0, count); }` - the excess tabs are left open, not closed, consistent with this file never closing worker tabs on its own; they're just no longer tracked as workers for that run.

**The Stop-race fix from live testing, written up here since it hadn't been documented yet:** a user report ("when I stopped it just kept opening new tabs") traced to a narrow window in `runWorker()`'s loop - a worker's tab could die in the instant *between* passing the `waitIfPausedOrStopped()` gate at the top of the loop and reaching the tab-liveness check just after it, and if `STATE.stopped` became true in exactly that gap, the worker would still open a replacement tab for a run that was already ending. Fixed with a second `if (STATE.stopped) break;` check placed right before `chrome.tabs.create()` in the replacement path, so a worker never opens a new tab once Stop has been registered, no matter how narrow the timing.

**Testability audit: three functions were untestable by accident, not by design.** Reviewing what actually has test coverage against everything that reasonably could turned up `formatDateRangeLabel()`, the clamping logic inside `readWorkerTabCount()`, and `describeEvent()` (as it was then named) - all three pure (no DOM access at all) but written as local functions nested inside `content.js`'s `injectPanel()` closure, simply because that's where they were first needed. `content.js` can't safely get a `module.exports` test tail the way `content/utils.js` and `background.js` can (its top-level IIFE touches `window`/`document` unconditionally from its very first line - `require()`-ing it under Node would need a full DOM stub, a bigger lift than the narrow `chrome`/`window.location` stubs this project has stuck to per [Decision 13](#decision-13-automated-testing-strategy)). Moved all three into `content/utils.js` instead - not because they're shared across multiple content scripts (they aren't; only `content.js` calls them), but because that file already has the safe export tail, and the real dividing line was always "does this touch the DOM," not "which file does it happen to live in." `describeEvent()` was renamed to `describeWorkerEvent()` in the move, since a generic name became a real global shared across every content script once it left its private closure, not just a name scoped to one file's own concerns. `readWorkerTabCount()` itself stays in `content.js` (it does touch the DOM, reading `panel.querySelector(...).value`), now just calling the extracted `parseWorkerTabCountInput()` for the pure part.

**A mistake caught by `node --check`, not a test - worth recording as its own small incident, matching this project's practice of not hiding the process behind the result:** while writing the header comment explaining why these functions moved, the comment literally contained the two-character sequence `*/` (as part of "the narrow `chrome.*`/`window.location` stubs") - which is the block-comment close token. It happened twice, in two different comments, each one prematurely closing the surrounding `/** ... */` block and leaving the rest of the intended comment sitting as bare, syntactically invalid text below it. `node --check` caught both immediately, before either reached the browser or even a test run - a reminder that even documentation-only edits need the same verification pass as logic changes, since a broken comment block is still a syntax error.

**Net result of this pass:** two real behavioral fixes (the tab-shrink bug, the Stop-race tab), one testability fix (9 new tests: `formatDateRangeLabel`, `parseWorkerTabCountInput`, `describeWorkerEvent`), bringing the suite from 44 to 53 tests, and this write-up closing the gap where the Stop-race fix had already shipped in a previous turn but never made it into `DESIGN.md`.

## Decision 20: The First Real-Scale Bug — CSV Export Hanging Forever on an 8000-Room Scan

**Problem, found live at the scale this whole project was built for:** an 8000-room scan finished, and "Scan & Export List" got stuck on "Exporting CSV..." forever - no error, no timeout, nothing. This is a different symptom from [Decision 16](#decision-16-every-contentjs--backgroundjs-message-needs-error-handling-not-just-some)'s stuck-CSV bug (stale content script after an extension reload), which *does* show an error via the `.catch()` added there. A true, silent, indefinite hang with zero error surfaced anywhere is a different failure class entirely - it means neither the message's `.then()` nor its `.catch()` ever fired.

**Root cause: `encodeURIComponent()` throws on a lone (unpaired) UTF-16 surrogate, and the `DS_EXPORT_SCAN_LIST` handler's `try/catch` didn't cover the code that could throw it.** `chrome.runtime.sendMessage()` only *rejects* when the message channel itself closes (e.g. the receiving context is gone) - not merely because the handler on the other end threw an uncaught exception internally while still holding the channel open. The handler's `try` block wrapped only the `chrome.downloads.download()` call; building `rows`, the CSV string, and the `data:` URL all happened *before* that `try`, unguarded. At a 25-room test scale, the odds of any single room name containing a malformed lone surrogate are low enough to never come up. At 8000 real room names pulled from a live account, they're high enough to actually hit - and once one did, the whole handler threw, `sendResponse()` was never called, and the content script's `sendMessage()` promise just sat there forever, since the channel technically never closed either.

**Fixed two ways, not one - error-visibility isn't a substitute for the actual fix, and vice versa:**
1. `safeEncodeURIComponent(str)` tries the real `encodeURIComponent()` first (byte-identical output for every normal string, including valid surrogate pairs like an emoji in a room name); only on a genuine `URIError` does it fall back to replacing *just* the unpaired surrogates (U+FFFD) via `/[\uD800-\uDBFF](?![\uDC00-\uDFFF])|(?<![\uD800-\uDBFF])[\uDC00-\uDFFF]/g` and retrying - a valid pair elsewhere in the same string survives untouched, since the regex's lookahead/lookbehind specifically distinguish "high surrogate not followed by its low partner" and "low surrogate not preceded by its high partner" from a real pair. Used in place of `encodeURIComponent()` everywhere a CSV becomes a `data:` URL: `createReport()`, `createEventLogReport()`, and the `DS_EXPORT_SCAN_LIST` handler - all three built their `dataUrl` the identical way, so all three had the identical vulnerability, confirmed live for one and fixed for all.
2. The `DS_EXPORT_SCAN_LIST` handler's `try` now wraps the entire body, not just the download call - *any* future throw in that handler, for any reason, now reaches `sendResponse({ok: false, ...})` instead of leaving the caller hanging indefinitely. Belt-and-suspenders deliberately: fixing only the specific `encodeURIComponent` cause and leaving the narrow `try` in place would have left the same *class* of bug (a hang with zero error, for whatever the next unforeseen throw turns out to be) waiting for the next 8000-room-scale surprise.

**A related, previously-silent failure mode found while fixing this - `createReport()`/`createEventLogReport()` had the identical vulnerability, but failing there was worse: completely invisible.** Both are called from `runQueue()`'s completion path as `await createReport().catch(() => "")` - a bare catch that discards the error entirely. At real scale, the same lone-surrogate throw there wouldn't hang anything (the run still completes, `STATE.running` still resets), but the download report or activity log for an entire 8000+ room run would simply never get written, with no trace anywhere that it happened. Fixed alongside `safeEncodeURIComponent()`: both `.catch()` calls now log via `console.error` and a new `report_failed` worker event (with a `stage` of `"download_report"` or `"activity_log"`), so a failure here shows up in the Activity Log and its exported CSV instead of vanishing.

**Tested:** `safeEncodeURIComponent()`'s happy path (byte-identical to `encodeURIComponent()`), that it preserves a valid surrogate pair untouched, that it doesn't throw where the real function would (the actual regression), and that a string with *both* a valid pair and a lone surrogate keeps the pair intact while only replacing the lone one. `describeWorkerEvent()`'s new `report_failed` case, for both `stage` values. Not tested: the widened `try/catch` boundary itself or the `runQueue()` wiring, consistent with this project's scope (chrome.\* orchestration - see [Decision 13](#decision-13-automated-testing-strategy)).

## Decision 21: Stop/Pause/Resume for Scanning, Not Just the Download Run

**Problem, raised directly after the same 8000-room test that surfaced Decision 20's bug:** scanning had zero user control once started - no Stop, no Pause, nothing. The download-run phase already has all three (Decision 6, Decision 3); the scan phase (`autoScrollAndCollectRooms()`, called from either the Start button or "Scan & Export List") never got the same treatment, because every scan tested before this was small enough (~25 rooms, well under a minute) that the gap never mattered. At 8000 rooms - `totalScrolls` capped at 400, ~1.5-2s per scroll - a scan can run for several minutes with the user unable to do anything but wait it out or close the tab.

**Decision: extend the same Start/Stop and Pause/Resume buttons to control scanning too, rather than adding separate scan-only controls** - one set of buttons, whose meaning depends on what's currently happening (idle → start a scan; scanning → stop/pause *that* scan; running → stop/pause the download run), driven by a new client-side-only `scanControl` object (`{ stopped, paused }`) that's `null` whenever nothing is scanning.

**Deliberately NOT crash-persistent, and said so rather than left ambiguous:** the download run's Stop/Pause/Resume survives a service-worker restart because `background.js` persists its state to `chrome.storage.local` (Decision 6). Scanning happens entirely inside `content.js`/`content/scan.js` - a single content-script execution, with no service worker involved at all until the scan finishes and hands its results to `background.js` via `DS_START_QUEUE`. Building true crash-safe scan resumption would mean adding a whole new persistence layer for partial scan progress - a bigger, separate feature, not a natural extension of this fix. What Stop/Pause *do* give: control within one page session, and a Stop still returns whatever rooms were already collected (same `getRoomCardsAndLinks().filter(...)` call runs whether the loop finished naturally or was interrupted) - a stopped scan's partial results are still usable for Export or Start, not thrown away.

**Implemented.** `content/scan.js` gained `waitIfScanPausedOrStopped(scanControl, updateStatus)`, deliberately mirroring `background.js`'s `waitIfPausedOrStopped()` shape (same spin-wait-while-paused, return-false-if-stopped pattern) - the same problem at the scan layer gets the same solution shape, not a reinvented one. `autoScrollAndCollectRooms()` takes `scanControl` as a new optional third parameter (default `null`, so any caller that doesn't pass one - none currently, but the signature stays backward-compatible - behaves exactly as before) and checks it once per loop iteration, before the next scroll. `content.js`'s `updateButtonStates(s)` reads `scanControl` directly as a closure variable rather than requiring every call site to thread a `scanning` field through `s` - the existing `DS_BULK_STATUS` broadcast listener and initial `DS_GET_STATUS` fetch needed no changes at all, since background.js has no concept of scanning and was never going to send one.

**Scope note on "Scan & Export List" sharing the same buttons as Start:** both call the identical `autoScrollAndCollectRooms()`, so both create a `scanControl` and are controlled by the same Stop/Pause - there's no scan-specific behavior that would justify separate controls per entry point. What's *not* addressed here, left as a pre-existing and unchanged behavior rather than silently scope-creeped into this fix: "Scan & Export List" can still be clicked while a download run (`isRunning`) is active, starting a scan concurrently with an active run - the Start/Stop button already correctly refuses to do this (its `if (isRunning)` branch takes priority), but the separate Export button has no equivalent guard. Not reported as a live problem; not fixed here.

## Decision 22: Making CSV-Upload Resume Actually Reliable

**Problem, raised directly mid-run: "I've seen CSVs where the room downloaded but the status was Success/Attempted"** - during an in-progress 8000-room run (~2500 done, going well), asked whether Stop-then-reupload would correctly resume. Tracing the code confirmed the mechanism itself was sound (Decision 6, [Decision 12](#decision-12-closing-out-build-step-1-under-time-pressure--csv-export-manifest-wiring)'s CSV-resume path), but surfaced two real gaps that would make it *unreliable* rather than broken outright - both flagged as open risks earlier in this project ([Decision 19](#decision-19-pre-real-run-review-pass)'s 10k-readiness assessment mentioned the first one as untested) and now confirmed live.

**Gap 1 - the report-timing race: `createReport()` ran the instant every worker ran out of rooms to claim, not once every started download had actually finished.** `processRoom()` only waits for a download to *start* (`waitForDownloadStart()`, watching for `chrome.downloads.onDeterminingFilename`) before moving on to claim the next room - the file itself keeps downloading in the background, tracked independently by the `chrome.downloads.onChanged` listener, which is what actually flips a result's status from `"Success/Attempted"` to `"Downloaded"` once Chrome reports completion. If the run ended (naturally or via Stop) while a download was still in flight, `createReport()` could run before that `onChanged` "complete" event arrived - the room's ZIP would finish fine moments later, but the report already froze its status at `"Success/Attempted"`. Since `parseUploadedCsv()` only treats a literal `"Downloaded"` status as already-done, re-uploading that report would re-download a room that had actually already succeeded - not data loss, but wasted work and a report that undersold what had really finished.

**Fixed with `waitForInFlightDownloadsToSettle(timeoutMs = 20000)`**, called in `runQueue()`'s completion path right before `createReport()`/`createEventLogReport()` (the same shared point that already covers both natural completion and Stop, per the existing `clearPersistedJob()` comment there). Polls `STATE.downloads` for entries with neither `completedAt` nor `error` set yet; returns immediately if none exist (the common case - most downloads finish well before the last room is even claimed), otherwise waits up to `timeoutMs`. Bounded deliberately, not an unlimited wait - a single genuinely stalled download (a real possibility, not just a race) must not hang run completion forever; whatever hasn't settled by the deadline is still reported as-is, exactly as before this fix existed, not worse. Logs a `waiting_for_downloads_to_settle` event (with a count) only when there's actually something to wait for, so the Activity Log doesn't fill with noise for the normal case.

**Gap 2, raised in the same conversation, same underlying goal - empty rooms were marked `"Failed"`, so every CSV-upload resume re-visited and re-confirmed every empty room from scratch.** `content.js`'s `processCurrentRoom()` correctly detects an empty room via `[data-qa="group-name"]`'s document count (Decision 4's correction) and returns immediately - but the result fed into `background.js` as `{ok: false, reason: "Room is empty..."}`, which `processRoom()` folded into the same `"Failed"` status as a genuine failure (button not found, page didn't load, tab error). `parseUploadedCsv()` only skips re-processing for `"Downloaded"` rows, so every empty room got re-navigated to and re-checked on every resume - wasted time that scales with how many empty rooms an account has, which can be a lot at real scale.

**Fixed by giving "confirmed empty" its own outcome, not folding it into "failed."** `processCurrentRoom()` now returns `{ok: true, empty: true, reason: "Room is empty (0 documents)"}` - `ok: true` because nothing actually went wrong, `empty: true` as the distinct signal. `background.js`'s `processRoom()` branches on `response?.empty` to set `result.status = "Complete (Empty)"` instead of the generic ok/not-ok branch, **and** skips the `waitForDownloadStart()` call for empty rooms specifically (`response?.ok && !response?.empty`) - simply flipping `ok` to `true` without that second change would have made every empty room burn up to 15 extra seconds waiting for a download that can structurally never start, worse than the original bug. `parseUploadedCsv()`'s already-done check became `status === "Downloaded" || status === "Complete (Empty)"`. The panel's results breakdown gained its own `Empty N` bucket so these rooms are counted distinctly instead of silently falling through every existing bucket uncounted.

**Testability found and fixed along the way, not a separate initiative - `parseUploadedCsv()` was pure (no DOM access) but sitting untested inside `content.js`'s closure**, the exact same class of gap [Decision 19](#decision-19-pre-real-run-review-pass) closed for three other functions. Moved to `content/utils.js` alongside them, given real coverage - directly exercising the changed behavior (a `"Complete (Empty)"` row routing to `priorResults` alongside `"Downloaded"`) rather than trusting a read-through of the code alone.

**Tested:** `waitForInFlightDownloadsToSettle()` - immediate return with nothing in flight (and no log noise), returning promptly once the one in-flight download settles rather than waiting out the full timeout, and giving up at the timeout when nothing ever settles. `describeWorkerEvent()`'s `waiting_for_downloads_to_settle` case. `parseUploadedCsv()` - empty/malformed input, a `"Complete (Empty)"` row correctly routing to `priorResults` (the actual regression under test), `"Downloaded"` still working as before, `"Failed"`/`"Success/Attempted"`/`"Waiting"` still queued for reprocessing, and a plain Scan List CSV (no `Status` column) treating everything as needing work. Not tested: the `processRoom()`/`processCurrentRoom()` wiring itself, consistent with this project's scope (chrome.tabs orchestration - see [Decision 13](#decision-13-automated-testing-strategy)) - the logic there is a straightforward two-branch `if`, low-risk relative to what's already covered by the DOM-driving code this project has always left to live testing.

## Decision 23: The Second Real-Scale Bug — Trailing Periods Silently Breaking Folder Routing

**Problem, found live: "some files did not get saved to the Docusign Rooms folder."** Initially investigated as a possible size limit (ruled out quickly - `chrome.downloads.download()` has no meaningful size cap for a normal HTTP-served file; the only size-sensitive `data:` URLs in this codebase are the CSV exports, an unrelated code path) or a residual `findCurrentRoomForDownload()` timing race. Neither guess was needed once real evidence arrived: the user's own DevTools console showed repeated `Unchecked runtime.lastError: Invalid filename` entries, and separately confirmed exactly 7 rooms (out of thousands) had landed in the flat Downloads root instead of their own folder.

**Root cause: `cleanName()` never stripped a trailing period or space, and Chrome's downloads API rejects a suggested filename whose path segment ends in either - a real, enforced rule inherited from Windows, applied by Chrome cross-platform regardless of the user's actual OS.** `background.js`'s `onDeterminingFilename` listener calls `suggest({filename, conflictAction: "uniquify"})` with no callback to check for an error - when Chrome rejects the suggestion (as it silently does for a trailing `.` or space), the only trace is exactly the `Unchecked runtime.lastError` the console showed, and the download falls through to Chrome's own default location instead of the intended `Docusign Rooms/<Room Name>/` folder. Business names ending in an abbreviation - "LLC.", "Inc.", "Jr.", "St." - are common enough in a real account that this reliably produces a small, nonzero fraction of misrouted files at real scale (7 out of thousands here), while a small hand-picked test set of ~25 rooms had simply never happened to include one.

**A red herring worth recording, not silently dropped:** the same console dump included several `[DSBD] Unmatched download - no current room found` warnings - but for `data:text/csv;...` URLs, not room ZIPs. These are the CSV report exports themselves (the Download Report and Activity Log) triggering the same `onDeterminingFilename` listener that watches every download, correctly finding no matching room (because they aren't room downloads), and correctly doing nothing - this is expected, already-understood behavior from much earlier in the project, not a second bug. Confirmed by inspecting the `url` field directly rather than assuming: it began with `data:text/csv;charset=utf-8,` and contained recognizable CSV header text.

**Fixed at the source - `cleanName()` in `content/utils.js`, the single choke point every folder/file name in this codebase passes through** (room folder names, the disambiguated `(roomId)` suffix already appends safely since it always ends in `)`, and the date-range label used in every exported CSV's filename via `labeledFilename()`), rather than patching each call site separately. Strips a trailing run of periods/spaces (`/[.\s]+$/`, handling any interleaving of the two in one pass) - applied *after* the existing 120-character length cap as well as before, since truncation itself could expose a new trailing period/space that wasn't in the original string. Falls back to `"Unnamed Room"` if stripping leaves nothing, same as the existing empty-input fallback. Also added a guard for Windows' reserved device names (`CON`, `PRN`, `AUX`, `NUL`, `COM1`-`9`, `LPT1`-`9`) as an exact match only - cheap to add once the trailing-period case proved Chrome really does enforce Windows path rules regardless of platform, even though an exact collision with a real room name is far less likely than the trailing-period case that was actually confirmed.

**Tested:** the exact confirmed scenario (`"Smith Properties LLC."` → `"Smith Properties LLC"`), a bare trailing space, interleaved trailing periods and spaces, a non-trailing period left untouched (`"St. James Properties"` correctly unaffected), the length-cap interaction (a trailing period newly exposed by truncation is still stripped), the all-punctuation fallback to `"Unnamed Room"`, and the reserved-device-name guard (exact match only - `"CONstruction Room"` is correctly left alone). All of `cleanName()`'s previously-existing tests (character stripping, whitespace collapsing, length capping, empty-input fallback) still pass unchanged, confirming this was a strict addition, not a behavior change to the cases already covered.

**Extended afterward with the actual confirmed data, not just the invented example above** - once the user pulled the exact five room names out of the real Download Report CSV (`"NJ-77, Bridgeton, NJ, USA."`, `"124 Rosman Rd."`, `"Greenberg - 156 Pine St."`, `"1 Landmark Sq."`, `"693 Squaw Brook Rd."`, found by cross-referencing the CSV's *Room Name* column - the *Downloaded Filename* column was a red herring the first time through, since Chrome overwrites it with its own fallback name once it rejects the suggested one, which looks nothing like the original room name), two more tests were added: one confirming `cleanName()` itself fixes all five real names, and a second, more end-to-end one confirming `computeFolderNames()` - the function `background.js` actually calls to build the real download path, not `cleanName()` directly - also produces a safe result for all five. The second test exists because `cleanName()` being correct in isolation doesn't by itself prove nothing downstream (e.g. the `(roomId)` disambiguation suffix logic) could reintroduce the same problem a different way.

## Decision 24: Moving the Panel Out of the Page — A Detached Window

**Problem, raised as a design question, not a bug: "since [the panel is] tied to the web page anytime the page is refreshed or it moves from tab to tab it becomes super hard to press any of the buttons or accurately see progress."** True from the very first panel (README's phase 3, predating this document's Decision log), but never actionable until a real multi-thousand-room run made it matter: `content.js`'s `injectPanel()` built the entire control panel as DOM injected into the live Docusign page. A refresh, a navigation, or simply clicking to a different tab either destroyed the panel outright or made it invisible/unreachable, even though the run itself (owned by `background.js`'s service worker, not the page) kept going unaffected. Explicitly authorized to build immediately ("do it now"), with the standing instruction from earlier the same conversation to keep testing and verifying existing functionality throughout.

**Decision: extract the panel into `panel.html`/`panel.js`, a standalone Chrome extension window opened via the toolbar icon (`chrome.action.onClicked`), independent of any Docusign tab - rather than, say, trying to keep the panel alive across navigations with more injection tricks.** A separate extension page is a stable execution context Chrome doesn't tear down on a page refresh or tab switch, which is the actual property being chased here; patching the in-page approach further would still leave it fundamentally tied to a DOM that legitimately needs to reload sometimes.

**The core design problem this created: the download run and the room scan need fundamentally different capabilities, and no single execution context has both.** The download run (`runQueue()`, `processRoom()`) already lived entirely in `background.js` and needed no DOM access - `chrome.tabs.sendMessage()` to worker tabs was always how it drove them, so moving its *controls* into a standalone window changed nothing about how the run itself worked. Scanning (`autoScrollAndCollectRooms()`) is different: it's DOM automation, scrolling and reading the room list directly off a live Docusign page - it must run inside a content script, in an actual Docusign tab, and a standalone panel window structurally cannot do that work itself no matter how it's built.

**The asymmetry that shaped the whole relay protocol: `chrome.tabs.sendMessage(tabId, msg)` reaches a specific tab's content script but not other extension pages; `chrome.runtime.sendMessage(msg)` (no tabId) reaches the background worker and other extension pages (panel.html included) but not content scripts.** Neither call reaches both destinations - there is no single message that goes straight from the panel to a content script. `background.js` sits in the middle of every hop by necessity, not by choice: `panel.js` sends `DS_RUN_SCAN` (a `chrome.runtime` broadcast, since the panel doesn't know or care which tab is running Docusign); `background.js` finds the right Docusign tab and relays `DS_BEGIN_SCAN` to it via `chrome.tabs.sendMessage`; `content.js` runs the actual scan and reports back via `DS_SCAN_PROGRESS`/`DS_SCAN_COMPLETE` (`chrome.runtime` broadcasts, since content scripts can't address a specific extension page either); `background.js` relays the final result to the panel as `DS_SCAN_RESULT`. Four hops for one logical operation, but each hop is doing something the other three structurally can't.

**Decoupling the request from its (much later) response, the same pattern already used for the download run itself:** a scan across thousands of rooms can take minutes - `DS_RUN_SCAN`'s handler in `background.js` and `DS_BEGIN_SCAN`'s listener in `content.js` both acknowledge synchronously (`sendResponse({ok:true})` before any `await`) that the scan *started*, then deliver the real result later via a separate `DS_SCAN_COMPLETE`/`DS_SCAN_RESULT` message. Holding one message channel open for a multi-minute operation was never how this codebase did long-running work (the download run doesn't either), so the scan relay didn't invent a new pattern here, just reapplied the existing one across an extra hop.

**Preserving the pre-existing UX deliberately, not by accident:** `DS_SCAN_COMPLETE` for mode `"start"` does *not* auto-launch the download queue - `background.js` relays the room list back to the panel via `DS_SCAN_RESULT`, and `panel.js` shows the exact same `confirm()` dialog the old in-page code always showed before calling `beginRun()`. A user who has run this tool before sees the same confirmation step they always have; only the wiring behind it changed.

**Two gaps found during my own review, not reported live, and fixed before considering this done - per the standing "verify nothing broke, test what you can" instruction:**

1. **A synchronous-guard race in `DS_RUN_SCAN`**, the same class of bug this project already fixed once for `STATE.running`/`DS_START_QUEUE` (Decision 3): the `STATE.scanning` guard was being checked before an `await chrome.tabs.query(...)` but only set to `true` after it returned, leaving a window where two overlapping `DS_RUN_SCAN` calls could both pass the guard and start two scans at once. Fixed by moving `STATE.scanning = true` to immediately after the guard check, before any `await` - closing the window the same way the earlier fix did.
2. **No recovery if the Docusign tab running an active scan gets closed mid-scan.** Scanning has no service-worker involvement until it finishes (unlike the download run, which persists to `chrome.storage.local` and can resume after a restart - Decision 6) - if the tab closes, the content script's whole execution context disappears with it, and no `DS_SCAN_COMPLETE` can ever arrive to reset `STATE.scanning`, which would otherwise stay stuck `true` forever, permanently blocking every future scan behind an "already in progress" guard even though nothing is actually running. Fixed with a `chrome.tabs.onRemoved` listener that checks `STATE.scanTabId === tabId`, resets `STATE.scanning`/`scanTabId`/`scanMode`/`scanDateRangeLabel`, logs a new `scan_tab_closed` worker event, and broadcasts `DS_SCAN_FAILED` so `panel.js` can reset its own `scanInProgress` flag and show the reason instead of being left stuck showing "scanning" with no way to start another one.

**`broadcastStatus()` simplified as a direct consequence, not a separate cleanup:** it used to `chrome.tabs.query()` for every Docusign tab and `chrome.tabs.sendMessage()` to each one, because the in-page panel living inside those tabs was the only thing listening. With the panel now a standalone page reachable by `chrome.runtime.sendMessage()` like any other extension surface, that whole tab-enumeration loop collapsed into a single broadcast call - simpler code that fell out of the architecture change rather than being pursued on its own.

**A design tradeoff accepted, not hidden: a reopened panel can't recover whether a scan-in-progress was paused.** `background.js` has no persisted concept of "paused" for a scan the way it does for a run (scanning was never meant to survive a service-worker restart at all - see the gap above); `DS_GET_STATUS`'s response includes `scanning: STATE.scanning` so a reopened panel correctly shows a scan as in-progress, but always assumes not-paused even if it actually was. Narrow and documented rather than silently wrong: `content.js` is what's actually enforcing pause/stop either way, so clicking Pause/Resume from the reopened panel still works correctly against the real state regardless of what the panel initially displayed.

**Not tested by the automated suite, consistent with this project's established scope (Decision 13): the message-relay wiring itself** - `DS_RUN_SCAN`/`DS_BEGIN_SCAN`/`DS_SCAN_COMPLETE`/`DS_SCAN_STOP`/`DS_SCAN_PAUSE`/`DS_SCAN_RESUME`/`DS_SCAN_FAILED` handlers, the `chrome.action.onClicked` and `chrome.tabs.onRemoved` listeners, and `panel.js` end-to-end - all chrome.\*-orchestration code this project has always left to live testing rather than mocking Chrome's message-passing behavior. **What *is* tested:** `describeWorkerEvent()`'s new `scan_tab_closed` case (a pure formatting function, the same category of thing every other worker-event type already has coverage for). Every change to `background.js`'s exported pure functions and the test infrastructure itself (`tests/helpers/chrome-stub.js` needed `chrome.action`, `chrome.windows`, and `chrome.tabs.onRemoved` stub entries added as each new top-level API call was introduced, or the whole suite fails at `require()` time) was verified against the full existing suite after every edit - 78/78 passing throughout, confirming this refactor didn't regress any previously-covered behavior.

## Decision 25: Organizing Downloads by Year

**Problem, requested directly: "lets make it so that downloaded rooms are organized by year. in the folder docusign rooms it has one more subfolder at the top that being the year."** Every room's ZIP had always landed at `Docusign Rooms/<Room Name>/<Room Name>.zip` - flat, no matter how many thousands of rooms a run covered. At real scale (the 8000+-room production account this tool was built for) that's a single folder with thousands of children, hard to browse or hand off to someone who only wants a specific year's records.

**First real decision: what does "year" mean?** Two candidates, genuinely different in both meaning and implementation cost: the room's own created date (the same "created" date already scanned and used for the From/To filter - Decision 4) versus the date the export happened to run. Asked directly rather than assumed, since the answer changes both the code and whether reorganizing already-downloaded files is even possible - the user's own account has years of history, so "download date" would dump everything from one run into a single year folder regardless of when the underlying rooms were actually created, while "created date" preserves the same year-shaped structure Docusign's own account history has. Chosen: **room's created date.**

**Second question, raised in the same breath: "is it possible to reorganize the one currently in there or no?"** Only if a created-date-to-room-name mapping still exists somewhere, since the folders already on disk carry no created-date metadata of their own - a file's mtime only reflects when it was *downloaded*, not when the room was *created*, and those are commonly different by years for an account with real backlog. Confirmed the user still had a Scan List CSV (`Room ID`, `Room Name`, `Created Date`) covering the exact same room set as an existing Download Report (verified by a full Room ID intersection, not just a matching row count, before trusting it) - making the reorganization possible as a one-time, separate operation outside the extension itself (a real filesystem move on the user's live Downloads folder, not something a Chrome extension's `chrome.downloads` API can do to files it didn't just create).

**A real, pre-existing bug found while building this, not a hypothetical:** the Scan List CSV's "Created Date" column (added in [Decision 18](#decision-18-date-range-labels-in-exported-csv-filenames)) used `String(room.createdDate || "").slice(0, 10)` - this happens to look like it might produce an ISO date, but `Date.prototype.toString()` isn't ISO format at all. Confirmed directly on the development machine (America/New_York): `new Date("2021-01-04")` stringifies to `"Sun Jan 03 2021 19:00:00 GMT-0500..."`, and slicing the first 10 characters gives `"Sun Jan 03"` - no year, and a calendar day off from the real date, silently, in every CSV this column had ever produced outside UTC. This had shipped unnoticed because nothing depended on that column being machine-readable before now; the moment year-folder routing needed to parse it back out, it had to be fixed first.

**Decision: a small shared pair of helpers in `content/utils.js`, not a fix scattered across every call site.** `coerceCreatedDate(createdDate)` normalizes either a real `Date` (fresh off a live scan) or a plain string (round-tripped through an uploaded CSV) into a `Date` or `null`, treating an unparseable string as `null` rather than letting `Invalid Date` propagate. `formatCreatedDateForCsv(createdDate)` uses `toISOString().slice(0, 10)` - the same pattern `formatDateRangeLabel()` already used correctly - instead of `toString()`. `roomCreatedYear(createdDate)` extracts the year for folder routing, using `getUTCFullYear()` rather than `getFullYear()` specifically: `content/scan.js` parses a room's date-only page text ("Jan 4, 2024") straight into `new Date(...)`, which the language spec treats as UTC midnight - reading the year back out with local time instead could roll a room created right at a year boundary into the wrong year, depending on which side of UTC the browser's timezone happens to fall. A room with no usable createdDate at all falls into `"Unknown Year"` rather than throwing or silently disappearing - the only way to reach that today is a room re-queued from an older-format Download Report CSV that predates the new column below, or one a user hand-edited to drop it.

**`computeFolderNames()` reworked to key on `(year, name)` instead of just `name`.** Collision disambiguation (Decision 2's `(roomId)` suffix for two same-named rooms) existed because two rooms sharing a cleaned name would otherwise target the exact same folder - true when every room lived in one flat `Docusign Rooms/` directory, no longer true once rooms are split across year folders: two identically-named rooms created in different years land in different folders on their own and don't need disambiguating. Rescoping the collision key to `${year}/${name}` means fewer rooms get the `(roomId)` suffix than would under the old per-name-only scheme, without weakening the actual guarantee - a same-name collision *within* one year folder still gets it. `folderNames.set(room.roomId, {year, roomFolderName})` - the map's value changed from a plain string to a small object, since both pieces are needed at every call site (`processRoom()`'s reported `downloadedFilename`, and the `onDeterminingFilename` listener's real `suggest()` call) and computing them separately in two places would risk the two disagreeing.

**A field that had to survive three separate hops, or year-folder routing would silently degrade to "Unknown Year" for real rooms:** `room.createdDate` needs to reach `computeFolderNames()` at `DS_START_QUEUE` time, but `DS_START_QUEUE`'s `normalized` room-mapping step previously stripped every incoming room down to just `{roomId, roomName, documentsUrl}`, dropping anything else - including a field this feature didn't need before now. Fixed by explicitly carrying `createdDate` through that mapping, and through the parallel `priorRoomsForQueue` mapping built from `priorResults` (already-`Downloaded`/`Complete (Empty)` rooms carried over on a CSV-upload resume) - not because those specific rooms ever get re-downloaded (they don't, so their own folder routing is moot), but because `createReport()`'s new "Created Date" column (below) reads directly off `STATE.queue`, and a `priorRoomsForQueue` entry missing `createdDate` would report a blank year for a room that actually had a perfectly good date sitting in the uploaded CSV the whole time.

**The Download Report CSV never had a "Created Date" column at all - added one, for the same resume-integrity reason as everywhere else in this project.** Without it, a room re-queued from a Download Report (as opposed to a Scan List) on a CSV-upload resume would have no way to know its own year, defeating the point of the feature for exactly the resume path Decision 22 built CSV-upload resume to support in the first place. `parseUploadedCsv()` (`content/utils.js`) reads the column via the same header-lookup-by-name pattern every other column already uses (`header.indexOf("Created Date")`, `-1` if absent) - an older-format CSV without it still parses correctly, `createdDate` just comes back `null` and the room falls into `"Unknown Year"`, not broken.

**Tested:** `formatCreatedDateForCsv()`/`roomCreatedYear()` - a `Date` object and a CSV-round-tripped string both handled the same way, `null`/`undefined`/empty/unparseable input all falling back safely instead of throwing, and the exact regression that motivated the fix (`formatCreatedDateForCsv()` must match `toISOString()`, and must *not* match the old `toString()`-based output, checked against the same real value - `"2021-01-04"` - that exposed the bug). `roomCreatedYear()`'s UTC-vs-local distinction, checked at both ends of a calendar year. `computeFolderNames()` - the existing collision/fallback/trailing-period-name tests updated for the new `{year, roomFolderName}` return shape, plus new coverage for: two same-named rooms in different years correctly *not* colliding, two same-named rooms in the same year still colliding, and a room with no createdDate landing in `"Unknown Year"` without being dropped from the map. `parseUploadedCsv()` - a "Created Date" column parsed onto both still-queued rooms and already-done `priorResults` rows, and an older-format CSV without that column still working (falls back to `null`, not a crash). Not tested, consistent with this project's established scope (Decision 13): the actual `chrome.downloads.download()`/`suggest()` call sites that consume this data, and the one-time filesystem reorganization script for already-downloaded files, both chrome/filesystem-orchestration code this project has always left to careful live execution rather than mocking.

## Decision 26: Verifying "Success/Attempted" Rooms Instead of Blindly Re-Downloading

**Problem, surfaced by directly investigating a real "why does it say 1085 still Waiting when the previous CSV said it was complete" question.** Tracing the actual Activity Log for that run (timestamps cross-referenced against report mtimes, not guessed) showed exactly what happened: a resumed run got stopped only ~5.5 minutes after it started, having processed 225 of the 1310 rooms it re-queued. Not a bug - `claimNextRoom()`'s single-pointer walk through `STATE.pending` has no way to "lose" a room or hit a false limit, confirmed by re-reading the code rather than assuming. But the underlying complaint was still valid and led somewhere real: **"the first run should have redone the non-completed rooms - I shouldn't have had to re-upload the CSV to finish it off again. It's deceiving when it says done when it may not actually be."**

**First design instinct - auto-retry `Failed` and `Success/Attempted` rooms automatically at the end of a run - rejected before building it, for a concrete reason.** `Failed` genuinely means nothing was ever downloaded (page didn't load, button not found) - safe to retry. `Success/Attempted` means something different: a download was *triggered*, just never *confirmed* complete before the report was written. A meaningful fraction of those rooms already have a real file sitting on disk - the report-timing race Decision 22 mostly closed, plus the class of gap this decision exists to close (a completion event that's never recorded at all, not just not-yet-settled). Blindly re-clicking Select All → Download for a room that already succeeded doesn't fix anything - it risks a genuine duplicate ZIP. **Corrected mid-conversation, by the user, to exactly this point: "don't check for the failed ones, only for the success/attempted."**

**Decision: verify against ground truth before re-processing anything, using `chrome.downloads.search()` - an API this extension already has permission for (the existing `"downloads"` permission covers `search()`, not just `download()`), no manifest change needed.** Chrome maintains its own persistent download history independent of anything this extension tracks in memory, including an `exists` flag it keeps current by actually checking the filesystem. `findVerifiedExistingDownloads(rooms)` wraps the actual `chrome.downloads.search({state: "complete", exists: true, filenameRegex: "Docusign Rooms"})` call - one bulk search, not one per room, since a real account's download history can be large and a native call per room would add up needlessly across a big resume. Never throws: a failed or unavailable search just means nothing gets verified, degrading to the pre-existing "queue everything the CSV says isn't done" behavior rather than blocking the run. `matchVerifiedDownloads(existingItems, rooms)` is the pure matching core (testable without mocking Chrome) - see the correction directly below for how it actually decides whether an existing download belongs to a given room.

**Corrected during a later, explicitly-requested stress-test pass ("really stress test this... apply coding fundamentals"), before this had shipped to production use - the first version matched by name, and that was a real, confirmed bug, not a hypothetical.** The original `matchVerifiedDownloads()` matched each room against the existing items' *leaf filename only* - `<name>.zip` or `<name> (<roomId>).zip` - reasoning that this would work identically whether a file landed under the old flat structure or the new year-folder one (Decision 25), since it wouldn't need to know which naming scheme was active when the file was created. Verified directly, not just reasoned about, that this was unsafe: `matchVerifiedDownloads([{filename: ".../2021/Main St Listing/Main St Listing.zip", url: ".../transaction/100/..."}], [{roomId: "200", roomName: "Main St Listing"}])` returned a match for room 200 - a completely different, never-downloaded room that merely happens to share room 100's cleaned display name (a plain address, or a generic name like "Rental," reused across different years or clients, is a real, observed pattern in this project's actual data, not an invented edge case). A first attempted fix - excluding a leaf name from matching if more than one *existing* item shared it - was also verified and also failed: the false match above involves exactly one existing file, not two competing ones, so nothing about counting duplicate leaf names touches it. The name-based approach was unsafe by construction, not fixable with a patch, because a filename carries no information about which specific room it belongs to when two different rooms share a name.

**Rebuilt to match on `roomId` extracted from the download's own `url`/`finalUrl`/`referrer`** - the exact same `/rooms/<id>/` or `/transaction/<id>/` pattern `findCurrentRoomForDownload()` already trusts to identify a live download (Decision 2's second correction), not the filename at all. Since a room's numeric ID is unique by construction, this makes the false-positive class of bug above structurally impossible rather than merely less likely - there's no name to collide on anymore. Verified against six cases directly, including the exact scenario that broke the first version (still correctly excluded) and the legitimate same-file-appears-twice-in-history case the interim "duplicate leaf name" fix was trying to preserve (still correctly included, now for the right reason - matching by ID never needed to treat that case specially in the first place).

**Wired into two places, not one, after the user asked directly: "can this step be done without having to re-upload the completed CSV, but more of a before the final CSV is generated?"**

1. **`runQueue()`'s completion path, right after `waitForInFlightDownloadsToSettle()` and before `createReport()`.** `verifySuccessAttemptedResults()` checks this run's own `Success/Attempted` results and, for anything verified, mutates the result in place (`status: "Downloaded"`, corrected `reason`/`downloadedFilename`/`downloadId`) before the report is ever written - so the *first* report already reflects reality instead of requiring a second CSV-upload pass just to reconcile. This closes a gap `waitForInFlightDownloadsToSettle()` structurally can't: that function only tracks downloads still present in this session's in-memory `STATE.downloads`; it has no way to catch a download that genuinely finished but whose completion event was never recorded at all (the tab closed or crashed right after triggering it, or the service worker restarted before `chrome.downloads.onChanged` fired). **A real bug caught before it shipped, by re-reading the surrounding code rather than trusting the first draft:** `verifySuccessAttemptedResults()` initially called `persistJob()` when it made changes, matching the pattern most other STATE-mutating functions in this file follow - but this call site runs *after* `clearPersistedJob()` has already run for the completed job. Persisting again there would have resurrected a "job" entry in `chrome.storage.local` the instant after it was cleared, which a later service-worker restart could have mistaken for an interrupted run still needing resume. Removed - nothing needs to survive a crash between this point and `createReport()` reading `STATE.results` right after, since both happen synchronously within the same already-completed `runQueue()` call.
2. **`DS_START_QUEUE`'s CSV-upload path**, scoped to whichever queued rooms have `status === "Success/Attempted"` (the room's *prior* status from the uploaded CSV, threaded through `parseUploadedCsv()` and the `normalized` mapping specifically so this distinction survives the trip - previously `parseUploadedCsv()` didn't carry status at all for non-final rows, since nothing needed it before now). This is what catches everything check #1 couldn't: older reports that predate this fix entirely (like the historical CSVs from this exact investigation), or the rare case where the gap wasn't caught the first time either.

**The "Done" message fixed at the source of the actual complaint, not just the mechanism.** Even with verification in place, a run can still legitimately end with real outstanding rooms (Stop was clicked, or a genuinely-`Failed` room stays failed). `panel.js`'s flat `"Done."` text on `s.finishedAt` was itself part of what made the original report "deceiving" - it said the same thing whether every room succeeded or 1,371 didn't. Now counts anything not `Downloaded`/`Complete (Empty)` and says so plainly: `"Done, but N rooms still need attention..."` versus `"Done - every room downloaded or confirmed empty."` - an honest answer either way, not confidence the run itself can't actually back up.

**Tested:** `matchVerifiedDownloads()` - matching via the `transaction/<id>` URL pattern and the `rooms/<id>` one, no match when nothing corresponds, the confirmed regression itself (two different rooms sharing a display name must not cross-match), `referrer`/`finalUrl` checked as fallbacks the same way `findCurrentRoomForDownload()` does, and missing-URL/empty/null inputs all handled without throwing. `describeWorkerEvent()`'s new `verified_existing_downloads` case, for both the `pre_report` and `csv_resume` stage variants. `parseUploadedCsv()`'s new `status` field surviving onto queued (not-yet-final) rooms - the regression this whole distinction depends on. Not tested, consistent with this project's established scope (Decision 13): the actual `chrome.downloads.search()` call inside `findVerifiedExistingDownloads()`, and `verifySuccessAttemptedResults()`'s/`DS_START_QUEUE`'s own wiring - chrome-orchestration this project has always left to live testing.

## Decision 27: An "Unassigned" Catch-All for What Can't Be Placed

**Problem, raised as a direct follow-up: "add an unassigned subfolder to the docusign folder where if something cant be identified or put in a subfolder it goes to the unassigned."** Two genuinely different situations already existed where a room's proper location couldn't be determined, and neither had a good answer: (1) a room is identified, but its created date isn't available - Decision 25 already handled this with an `"Unknown Year"` fallback folder, just under a different name than what was being asked for here; (2) a download can't be matched to *any* room at all - `onDeterminingFilename`'s listener already detected this case (`findCurrentRoomForDownload()` returning `null`) but had never done anything about it beyond a `console.warn` - it simply didn't call `suggest()`, so Chrome fell back to its own default location, **outside** the `Docusign Rooms` folder entirely. Asked directly whether both should be covered, not just the first (already-partially-solved) one - confirmed: both.

**Case 1 - a straight rename, `"Unknown Year"` → `"Unassigned"`, no logic change.** `roomCreatedYear()`'s fallback string (`content/utils.js`) is the only place this needed to change; every call site that builds a folder path from it (`computeFolderNames()`, `processRoom()`'s reported filename, the `onDeterminingFilename` listener's real `suggest()` call) already treats the year as an opaque string, so nothing downstream needed touching. The two failure modes now deliberately share one top-level bucket name rather than two different ones - both mean the same thing to whoever finds the folder afterward ("this one needs a human to sort out"), so there was no reason to keep them visually distinct.

**Case 2 was the real risk, and needed a much narrower trigger than "anything unmatched" to build safely.** `chrome.downloads.onDeterminingFilename` fires for **every download in the entire browser**, not just this extension's - a user could be downloading an invoice from Gmail in a completely unrelated tab while a Docusign Rooms tab happens to be open, and that download would hit this same listener. The existing "unmatched" case already included this extension's own CSV report exports (`data:text/csv;...` URLs, confirmed harmless back in [Decision 23](#decision-23-the-second-real-scale-bug--trailing-periods-silently-breaking-folder-routing)'s investigation) mixed in with any genuinely-unrelated download. Blindly routing *every* unmatched download into `Docusign Rooms/Unassigned/` would have redirected some stranger's Gmail attachment into this extension's folder structure - a materially worse bug than the one being fixed.

**Decision: only treat a download as "ours, but unidentifiable" if its URL actually looks like a Docusign document download in the first place** - reusing the same `/rooms/<id>/` or `/transaction/<id>/` pattern `findCurrentRoomForDownload()` already checks (Decision 2's second correction), tested independently against `referrer`/`url`/`finalUrl` rather than refactoring that existing, already-corrected-twice function itself - the risk of introducing a fourth regression into code with that history outweighed the small duplication of one regex literal. A download whose URL doesn't match this pattern at all (an unrelated download, or this extension's own CSV exports) is left completely untouched, exactly as before this change - no `suggest()` call, Chrome's own default behavior applies. Only a download that *does* match - a real Docusign document URL that still couldn't be tied to a tracked room (its `STATE.currentRooms` entry already cleared by the time this event fired, a timing edge case, not the common case) - gets routed to `Docusign Rooms/Unassigned/<fallback name>`, using `downloadItem.filename` (Chrome's own pre-suggestion guess, already populated by the time `onDeterminingFilename` fires) run through the existing `cleanName()` sanitizer, or a generated `Unassigned Download <id>` name if even that's unavailable. Logged via a new `unassigned_download` worker event - diagnostic visibility into a real gap being closed, not just the fix landing silently.

**Not given its own per-item subfolder, unlike a normal room.** A normal room's ZIP gets `Docusign Rooms/<year>/<Room Name>/<Room Name>.zip` - its own folder, because the room name is known and meaningful. An unidentifiable download has no such name to build a folder from, so it lands as a flat file directly under `Docusign Rooms/Unassigned/` instead of inventing an artificial one-off subfolder for it.

**Tested, to the extent this project's established scope covers chrome-orchestration code (Decision 13): none of the new `onDeterminingFilename` logic directly** - it's chrome.downloads listener wiring, the same category of code this project has always left to live testing. What *is* covered: `roomCreatedYear()`'s renamed fallback (already-existing tests updated, not new coverage), and `describeWorkerEvent()`'s new `unassigned_download` case.

## Decision 28: "Waiting" Rooms Deserve the Same Verification "Success/Attempted" Rooms Get

**Problem, raised after a direct correction: "waiting status means no way it got downloaded so i think its fine to reprocess."** Plausible-sounding, but wrong, and disprovable directly against this account's own real data rather than argued about abstractly: `"Waiting"` only means *the run that produced a given report* never claimed that room - it says nothing about whether an *earlier, separate* run already downloaded it successfully. Verified by cross-referencing the account's real Download Report against the actual files on disk (using `computeFolderNames()` itself, not a reimplementation, so there was no room for the check to drift from what the extension would actually compute): of 977 non-`Downloaded` rooms found already sitting at their correct location, 839 were at `Waiting` and only 138 at `Success/Attempted` - the room-status confusion this decision fixes was, by a wide margin, the more common case, not the rarer one.

**Decision: widen `DS_START_QUEUE`'s verify-before-reprocess check from `Success/Attempted` only to `Success/Attempted` or `Waiting`.** `findVerifiedExistingDownloads()`/`matchVerifiedDownloads()` (Decision 26) needed no changes at all - they already operate on whatever room list they're handed, agnostic of status. Only the caller's filter changed: `normalized.filter(r => r.status === "Success/Attempted")` became `normalized.filter(r => r.status === "Success/Attempted" || r.status === "Waiting")`. `"Failed"` deliberately stays excluded, per the same reasoning as Decision 26 - a genuinely failed attempt is a different signal than "never touched." `verifySuccessAttemptedResults()` (the *other* verify call site, checking a run's own in-memory results right before its report is written) was deliberately **not** widened - `"Waiting"` is a `createReport()`-time display default for a queue entry with no result at all, never a status `processRoom()` actually writes into `STATE.results`, so there is nothing there for it to match against; documented directly in that function's own comment so a future reader doesn't wonder why the two checks aren't symmetric.

**Verified empirically, not just reasoned about, mirroring the same discipline Decision 26 used to catch its own first draft's bug.** Ran the actual `DS_START_QUEUE` handler (via the chrome-stub harness) against three rooms - one `Waiting`, one `Success/Attempted`, one `Failed` - each with a matching entry in a simulated download history. Confirmed: the `Waiting` and `Success/Attempted` rooms both correctly resolved to `Downloaded` and dropped out of the real-reprocessing queue; the `Failed` room correctly stayed queued for genuine reprocessing despite also having a "matching" history entry, proving the exclusion actually holds rather than assuming it from reading the filter alone.

**A one-time, real-data correction followed the same session, not a hypothetical exercise.** The account's actual Download Report was cross-checked against real files using this project's own `computeFolderNames()`, uncovering (and initially mis-flagging, then correctly resolving) several categories of false "missing" result before landing on the true picture: single-document rooms save as `.pdf`, not `.zip` (a blind spot in the one-off verification script, not in the extension itself); some already-moved files still carry a now-unnecessary `(roomId)` collision suffix left over from before Decision 25's per-year collision scoping existed (cosmetically stale, not mislocated); and five files were genuinely sitting in the wrong place - the original Decision 23 trailing-period casualties, parked in `Unassigned/` under Chrome's own fallback names before this session's year-folder and `Unassigned` features existed to route them properly. Those five were moved to their correct year folder using the exact room-ID-to-year mapping `computeFolderNames()` itself produces - not name-guessing, the same discipline Decision 26 exists to enforce. Two more candidates in `Unassigned/` were deliberately left alone after checking further: both correspond to rooms that already have a correctly-placed copy elsewhere (one confirmed via matching file size across three separate copies), so moving them would only have created more duplicates, not fixed anything.

A corrected Download Report CSV was generated from this data - reusing the extension's own `csvEscape()` and `formatCreatedDateForCsv()` rather than reimplementing them, for the same reason `computeFolderNames()` was used directly for the file-location check. A genuine ordering bug was caught before the file was ever produced: the script initially spliced a new "Created Date" column into each row *before* writing the status/reason/filename corrections, which used column indices computed from the *original*, pre-insertion header - silently writing every correction into the wrong field. Caught by inspecting the actual output, not by re-reading the script and assuming it was right; fixed by reordering the writes to happen first, against the original indices, with the column insertion done last. The corrected CSV was also given the "Created Date" column the source report predated entirely (from Decision 25) - without it, all 302 rooms still genuinely needing work would have round-tripped through `parseUploadedCsv()` with no date at all and landed in `Unassigned` on the next run instead of their correct year. Round-tripped the finished file back through the real `parseUploadedCsv()` before considering it done: 6,061 `Downloaded` + 985 `Complete (Empty)` + 302 still-genuinely-outstanding, summing exactly to the account's 7,348 rooms, with every one of the 302 carrying a real `createdDate`.

**Tested:** the widened `DS_START_QUEUE` filter, end-to-end against the real handler (not a unit test of an isolated function, consistent with this project's established chrome-orchestration scope - Decision 13) - confirmed both that `Waiting` now benefits from verification and that `Failed` still correctly doesn't. The one-off CSV-correction and file-relocation scripts are intentionally outside the automated suite entirely - one-time data-migration tooling operating on this specific account's real files, not logic this codebase ships or re-runs.

## Decision 29: "Failed" Doesn't Belong in the "Still Needs Attention" Count

**Problem, found through real use immediately after Decision 26 shipped: "it downloaded, the csv said that 185 rooms needed attention but they all were just failed rooms."** Decision 26's "Done, but N rooms still need attention" message (`panel.js`) counted anything that wasn't `Downloaded`/`Complete (Empty)` - which included `Failed` alongside the genuinely ambiguous `Success/Attempted` and `Waiting`. A run with 185 real, conclusively-failed rooms and zero ambiguous ones reported the same "still needs attention, not confirmed downloaded" framing as a run that was genuinely incomplete - misleading, since a `Failed` room's outcome isn't unconfirmed, it's already fully known.

**Decision: only `Success/Attempted` and `Waiting` count toward "still needs attention" - `Failed` is surfaced separately, not folded into the same alarm.** The distinction is exactly the one Decision 26 already drew for *which* rooms get automatically re-verified against Chrome's download history (`Success/Attempted`/`Waiting`, never `Failed`, since nothing was ever downloaded for a Failed room to verify) - this decision applies the same line to how the *summary message* talks about them. `Waiting` needed a small extra step to compute correctly: it's never an actual status value stored in a result object (`processRoom()` never writes it - it's a `createReport()`-time display default for a queue entry with no result at all), so it has to be derived the same way `renderBreakdown()` already does a few lines up in the same file - `total - results.length` - rather than filtered out of the results array directly. A `Failed` count is still shown, just in its own clause ("Done, but N room(s) still need attention..., plus M that already failed and won't change") when both exist, or its own sentence ("Done - every room downloaded or confirmed empty, except M that failed") when Failed is the only thing left - never implying the failed ones are part of the "not confirmed" count, since they aren't.

**Tested:** the exact reported scenario (185 `Failed`, nothing else outstanding) now produces "Done - ... except 185 rooms that failed," not "still needs attention" - verified directly by extracting the computation and running it against constructed result sets, not just re-reading the code, the same discipline this whole session has held to. Also checked: an all-clean run, a genuinely-ambiguous-only run (still correctly flagged), a mixed unconfirmed-and-failed run (correctly keeps the two counts and their grammar separate - "1 room still needs attention... plus 2 rooms that already failed"), and an empty/zero-room edge case (falls through safely, no divide-by-zero or negative count).

## Decision 30: Exported CSVs Were Landing as "download.csv," Not Their Real Name

**Problem, raised directly: "the csv that gets downloaded... right now when they download it just says download.csv. They need clearer titles."** `createReport()`, `createEventLogReport()`, and `handleExportScanList()` all build a `data:text/csv;...` URL and call `chrome.downloads.download({url: dataUrl, filename: "Docusign Rooms/_Download Reports/Docusign Rooms Download Report (...).csv", ...})`, trusting the `filename` option alone. On disk, these were landing as generic `download.csv`, `download (1).csv`, `download (2).csv` - Chrome's own fallback pattern for a download with no usable name, sitting flat in the Downloads root, not even inside `Docusign Rooms/`. Confirmed by direct evidence gathered earlier the same session (Decision 28's file-verification pass): the account's actual report files were named exactly this way. In hindsight, this was the same underlying gap the `[DSBD] Unmatched download` console warnings for `data:` URLs had been surfacing all along (first seen back in Decision 23) - correctly identified at the time as *not a room-matching bug*, but the downstream consequence (the wrong filename actually landing) was never chased down until raised directly here.

**Decision: don't trust `chrome.downloads.download()`'s `filename` option for a `data:` URL - suggest() it explicitly via `onDeterminingFilename`, the exact mechanism already proven reliable for every room ZIP.** A new module-level `pendingReportFilenames` Map, keyed by the exact `data:` URL (unique per export, since the CSV content - including a per-row timestamp - differs every time), lets the listener recognize "this is one of our own report exports" and call `suggest()` with the real intended filename directly - checked first, before any room-matching logic runs at all, since these are never room downloads. At most 3 entries pending at once (one run's Scan List, Download Report, and Activity Log), consumed and deleted by the listener itself the moment they're used, so there's no meaningful growth risk even without a cap.

**Verified end-to-end, not assumed fixed from reading the code alone:** drove the real `DS_SCAN_COMPLETE`/export message path through the actual exported listener, had the stubbed `chrome.downloads.download()` fire the captured `onDeterminingFilename` listener with the same URL exactly the way Chrome would, and confirmed `suggest()` received the real labeled filename (`"Docusign Rooms/_Scan Lists/Scan List (2024-01-01 to 2024-06-01) ....csv"`), not a generic fallback.

**Tested:** consistent with this project's established scope (Decision 13), the `onDeterminingFilename`/`pendingReportFilenames` wiring itself is chrome-orchestration, verified the same way the DS_START_QUEUE/DS_RUN_SCAN stuck-state fixes were (Decision 26) - a direct, reproducible script exercising the real registered listener - rather than added to the permanent `node:test` suite, which would need a meaningfully larger chrome-stub investment for this one scenario.

## Decision 31: Native `confirm()` Silently Suppressed in an Unfocused Popup Window

**Problem, surfaced by a real Chrome console warning during live use:** *"A `window.confirm()` dialog generated by this page was suppressed because this page is not the active tab of the front window."* `panel.js` used the native `confirm()` in three places - most critically in `beginRun()`, called the moment a scan's result arrives (`DS_SCAN_RESULT`) to ask "Found N rooms... Continue?" before actually starting a download run. Chrome silently suppresses a real `confirm()`/`alert()`/`prompt()` whenever the window that calls it isn't the currently focused one, auto-resolving it as Cancel with **no visible error** - the dialog simply never appears. `panel.html` is a standalone popup window (Decision 24), and a scan on a large account can run for several minutes - long enough that a user reasonably switches to another window while waiting, exactly the moment `DS_SCAN_RESULT` would arrive and try to confirm. The failure mode this produces is close to the worst kind: the run silently never starts, `beginRun()` sets the status to "Cancelled," and nothing about that looks like an error - it looks like the user's own doing, when they never saw a dialog at all.

**Decision: replace all three `confirm()` calls with a custom, in-page overlay dialog - not an attempt to force window focus.** A `chrome.windows.update(id, {focused: true})` call before each `confirm()` was considered and rejected: it would still leave a narrow race (focus and the dialog call aren't atomic), it's intrusive (yanking focus away from whatever the user is actually doing, on every single confirm - including the low-stakes Stop-button ones), and it doesn't address the deeper issue - a dialog whose entire reliability depends on which window happens to be frontmost at one exact instant is fragile by construction. A DOM element rendered inside the page, by contrast, is just page content - it has no OS-level "is this window focused" precondition to fail. `showConfirmDialog(message)` returns a `Promise<boolean>`, backed by a hidden overlay (`panel.html`) shown/hidden via the `hidden` attribute, wired to Enter/Escape the same way the native dialog behaves so switching away from `confirm()` doesn't feel like a downgrade to anyone used to it.

**A regression the native dialog structurally couldn't have had, caught before shipping rather than after:** a real `confirm()` is fully blocking at the OS level - two calls in the same page can never overlap, by construction. A Promise-based replacement has no such guarantee: two `showConfirmDialog()` calls close together (a scan result arriving right as someone clicks Stop, say) would both attach fresh click listeners to the *same* overlay element at once, letting a single click resolve two different pending Promises incorrectly. Fixed by chaining every call onto a module-level `confirmDialogChain` Promise, serializing them - a second dialog only actually appears once whatever's currently pending has been answered, never layered underneath it.

**`beginRun()` and the Start/Stop button's click handler both had to become `async`** to `await` the new Promise-returning `showConfirmDialog()` instead of reading a synchronous boolean - a small mechanical change at both of `beginRun()`'s call sites (the CSV-upload handler, already `async`; the `DS_SCAN_RESULT` listener, which correctly calls it without `await`, fire-and-forget, matching how it already treated the synchronous version).

**Tested:** consistent with this project's established scope (Decision 13) for DOM-orchestration code, verified by direct code review and syntax/consistency checks rather than a `node:test` entry - `panel.js` has never been unit-testable without a DOM implementation this project has deliberately not taken on as a dependency (Decision 13's own reasoning), and this fix doesn't change that boundary.

## Decision 33: Two Ways a Scan Could Silently Hang Forever, Found by Auditing the Scan Relay End-to-End

**Problem, raised directly: "double check the scanning feature to see it doesn't suddenly stop or anything."** Audited the full scan path (`content/scan.js`'s `autoScrollAndCollectRooms()` → `content.js`'s `DS_BEGIN_SCAN` handler → `background.js`'s `DS_RUN_SCAN`/`DS_SCAN_COMPLETE` relay → `panel.js`'s `DS_SCAN_RESULT`/`DS_SCAN_FAILED` listeners) rather than trusting that Decision 26/28's `STATE.running`/`STATE.scanning` try/catch work already covered this. It didn't, fully - two real gaps found, both the same failure shape as those earlier ones: an event with nothing to reset `STATE.scanning`, leaving it stuck `true` forever and the panel frozen on its last progress line with no error and no way to recover short of reloading the extension.

**Gap one: content.js's `DS_BEGIN_SCAN` handler had no try/catch around the actual scan call.** If `autoScrollAndCollectRooms()` threw for any reason - an unexpected Docusign page-structure change, a DOM call failing in a way the code didn't anticipate - execution would never reach the `chrome.runtime.sendMessage({ type: "DS_SCAN_COMPLETE", rooms })` line at all. No completion message ever arrives at `background.js`, so `STATE.scanning` (set `true` at the top of `DS_RUN_SCAN`) never gets reset, and every future scan attempt is rejected with "A scan is already in progress" even though nothing is running. Fixed by wrapping the call in try/catch/finally: on success, `DS_SCAN_COMPLETE` is sent exactly as before; on a thrown error, `DS_SCAN_COMPLETE` is still sent, but with an `error` field instead of a room list, so a genuine scan failure is never confused with a scan that legitimately found 0 rooms. `background.js`'s `DS_SCAN_COMPLETE` handler now checks `message.error` first and routes it through the existing `DS_SCAN_FAILED` broadcast - the same path `panel.js` already understood from the tab-closed case below, reused rather than adding a second failure UX for the same underlying situation.

**Gap two: only the scan tab being *closed* was handled - not the scan tab *navigating or reloading*.** `chrome.tabs.onRemoved` (added in an earlier fix, alongside `STATE.scanTabId`) correctly resets `STATE.scanning` if the user closes the Docusign tab mid-scan. But a full-page navigation or reload of that same tab is just as fatal to the in-flight scan - it destroys and replaces the content script's entire JS execution context, silently taking `scanControl` and the running `autoScrollAndCollectRooms()` call with it - and the tab itself never closes, so `onRemoved` never fires. There was genuinely no existing signal for this case. Fixed by adding a `chrome.tabs.onUpdated` listener that resets the same `STATE` fields and sends the same kind of `DS_SCAN_FAILED` broadcast whenever the scan tab's `changeInfo.status` becomes `"loading"` - which only happens on a real navigation/reload (a new document being requested), not on Docusign's own client-side route changes within the page (those use the History API and never trigger a `tabs.onUpdated` `"loading"` status), so it can't misfire on ordinary in-app clicking around.

**A smaller, non-hanging issue found in the same audit: `content/scan.js`'s scroll loop had two silent exit paths.** The loop can end three ways - the date range is exhausted (`outOfRangeStreak >= 5`), no new rooms load after several tries (`noNewRoomAttempts >= 7`), or a hard 400-scroll safety cap is hit. Only the first of these ever called `updateStatus()` to say why; the other two just let the loop's `while` condition go false with no message at all, which is indistinguishable from a scan that "stopped updating for no reason" from the panel's perspective - not a hang, but the same lack-of-explanation the two real gaps above produce. Both now report explicitly why the loop ended, including how many rooms were found by that point, so a scan that hits the 400-scroll cap on an unusually large date range is visibly flagged as capped rather than silently returning a partial list that looks complete.

**Tested with real regression tests, not just code review** - unlike Decision 31's DOM-orchestration fix, this logic lives in `background.js`'s message dispatch and `chrome.tabs.onUpdated`/`onRemoved` listeners, which are pure `STATE` transitions and therefore within `node:test`'s established scope (Decision 13) - the gap was that nothing tested this layer of `background.js` at all before now, only the pure functions message handlers call into. `tests/helpers/chrome-stub.js`'s `onMessage`/`onRemoved`/`onUpdated` stubs were upgraded from silent no-ops to actually capturing the registered listener (`this._listener = fn`), and `runtime.sendMessage` now records every broadcast in `sentMessages`, so a test can invoke `background.js`'s real listener directly and assert on exactly what it did and broadcast - not a mock of the fix's *intent*, the actual code path. Four new tests in `tests/background.test.js` cover: a thrown scan correctly resets state and broadcasts `DS_SCAN_FAILED` (not `DS_SCAN_RESULT`); a normal scan still broadcasts `DS_SCAN_RESULT` as before; a mid-scan tab reload correctly resets state and broadcasts `DS_SCAN_FAILED`; and an unrelated tab's navigation, or a non-navigation status change on the scan tab itself, correctly does nothing. `content/scan.js`'s DOM-orchestration changes remain outside `node:test`'s scope per Decision 13, verified by direct code review instead, consistent with Decision 31. Full suite: 101/101 passing (97 prior + 4 new).

## Decision 34: The Same Silent-Hang Class of Bug, Found in the Actual Download-Running Path This Time - a Full Codebase Audit Before Sending This to Other Market Centers

**Problem, raised directly: "double check all features in this codebase... so that I can send to other market centers. would you say this is ready?"** Decision 33 audited and fixed the scan relay; this pass read every remaining file end-to-end (`background.js` in full - all ~1800 lines, `content.js`, `content/room.js`, `content/utils.js`, `panel.js`) specifically looking for the same failure shape: an async chain with no bound and no safety net, where an uncaught throw or a promise that simply never settles leaves some `STATE` flag stuck and the panel frozen with no explanation. Found two real gaps - both in the actual download-running path (`runQueue()`/`runWorker()`/`processRoom()`), not the pre-run scan step this time, which makes them the higher-stakes finding: this is the feature an hours-long, unattended run at real scale actually depends on.

**Gap one: `runQueue()` itself had no top-level try/catch, and both its call sites invoke it fire-and-forget.** `DS_START_QUEUE`'s handler and the startup-resume IIFE both call `runQueue();` with no `await` and no `.catch()` - correct, since a real run can take hours and nothing should hold a message channel open that long, but it also means `runQueue()`'s own body is the *only* place that could ever catch an unexpected throw inside it. Nothing did. The most plausible trigger: `ensureWorkerTabs()`'s `chrome.tabs.create()` call, the one spot in that whole chain not already defensively wrapped (`chrome.tabs.get()` calls elsewhere are all `.catch()`'d). An uncaught throw there would skip every line of cleanup after it - resetting `STATE.running`, clearing the persisted job, writing the final report - leaving the panel showing "running" forever with no report and no error, exactly the class of bug already found and fixed for `STATE.scanning` (Decision 26/28/33) but never closed at this level for the run itself. Fixed by wrapping `runQueue()`'s entire body in try/catch: on error, `STATE.running` resets, the failure is logged, a best-effort partial report is still written (`.catch()`'d individually, matching the normal-completion path's own pattern so a second failure here can't make things worse), and a new `DS_RUN_FAILED` broadcast tells the panel plainly that this was a crash, not a normal finish - without it, `running: false` plus a `finishedAt` from the partial report would read to the panel exactly like a real completion (see its "Done, but N rooms still need attention" logic), silently hiding what actually happened. Deliberately does *not* clear the persisted job on this path, unlike a genuine completion - whatever was checkpointed up through the last completed room stays in `chrome.storage.local`, so the run can still be picked back up automatically (the next service-worker restart) or manually (re-uploading the report this path still writes).

**Gap two, the more serious of the two: `processRoom()`'s `chrome.tabs.sendMessage()` call to the worker tab had no timeout - the one wait in this entire pipeline that didn't.** Every other wait already has an explicit bound: `waitForTabLoaded` (60s), `waitForDownloadStart` (15s), `waitForInFlightDownloadsToSettle` (20s). This one didn't, and unlike those, it structurally can't be fixed with more error handling - reasoned through Chrome's own extension-messaging semantics: `chrome.tabs.sendMessage()`'s returned promise stays pending forever unless `sendResponse()` is actually called on the content-script side, or the tab's port disconnects (closes/navigates). A rejected promise is already `.catch()`'d here; a promise that simply never settles is a different failure mode entirely, one no `try`/`catch` can help with, because `await` on it never returns control at all. If `content.js`'s `DS_PROCESS_ROOM` handler ever threw before reaching `sendResponse()` - it had no try/catch either, so any unexpected DOM issue on any single room would do exactly this - that one room would hang its worker's `runWorker()` loop forever, which keeps `runQueue()`'s `Promise.all()` from ever resolving, which hangs the *entire run*, not just that one room, even with every other worker tab long finished. Fixed on both sides: a new `withTimeout()` helper races the `chrome.tabs.sendMessage()` call against a 90-second bound (comfortably above `processCurrentRoom()`'s own worst-case legitimate duration of ~67s), falling back to a normal `{ok: false, reason: "Room processing timed out..."}` result exactly like any other Failed room; and `content.js`'s `DS_PROCESS_ROOM` handler is now wrapped in try/catch too, so a real error reports itself immediately with a specific reason instead of silently eating 90 seconds before the timeout has to catch it. Belt-and-suspenders deliberately, not redundant - the content.js fix handles the common case fast and informatively, the background.js timeout is the only thing that can bound a case where content.js never gets to respond at all (a truly unresponsive page, not just a thrown error).

**Everything else in this audit checked out already safe**, worth recording so this doesn't need re-auditing from scratch next time: `handleExportScanList()`/`createReport()`/`createEventLogReport()` are all either self-contained try/catch or `.catch()`'d at their call site; `persistJob()`/`clearPersistedJob()` are internally guarded to never throw, by design (see their own comment); `DS_PAUSE`/`DS_RESUME`/`DS_STOP` touch no risky `chrome.*` calls; `runWorker()`'s own tab-replacement logic already degrades gracefully (one fewer worker, logged, not stuck) if `chrome.tabs.create()` fails there; `content/room.js` and `content/utils.js` are both already thoroughly guarded with optional chaining and internal try/catch (`roomUrlToDocumentsUrl()`); `panel.js` has no `STATE`-stuck risk at all, being a UI page rather than a persistent service worker - `DS_GET_STATUS` refreshes it fresh on every open. `chrome.downloads.onDeterminingFilename`/`onChanged` remain the one place without explicit try/catch, deliberately left as-is - a throw there is bounded to "one file lands with a generic Chrome-assigned name instead of its organized folder," not a stuck run, a different order of severity than everything else in this Decision.

**Tested with 5 new regression tests**, continuing Decision 33's approach of driving the real message-dispatch layer rather than trusting code review alone: three isolated tests for `withTimeout()` itself (resolves with the real value well inside the deadline; resolves with the timeout value for a promise that never settles at all, using a genuinely-never-resolving `new Promise(() => {})`; doesn't fire early for a promise that settles just before its deadline) - fast and deterministic, so they carry the real proof for gap two's fix without needing a 90-real-second integration test. Two end-to-end tests drive a full `DS_START_QUEUE` message through the real listener with `chrome.tabs.create` mocked to throw: one confirms the crash path resets `STATE.running`, broadcasts `DS_RUN_FAILED` with the real error message, logs a `run_queue_failed` event, and leaves the persisted job alone (`tests/helpers/chrome-stub.js`'s `storage.local.remove` now records every call in `removeCalls`, specifically so this last claim could be verified rather than assumed); the other drives the same message with no injected failure and confirms a normal run still completes with no `DS_RUN_FAILED` broadcast, guarding against the new code firing it unconditionally. These two needed real elapsed time (`runWorker()`'s loop uses genuine `setTimeout`-based `sleep()` between claims, not just microtasks), so they poll for the expected end state with a bounded timeout rather than guessing a fixed delay. `content.js`'s `DS_PROCESS_ROOM` try/catch remains outside `node:test`'s scope per Decision 13/31, verified by code review. Full suite: 106/106 passing (101 prior + 5 new).

## Decision 35: A Scroll-Count Cap Can Never Be High Enough - Removed Entirely in Favor of the Signal That Actually Means "Done"

**Problem, reported directly with real numbers: "the code randomly just stopped a scan after 10k rooms... i did 1/1/2023 to 12/31/2024 but once it reached like 6/10/2023 it just stopped."** Checked against the account's own real Scan List CSVs rather than trusting the report at face value or guessing from the code alone (this project's established discipline - see Decision 28, among others). Found two independent scan runs, both requesting the same `2023-01-01` to `2024-12-31` range, that stopped at the *exact same room*: 2913 found, room ID `8659058`, created `2023-06-10` - identical room count, identical last room, across two separate live runs. That reproducibility is the tell: `content/scan.js`'s `autoScrollAndCollectRooms()` loop has two natural stopping conditions (the date range exhausted, or several scrolls in a row load nothing new) plus one artificial one, `totalScrolls < 400` - a hard cap added purely as a circuit breaker against a genuinely infinite loop, documented at the time as exactly that, never meant to be a real ceiling. A timing-dependent condition (no-new-rooms) landing on the identical room across two independent real-network sessions would be a remarkable coincidence; a fixed scroll-count cap landing on the identical room every time is exactly what a deterministic cap does. `2913 / 400 ≈ 7.3` rooms loaded per scroll on this account - and 400 scrolls turned out nowhere near enough for the 10,000+-room scale this project is explicitly built for (the README's own opening line).

**First fix attempt: raised the cap 25x, from 400 to 10,000 scrolls.** Immediately questioned, correctly: any fixed scroll count is still an arbitrary ceiling, just a bigger one - there is no number that's provably enough for every account, and an account large enough (or a slower page-render rate than the ~7.3 rooms/scroll observed here) would hit even a 10,000-scroll cap the same way this one hit 400. Raising the number treats the symptom, not the actual design flaw: the loop was using an unrelated proxy (how many times it happened to scroll) to guess at something it already has a real, direct signal for.

**Real fix: removed `totalScrolls` from the loop's stopping condition entirely.** The loop already has the correct signal for "the requested range is genuinely exhausted": `outOfRangeStreak`, which only stops once several consecutive rooms are confirmed *past* `dateRange.end` - valid specifically because the list is sorted oldest-first (enforced by `ensureOldestSort()`/`getSortLabel()` before the loop even starts). That's a real completion signal, not a proxy; a scroll count never was. The loop now runs until either `outOfRangeStreak` confirms the range is actually done, or `noNewRoomAttempts` confirms the account has genuinely stopped producing new rows (its threshold also widened, 7 → 15, since the two real runs that surfaced this bug stopped at different points - 2913 rooms at one run, 1663 at another - suggesting real timing variance in how fast this account's virtualized list renders newly-loaded rows, worth a wider margin). Stop remains available as a manual override for the case a scroll cap was really guarding against - something going genuinely wrong, not a large-but-legitimate scan. `totalScrolls` is still tracked and now surfaced in the periodic "Loading rooms..." status message instead of being discarded - without any cap, a scan still working through scroll #4000 would otherwise look identical, from the status line alone, to one that's silently frozen. The now-dead "hit the scroll-count cap" status branch (added in Decision 33 for the old cap) was removed along with the cap itself.

**Tested by direct calculation against the real observed rate** (~7.3 rooms/scroll × 400 scrolls confirmed against the account's own two CSVs - the exact data that proved a hard cap could never be set correctly, which is the whole point of removing it rather than re-tuning it), consistent with this file's established scope for DOM-orchestration logic (Decision 13) - a `node:test` entry can't drive a real virtualized Docusign page's scroll/render timing, and doesn't need to: this fix is a change to which conditions can end a loop, verified against the exact data that showed the old ones were wrong.

## Decision 36: The OS Lock Screen Can Still Interrupt a Scan Even When "Disabled" - Asked the Browser to Prevent It Directly, and Fixed a Silent-Empty-Result Gap It Exposed

**Problem, reported directly and in two parts: "again it randomly stopped why is that. my lockscreen turned on even though i have it deactivated im so confused."** Checked the real evidence again rather than assuming the same root cause as Decision 35 (already fixed, and confirmed working - this same session's next scan reached 7,464 rooms, up from 2,913, proving the scroll-cap removal held). The next scan attempt after that produced a header-only CSV - 0 rooms - which traced to `content/scan.js`'s own sort-order guard: `getSortLabel() !== "Created (Oldest)"` returned `[]` rather than throwing, so a scan that couldn't even start (most plausibly because the Docusign tab had been logged out, reloaded, or reset to a different view - all plausible after the tab sat backgrounded through whatever the lock-screen interruption actually was) was reported identically to a genuine "this date range really has zero rooms" result. **Fixed by throwing instead of returning `[]`** - this routes through the exact `DS_SCAN_COMPLETE`/`error` → `DS_SCAN_FAILED` path Decision 33 already built, turning a silently unhelpful empty CSV into a real, visible failure with an actionable reason ("make sure you're still logged into Docusign and on the Rooms list page").

**The deeper problem - the lock screen itself - can't be fixed by re-checking the user's own OS settings a second time; those settings had already, apparently, failed to hold.** Windows/macOS sleep and lock-screen preferences can be reset by a software update, overridden by a battery-vs-power-adapter profile switch on unplug, or overridden by a managed-device policy - none of which this extension has any visibility into, and none of which "tell the user to check their settings again" actually solves if it already happened once. Chrome extensions have a direct API for exactly this: `chrome.power.requestKeepAwake("display")`, which tells the OS not to sleep, dim, or lock the display for as long as it's held, independent of the user's own System Settings/Control Panel configuration entirely. Added the `"power"` permission to `manifest.json` and a new `updateKeepAwake()` helper, called after every one of the twelve places `STATE.running`/`STATE.scanning` change (both `DS_START_QUEUE`'s and `DS_RUN_SCAN`'s success and failure paths, `runQueue()`'s normal-completion and crash paths, the `chrome.tabs.onRemoved`/`onUpdated` scan-tab-lost listeners, and the startup-resume IIFE) - checking `STATE.running || STATE.scanning` and requesting or releasing the lock accordingly, rather than tracking a third flag of its own that could drift out of sync with what's actually active. `requestKeepAwake()`/`releaseKeepAwake()` are idempotent per Chrome's own documented behavior, so calling either redundantly at any of the twelve sites is harmless. This is a mitigation, not a guarantee - `chrome.power` is well-documented to not override every possible interruption (a laptop lid closing is a common exception on most OSes) - so the existing manual OS-configuration guidance in `HOW_TO_USE.md` stays in place as a first line of defense; this is a second, code-level one that doesn't depend on the user's settings holding.

**Tested with 3 new regression tests**, continuing the established pattern of driving the real message-dispatch layer: `tests/helpers/chrome-stub.js`'s `power` stub now records every `requestKeepAwake`/`releaseKeepAwake` call, in order, in a `calls` array (not just separate counters, so a test can assert ordering relative to `STATE` actually changing, not just that both were eventually called). Three tests confirm: a normal download run requests the lock only once it's genuinely active and releases it on completion; a *crashed* run (the same `chrome.tabs.create`-throws scenario from Decision 34) still releases the lock, not just a clean completion; and `DS_RUN_SCAN` requests and releases the lock correctly even on its earliest failure path (no Docusign tab open at all). The `content/scan.js` throw-instead-of-return fix remains outside `node:test`'s scope per Decision 13 (DOM-orchestration logic), verified by code review. Full suite: 109/109 passing (106 prior + 3 new).

## Decision 37: A Real Tab Crash ("Aw, Snap!") on a Large Account - DOM Trimming, Checkpointed Progress, a Stall Watchdog, and a Resource Leak Found Along the Way

**Problem, reported directly: "the web page crashes... it reaches max to i believe 10/2024 i believe it cannot handle so many rooms being loaded at once."** Confirmed via the user's own follow-up ("Aw, Snap is what it said") - a genuine Chrome renderer crash, not a hang or a bug in this extension's own logic. Root cause: Docusign's Rooms list is a plain infinite-scroll page - every room ever loaded stays in the DOM forever, nothing is recycled as the scan scrolls past it. Since a scan always starts from the account's very first room (oldest-first, no way to jump ahead) and this account has many thousands of rooms before the requested range even begins, the DOM had accumulated far more rows than the tab's renderer could hold in memory by the time it reached October 2024 - not tied to that date specifically, just to how much had piled up by that point in the scroll.

**Fixed with `trimOldRoomRows()`**, called every loop iteration: removes all but the most recently-rendered ~500 room rows from the DOM, keeping memory bounded regardless of how large the account is. Safe only because results are no longer read back out of the DOM at the end the way `autoScrollAndCollectRooms()` used to work - `seenUrls` (a `Set`) and `collected` (a plain array) now accumulate everything as the scan progresses, independent of whatever the DOM currently holds, so a trimmed-away row is never mistaken for "new" nor silently lost. The `500`-row buffer is a generous-but-arbitrary choice, not one confirmed safe against Docusign's own scroll-trigger logic directly (this project has no way to inspect that trigger's implementation) - reasoned to be safe because removing rows well above the viewport shouldn't disturb a bottom-anchored infinite-scroll trigger, and because the existing `scrollTo({top: scrollHeight})` call already targets a freshly-read `scrollHeight` every time rather than an absolute prior position, so a trim-induced height change can't desync it.

**A second, related request, raised in the same breath: "is there a way to actively write a file while rooms are being scanned?"** Previously, nothing was ever saved to disk until a scan finished completely - a crash lost everything back to the start, checkpointing or not. Added `onCheckpoint`, an optional callback `autoScrollAndCollectRooms()` invokes every 1,000 newly-collected rooms (roughly every 3-4 minutes at this account's observed ~7.3 rooms/scroll) with everything collected so far, filtered to the requested range. `content.js` relays this to `background.js` via a new `DS_SCAN_CHECKPOINT` message; `background.js` writes it to a *stable* filename (`STATE.scanCheckpointFilename`, computed once at scan start, not per-checkpoint) with `conflictAction: "overwrite"`, so repeated checkpoints replace the same in-progress file rather than piling up a new one every few minutes. Reuses `handleExportScanList()`'s own CSV-building logic (`buildScanListCsvDataUrl()`, factored out for exactly this reuse) so the checkpoint and the real final export can never quietly drift apart on column shape.

**A third gap, found while directly re-checking whether the earlier "Aw, Snap!" case was actually covered end-to-end (asked for explicitly): a crashed-but-not-closed tab is invisible to every existing detection mechanism.** `chrome.tabs.onRemoved`/`onUpdated` (Decision 33) catch a tab being *closed* or *navigated* - a crash is neither; Chrome leaves the tab in place showing its own error page, with no dedicated event for "this tab's renderer died." Confirmed there's genuinely no direct signal available for this specific case. Added a `chrome.alarms`-driven watchdog (the `"alarms"` permission, `SCAN_WATCHDOG_ALARM`, checked every 1 minute - the minimum period Chrome allows): if a scan is active and no `DS_SCAN_PROGRESS`/`DS_SCAN_CHECKPOINT` message has arrived in over `SCAN_STALL_THRESHOLD_MS` (2 minutes - comfortably longer than any single legitimate step in the loop, which cycles every ~1.5-2s), it's treated as stalled and reported through the same `DS_SCAN_FAILED` path the other two cases already use, rather than leaving the panel frozen indefinitely. `chrome.alarms` specifically (not `setInterval`) because MV3 service workers are ephemeral - an alarm survives the worker being killed and restarted, where a JS timer would simply be gone.

**Asked directly whether the same crash class threatens the download-*run* side, and whether persistence/CSV generation survive it - the priority being that the CSV always gets written no matter what, so a run can always be resumed.** Traced the full path rather than assuming: `runWorker()`'s existing tab-liveness check (`chrome.tabs.get()`) can't distinguish a crashed-but-present tab from a healthy one (both return a valid Tab object), so a crash isn't caught there - but `processRoom()`'s next step, `chrome.tabs.update(tabId, {url: documentsUrl})`, navigates to a *new* URL regardless of the current page's state, which recovers a crashed tab the same way any real navigation would. If the crash happens *during* that room's own processing (the content script dies mid-flight), Decision 34's `withTimeout()` (90s bound on the `DS_PROCESS_ROOM` message) already catches it, marking that one room `Failed` with a real reason rather than hanging - and since `persistJob()` runs immediately after every room's result is recorded regardless of outcome, `chrome.storage.local` never falls meaningfully behind. The structural reason the download side doesn't share scanning's crash risk at all: each room gets a fully fresh page load (`chrome.tabs.update()` to a new URL every time), never one continuously-scrolled session accumulating unbounded DOM the way the Rooms list page does - there's no equivalent "resets the DOM" fix needed here because there's no equivalent unbounded-accumulation problem to begin with.

**Verified this reasoning with a real end-to-end test, not just logic**: simulated `chrome.tabs.sendMessage` throwing "Could not establish connection. Receiving end does not exist." (the real error Chrome gives when messaging a tab whose content script is gone) on the first room of a two-room run, confirming the crashed room is marked `Failed` with that reason, is actually checkpointed to `chrome.storage.local` (not just held in memory - `tests/helpers/chrome-stub.js`'s `storage.local.set` now records every call), the *second* room still gets processed normally afterward, and a real Download Report CSV still gets written at the end.

**A genuine bug found while chasing down why this new test's run took the full test suite from ~4s to over 90s**: `withTimeout()`'s internal `setTimeout` was never cleared once its `Promise.race()` settled via the *other* branch - on the fast/common path (a real response arrives well before the 90s bound), Node still kept that timer alive and pending for the entire 90 seconds regardless, since `Promise.race()` never cancels its losing entries on its own. Not just a test artifact: in production, this meant one dangling ~90-second timer accumulating per room processed, on every single room, not just the rare stuck one - across an 8000-room run split over several workers, potentially hundreds pending in memory at once, real pressure on a service worker whose ephemeral MV3 lifecycle already has enough of that to contend with. Fixed by capturing the timer and clearing it in a `.finally()` on the race, so it's cleaned up immediately once either side wins. Confirmed by the same test suite run dropping back from ~92s to ~4s after the fix, with all tests still passing - the empirical proof, not just the code review.

**Tested with 5 new regression tests total**: `DS_RUN_SCAN` computing a stable checkpoint filename that `DS_SCAN_CHECKPOINT` reuses across repeated saves (`conflictAction: "overwrite"`, not `"uniquify"`); `DS_SCAN_CHECKPOINT` being a safe no-op when no scan is actually in progress; the scan-stall watchdog firing correctly on a genuine stall and correctly staying silent on recent activity; and the crashed-worker-tab end-to-end test described above. `tests/helpers/chrome-stub.js` gained `alarms` (capturing the real listener plus `create`/`clear` call logs) and `downloads.downloadCalls`/`storage.local.setCalls` (recording every call, not just no-opping) - each added because a specific claim in this Decision needed to be checked against what the code actually did, not assumed. `content/scan.js`'s DOM-trimming logic itself remains outside `node:test`'s scope per Decision 13 (DOM-orchestration code, no live Docusign page to test against), verified by code review and the reasoning above. Full suite: 114/114 passing (109 prior + 5 new).

## Decision 38: A Second, Distinct Way a Scan Could Silently Report "0 Rooms" as a Success

**Problem, reported directly right after Decision 37 shipped: "um i think there was an error it just randomly stopped."** Checked the real evidence rather than assuming the same cause as before: the panel's own status line read "Exported 0 rooms to: Scan List (2023-01-01 to 2024-12-31)..." - the *success*-path message (`DS_SCAN_RESULT` mode `"export"`, `response.ok` true), not the failure message Decision 36's sort-guard throw would have produced. That ruled out a recurrence of the already-fixed bug and pointed at something new. Confirmed no checkpoint file existed for this scan at all (`find ... -iname "*in progress*"` came back empty), meaning the scan never accumulated even 1,000 rooms before ending - on an account/range already directly confirmed, earlier the same session, to hold 7,000+ real rooms. A "0 rooms" result here is never legitimate.

**Root cause: a second, structurally distinct way for `autoScrollAndCollectRooms()` to end up with an empty result and still return normally instead of throwing.** Decision 36 fixed the case where the sort dropdown itself isn't set to "Created (Oldest)" - but the loop can *also* exit via `noNewRoomAttempts >= 15` with zero rooms ever collected, if the sort is correctly set yet the room-list table simply never renders a single row for the whole ~22.5-second window (a transient page-load hiccup, an auth/session issue, or any other reason the table comes up empty despite the page otherwise looking ready). That case was never covered by the sort-order check, since the sort itself is fine - and unlike "found some rooms, then genuinely ran out" (a real, legitimate way for the loop to end this way), "found *zero* rooms this whole time" is never a genuine empty-range answer, since even an out-of-range room would still render as a row and fail the date check via `outOfRangeStreak` instead.

**Fixed by throwing in that specific sub-case** - `noNewRoomAttempts >= 15` AND `collected.length === 0` - routing through the same `DS_SCAN_FAILED` path as every other real scan failure, rather than taking the normal success path through to a misleadingly "successful" empty CSV export. Left the *other* sub-case (some rooms found, then genuinely ran out) exactly as it already correctly worked, since that one really is a legitimate, common way for a scan to finish.

**Also directly re-verified the checkpoint system end-to-end** on request, given it shipped in the same prior turn as the bug this Decision fixes - traced `content.js`'s `reportCheckpoint` → `DS_SCAN_CHECKPOINT` → `background.js`'s handler → `STATE.scanCheckpointFilename`/`conflictAction: "overwrite"` and found no bug in it; the absence of a checkpoint file for this incident is *consistent* with the checkpoint system working correctly (nothing substantial was ever collected to checkpoint), not evidence of it failing to save something that existed.

**Tested by direct code review**, consistent with this file's established scope for DOM-orchestration logic (Decision 13) - the exact failure mode (a room-list table that renders zero rows despite the sort being correct) isn't reproducible without a live Docusign page in a specific transient state, the same class of constraint Decision 36's sort-guard fix was verified under.

## Decision 39: A Research-Grounded Audit - a Real Stale-DOM-Read Bug, a Documented Storage Race, and a Reusable "High-Risk Areas" Map

**Problem, requested directly: "make sure these bugs are being caught... do an audit... research similar projects... verify with tests that represent accurate real world scenarios... keep checkpoints for heavily accessed functions and frequent bug locations."** A qualitatively different request from every fix in this session so far - not a specific reported symptom to trace, but a standing instruction to actively hunt for what hadn't been reported yet, grounded in how comparable systems (infinite-scroll scrapers, MV3 service workers, worker-pool task queues) are documented to fail, and to leave behind something a future debugging pass could actually use rather than just another chronological entry.

**Research first, findings second - and one finding discarded because the research didn't support it.** Confirmed via direct search (not recalled from memory) that all seven of `background.js`'s top-level `chrome.*.addListener()` registrations are correctly synchronous at module scope, avoiding a real, documented MV3 pitfall (listeners registered inside an async callback don't fire on the wake-up event that loaded the worker) - nothing to fix there, worth recording as checked rather than left unverified. A separate claim surfaced by the same research pass - that `chrome.runtime.sendMessage` from a content script can hang forever if the service worker is asleep - was checked further and found to describe a narrower, different scenario (a message with nowhere to be received, not the normal service-worker wake-up path this project actually depends on); not acted on, since acting on an unconfirmed claim would have been exactly the kind of hallucination this request explicitly warned against.

**Real finding one: a stale-DOM read in `content/scan.js`'s `getRoomCardsAndLinks()`.** Directly informed by the research (modern frameworks batch DOM updates, so a scraper can catch a row mid-render) and grounded in this project's own prior, independently-confirmed finding that Docusign Rooms is a React app (Decision 2's "an older jQuery modal bolted onto the React UI"). A room row could exist in the DOM - `<tr>` present, link present - before its own `name`/`date` child content had actually rendered; the previous code fell back to a placeholder name and a `null` date for that case, which is far worse than it looks: `autoScrollAndCollectRooms()` marks a room "seen" (via `seenUrls`) the *first* time it's read, so a room caught mid-render was marked seen with a `null` date and never re-read once the real date actually appeared - and a `null` date fails the final range filter, so the room silently vanished from the export entirely, permanently, with no error and no retry. Fixed by treating a row missing either its name or date element the same as a row missing its link entirely (already-existing behavior) - skipped for *this* iteration, correctly picked up again once `getRoomCardsAndLinks()` re-runs and finds it fully populated.

**Real finding two: `persistJob()`'s concurrent writes had no ordering guarantee - confirmed against Chrome's own documented behavior, not assumed.** Direct research confirmed `chrome.storage.local` "wasn't designed to be ACID compliant" and provides no ordering guarantee for concurrent `set()` calls to the same key (the Chromium extensions team's own description). Multiple worker tabs genuinely call `persistJob()` at effectively the same moment in real operation - each reaches its own call via an independently-timed chain of awaits inside `processRoom()` (page loads, the 90s processing bound, download-start polling), so overlapping in-flight writes are the normal case at real concurrency, not an edge case. Without serialization, a write that happened to *complete* later - even though issued earlier - could silently overwrite a newer one in the *persisted* copy only (in-memory `STATE` is never affected). Fixed by serializing every `persistJob()`/`clearPersistedJob()` call through a shared promise chain (`persistChain`), the same pattern already proven for panel.js's `confirmDialogChain` - writes are never actually concurrent at the `chrome.storage.local` API level at all anymore, so correctness no longer depends on an implementation detail this project has no control over.

**A test written against this fix, then corrected after it failed - worth recording as an example of the verification discipline this request asked for, not hidden as a false start.** The first version of the regression test asserted that an *earlier-issued* write should still reflect an *older* snapshot of `STATE` than a later one. It failed - not because the fix was wrong, but because the test's own premise was: `persistJob()`'s internal write function reads `STATE` fresh at *execution* time (when its turn in the chain arrives), not at *call* time, so a write queued early but delayed by serialization ends up seeing whatever is true by the time it actually runs - which is correct, arguably even better (freshest data always wins), just not what the test assumed. Rewritten to check the property that actually matters and is actually guaranteed: `chrome.storage.local.set()` is never called a second time while an earlier call is still in flight.

**Two additional, smaller hardening changes, documented honestly as hardening rather than overstated as confirmed-live fixes:** `chrome.downloads.onChanged`'s "download completed" handler now calls `persistJob()` (previously only `broadcastStatus()`) so a room's status upgrade to "Downloaded" is checkpointed close to real time, not just at its *first* result - not load-bearing for final correctness (`verifySuccessAttemptedResults()` already re-derives this from Chrome's real download history at the run's natural end regardless), but a tighter, more accurate on-disk snapshot at every point in time for the same low cost as everywhere else `persistJob()` is already called. Added the `unlimitedStorage` permission, removing `chrome.storage.local`'s default ~10MB quota entirely - this account's real size (13,000+ rooms confirmed this session) means a persisted job could plausibly approach that ceiling; hitting it was already handled gracefully (a caught, logged, degrade-gracefully error, not a crash), but removing the ceiling outright is a stronger guarantee than relying on graceful degradation for something explicitly meant to be "airtight for production."

**Delivered a permanent "High-Risk Areas" reference section**, placed before the chronological Decision log rather than folded into it - a cross-reference by *function/area* instead of by *time*, answering "is this specific thing dangerous to touch, and what should I check before I do" without requiring a read of the entire history first. Covers `content/scan.js`'s scan loop (five separate fixes this session alone), `findCurrentRoomForDownload()` (corrected repeatedly within Decision 2), the `STATE.scanning`/`STATE.running` stuck-forever pattern as a recurring *class* of bug rather than a single function, `persistJob()`, `cleanName()`, and `computeFolderNames()` - each entry grounded in verified mention/correction counts pulled directly from this file, not from impression.

**Tested with 1 new regression test** (the corrected `persistJob()` serialization test above); the stale-DOM-read fix remains DOM-orchestration code outside `node:test`'s scope per Decision 13, verified by code review, consistent with every other `content/scan.js` fix this session. Full suite: 115/115 passing (114 prior + 1 new).

## Decision 40: "We Cannot Tolerate a Room Being Glossed Over" - Closing the Rest of the Stale-DOM Gap, and Proving (Not Just Claiming) Neither Side Loses One Silently

**Problem, stated as a hard requirement, not a bug report: "we need the download and scan to be verified we cannot tolerate a room being glossed over like the bug you described."** A direct challenge to Decision 39's own stale-DOM-read fix - had it actually closed the gap completely, or only the part that happened to be found first? Re-examined the fix rather than defending it as already sufficient.

**Found a second, closely related hole in the same fix: element *existence* isn't the same as element *content*.** `getRoomCardsAndLinks()` checked `!nameEl || !dateEl` - whether the elements existed - but not whether `dateEl` actually had text in it yet. `new Date("")` (what a present-but-still-empty date element produces) is an **Invalid Date** - a real object, therefore truthy, so it slides straight past a bare existence check; every comparison against it (`>=`, `<=`) then silently evaluates to `false`, exactly mimicking a legitimately out-of-range room in the final filter. The original fix closed "element missing"; this closes "element present but empty" - the more likely of the two for a framework that (per Decision 39's own research) creates an element before painting its text content into it.

**Built a standing safeguard, not just a second patch - because a third variant of this same shape of bug is always possible, and "found it eventually" isn't the same as "verified."** `autoScrollAndCollectRooms()` now tracks every `documentsUrl` ever seen as an incomplete row (real link, name or date still missing) across the *entire* scan, unioned in `everIncompleteUrls`. Right before returning, it reconciles that set against `seenUrls` (everything that *did* eventually become a real, complete room) - any URL present in one but not the other represents a room that was glimpsed but never resolved by the time the scan ended, for any reason, not just the two specific timing gaps already found and fixed. If any exist, the scan throws - routed through the same `DS_SCAN_FAILED` path every other real scan failure already uses, with a message naming exactly how many rooms and their URLs, rather than a status line that the next progress update would silently overwrite. Deliberately a hard failure, not a warning that could be missed: given the explicit "cannot tolerate" standard, forcing the user to notice and re-run is the correct tradeoff over risking an export that looks complete but silently isn't. Any checkpoint already saved (Decision 37) still holds everything collected up to the last 1,000-room milestone even when this fires, so it's not a full loss when it does.

**Verified this reconciliation also correctly catches a case neither the original bug nor its fix anticipated: a room trimmed out of the DOM (Decision 37) while still incomplete.** `trimOldRoomRows()` only removes rows once far enough back to be well clear of the live scroll position, so a row would need to sit incomplete through 500+ newer rooms loading past it - a narrow window, but a real one, and once a row is removed from the DOM entirely, it structurally *cannot* ever finish rendering afterward. Traced through deliberately: this case still lands correctly in `everIncompleteUrls` without a matching `seenUrls` entry, and gets caught by the exact same reconciliation check - not a separate fix, a confirmed side effect of the general design being actually general, not narrowly patched to the one scenario that was directly observed.

**On the download side, verified (not assumed) that the equivalent guarantee already existed, and proved it with a real test rather than resting on the claim.** Traced the one place a claimed room could plausibly vanish without a result: `processRoom()`'s `if (!(await waitIfPausedOrStopped())) { keepGoing = false; }` branch - reachable if Stop is clicked in the exact window between a room being claimed and its result ever being pushed - genuinely does skip pushing a result for that room. But `createReport()` was already built (well before this session) to walk `STATE.queue` - the full, immutable original list - rather than `STATE.results`, specifically so a room with no result still gets a row, falling back to `"Waiting"`. That design already fully covers this case; nothing needed fixing on the download side. Proved it directly rather than trusting the reasoning alone: a new test seeds a 3-room queue with only 2 results (the third deliberately absent, simulating the exact Stop-race above), calls the real `createReport()`, decodes the resulting CSV out of the mocked `chrome.downloads.download()` call, and confirms the header plus all 3 rows are present - the un-resulted room correctly marked `"Waiting"`, not missing.

**Tested with 1 new regression test** (`createReport()`'s reconciliation, described above) - passed on its first real run, a genuine confirmation of an existing guarantee rather than a fix. The `getRoomCardsAndLinks()` empty-date-text fix and the `everIncompleteUrls` reconciliation both remain DOM-orchestration code outside `node:test`'s scope per Decision 13, verified by code review and the trimming interaction traced through by hand above. Full suite: 116/116 passing (115 prior + 1 new).

## Decision 41: A Third Way to Silently Report "0 Rooms" - Found by Reading Real Filesystem Evidence, Not Assumption, Plus a Deliberate Revision of Decision 13's Testing Boundary

**Problem, raised directly by the user against real evidence, not a bug report: "i thought you mentioned csvs got downloaded gradually when scanning after like 1000 rooms so far i havent seen anything."** Rather than answer from memory of what the checkpoint feature (Decision 37) was *supposed* to do, checked the actual `~/Downloads/Docusign Rooms/_Scan Lists/` folder directly. Found no checkpoint/"in progress" file had ever been created - consistent with "no scan has reached 1,000 real rooms yet," *if* that were the only possible explanation. It wasn't: the same listing showed the account's large `2023-01-01 to 2024-12-31` scan producing a real, ~7,463-room, 850,428-byte export once, then failing with a header-only, 0-room, 61-byte CSV **four separate times since**, spanning multiple fix commits including ones made earlier in this same session - while smaller, easier-to-reach ranges (2020, 2021) succeeded every single time. `cat`ting one of the 61-byte files confirmed it was a genuine header-only success export, not a crash artifact or thrown-error case.

**Root cause: Decision 38's "did the scan find anything at all" check only ever compared against `collected.length`, not against how many of those rooms actually fell inside the requested range.** The Rooms list is sorted oldest-first (Decision 4) and this account's data goes back to at least 2020 - so a scan requesting 2023-2024 must first scroll *past* several thousand rooms from 2020-2022 before it ever reaches a single in-range room. If that preliminary scroll stalls for any reason (a network hiccup, a brief tab-focus loss, anything that pauses DOM growth for the ~15-attempt `noNewRoomAttempts` window) *before* reaching `dateStart`, `collected.length` is very much nonzero (thousands of genuinely-found pre-range rooms) - so Decision 38's `if (collected.length === 0) throw` never fires, and the loop falls through to a plain, successful-looking return of `collected.filter(inRange)`, which is legitimately empty. The result: a real failure indistinguishable, at the CSV level, from a genuinely empty range - exactly the ambiguity Decision 38 was written to eliminate, just not for this specific shape of it. This also directly explains why no checkpoint file had appeared: the scan never got anywhere near the 1,000-room-in-range checkpoint threshold, because it never collected a single in-range room before stalling.

**Fixed by checking rooms actually within `[dateStart, dateEnd]`, not `collected.length`, at the exact place the loop ends via a stall (`content/scan.js`, the `!stoppedEarly && noNewRoomAttempts >= 15` branch):**

```js
const inRangeCount = collected.filter(room => room.createdDate && room.createdDate >= dateStart && room.createdDate <= dateEnd).length;
if (inRangeCount === 0) {
  if (collected.length === 0) {
    throw new Error("No rooms loaded after scrolling for a while - ..."); // Decision 38's original message, still exact for this narrower case
  }
  throw new Error(`Scan stalled after finding ${collected.length} room(s), but none were within the requested date range - it likely stopped before reaching that range rather than the range genuinely being empty. Try again; if it keeps happening, try scanning in smaller date chunks so each scan has less to scroll through before reaching its range.`);
}
```

`outOfRangeStreak` (the other loop-ending condition, a few lines above) is left untouched and is the reason this fix can't just check `inRangeCount === 0` unconditionally at the very end: reaching that condition *proves* the scan actually scrolled through the requested range and found nothing there - a legitimately empty result that must still succeed. Ending via a stall instead proves nothing either way about whether the range was ever reached, so - same reasoning Decision 36 already established for the sort-order check - that ambiguity is resolved in favor of failing loudly rather than exporting a silently-empty CSV.

**Deliberately revised Decision 13's testing boundary for this one function, rather than verifying by code review alone.** Decision 13 scoped `content/scan.js`'s DOM-scraping/scrolling logic out of `node:test` entirely ("stays covered by live testing... not blanket coverage for its own sake") - a reasonable line when the file had no history of *control-flow* bugs, only DOM-timing ones caught live. That's no longer true: this is the **third** distinct way this exact loop has silently reported 0 rooms as success (Decisions 36, 38, and now this one), each one only found after it already happened for real. That pattern - a fix that closes the specific case just found without a way to prove it closes the *general* one - is exactly what a real test against the actual loop logic can catch that code review alone has now missed twice. Added `tests/helpers/dom-stub.js`, a narrow, purpose-built fake of only the `document` surface `content/scan.js` actually touches (`querySelectorAll('tr[data-qa="room-list-row"]')`, each row's `a[href]`/`strong[data-qa="room-name"]`/`strong[data-qa="room-date"]`, `.remove()`) - not a general DOM library, and not a reversal of Decision 13's reasoning about *timing*-dependent bugs (those still need a real browser), just an acknowledgment that the loop's *branching logic* (stall vs. out-of-range vs. genuine success, `collected.length` vs. `inRangeCount`) is itself pure enough to drive directly once the DOM reads it depends on are stubbed. Also added a `module.exports` tail to `content/scan.js` itself (previously had none, so nothing in it was `require()`-able at all), mirroring `content/utils.js`'s own test-tail pattern exactly (Decision 13) for the same reason: a no-op under Chrome, real exports under Node.

**12 new tests in `tests/scan.test.js`**, including direct regression coverage for this exact bug (a 20-room, all-pre-range DOM with scrolling stalled, asserting the new "stalled" message and specifically *not* the old "nothing ever loaded" message), a proof the fix doesn't overcorrect (a genuinely-empty range reached via `outOfRangeStreak` still returns `[]` without throwing), the original Decision 38 case still throwing its original message, `getRoomCardsAndLinks()`'s incomplete-element/empty-date-text guards (Decisions 39/40), `trimOldRoomRows()`'s keep-count and return-value behavior (Decision 37), and the `everIncompleteUrls` reconciliation (Decision 40) both failing when a room never resolves and succeeding when it resolves on a later scroll. One genuine test-authoring mistake self-caught before trusting the results: the first draft used non-numeric fixture room IDs (`"pre-0"`, `"stuck"`) which `roomUrlToDocumentsUrl()`'s real `/\/rooms\/(\d+)/i` regex - correctly - rejects as not a room URL at all, silently producing 0 parsed rooms and a false-positive-looking pass; caught by tracing *why* a supposedly-working fixture produced an empty result instead of accepting the first (wrong) explanation, and fixed by using digit-only fixture IDs throughout, matching what a real Docusign room ID actually looks like. Full suite: **128/128 passing** (116 prior + 12 new), confirmed via `npm test` after the fixture fix, not before it.

## Decision 42: A Scan-Side Activity Log - Periodic Aggregate Reporting, Plus an Audit That Found a Second Real Bug Along the Way

**Problem, requested directly: "kinda like you did for the download maybe do an activity log so that it can be recorded what happened to every room seen... this could be nice visual like it was for downloads."** The download side already has a live, exportable Activity Log (`STATE.workerEvents` / `logWorkerEvent()` / `describeWorkerEvent()` / `createEventLogReport()` - Decision 15) covering worker-tab lifecycle events; scanning had no equivalent at all - only a status line (`DS_SCAN_PROGRESS`) that the next update immediately overwrites, and the periodic checkpoint CSV (Decision 37), which shows *what* was found but not a running narrative of it.

**Scoped as a periodic aggregate, not a per-room diary - a deliberate, explicit decision, not an oversight.** A literal "room seen / room recorded / room removed from the DOM" entry for every room would mean tens of thousands of log lines on a large scan (13,000+ rooms, per the account this project is built around) - unreadable in the panel's Activity Log and pointless bulk in the exported CSV. Reused the same 1,000-room cadence `CHECKPOINT_EVERY` already established for checkpoint saves (Decision 37), so this is one more thing that happens "at the same milestone," not a second, independently-tuned timer to reason about.

**Implementation:** `trimOldRoomRows()` (`content/scan.js`) now returns the count of rows it actually removed (previously void) - this repurposes the exact detail already computed there, not a new pass over the DOM. `autoScrollAndCollectRooms()` accumulates that into `totalTrimmed` and gained a fifth, optional `onActivity` callback, fired at the same point as `onCheckpoint` (every 1,000 new rooms) with `{ totalFound, inRangeFound, totalTrimmed, final: false }`, and once more right before returning with `final: true` - guaranteeing at least one report even for a scan that never crosses the 1,000-room threshold at all. `content.js` wires this to a new `DS_SCAN_ACTIVITY` message; `background.js`'s handler logs it via the existing `logWorkerEvent("scan_activity", ...)` and - unlike `DS_SCAN_PROGRESS`, which only ever reaches the status line - explicitly calls `broadcastStatus()` so it's visible live in the panel's Activity Log during the scan itself, not only after `DS_SCAN_COMPLETE`. `content/utils.js`'s `describeWorkerEvent()` gained a case rendering it as `"Scan progress: N rooms found so far (M in range), T DOM rows trimmed"` (or `"Scan finished: ..."` for the closing one) - no panel.js changes needed at all, since it already renders the Activity Log generically off whatever `describeWorkerEvent()` returns for each event's `type`.

**A second, real, independent bug found while auditing this area before adding to it - not from a new report, from actually reading the code being touched.** The `chrome.alarms`-driven stall watchdog's own neighboring comment claims its sign-of-life signal is "`DS_SCAN_PROGRESS`/`DS_SCAN_CHECKPOINT` (both update `STATE.lastScanActivityAt`)" - but the `DS_SCAN_CHECKPOINT` handler never actually contained that line. It only appeared to work because `DS_SCAN_PROGRESS` fires on every scroll regardless (~1.5-2s), so the watchdog's timer kept getting refreshed anyway, by coincidence rather than by that handler doing what its own comment said it did. Harmless today only because of that redundancy - but exactly the kind of code/comment mismatch that stops being harmless the moment either message stops firing independently of the other for any reason. Fixed by adding the missing line, and the comment corrected instead of just the code, now naming all three messages (`DS_SCAN_PROGRESS`, `DS_SCAN_CHECKPOINT`, `DS_SCAN_ACTIVITY`) that genuinely update it.

**Also found, while extending `describeWorkerEvent()`'s switch statement, that its own test's name was already false before this session touched it.** `tests/utils.test.js` has a test literally named "describes every logWorkerEvent() type background.js actually emits" - but `background.js` has called `logWorkerEvent()` with `scan_failed` (Decision 33), `run_queue_failed` (Decision 34), `scan_checkpoint_failed`, `scan_watchdog_stalled`, and `scan_tab_navigated` (Decision 37) since well before this session, none of which had a real case in `describeWorkerEvent()`'s switch or an assertion in that test - every one of them was silently falling through to the generic `default: return evt.type` fallback in the actual Activity Log a user would see, showing a bare code like `scan_watchdog_stalled` instead of a real sentence. Added real cases for all five, plus `scan_activity`, and extended the test with genuine assertions for each - the test's name is now actually true, not just aspirationally so.

**Tested with 6 new tests** across `tests/background.test.js` (`DS_SCAN_ACTIVITY` logs the event and calls `broadcastStatus()` so it's live during a scan, not just at the end; `DS_SCAN_ACTIVITY` refreshes the stall watchdog's sign-of-life timestamp; `DS_SCAN_CHECKPOINT` now does too, direct regression coverage for the bug found above) and `tests/scan.test.js` (`onActivity` fires at the correct 1,000-room-crossing cadence with correct aggregate counts and a genuinely nonzero `totalTrimmed`, still fires exactly once with `final: true` on a scan that never reaches that threshold at all, and existing callers that omit the new optional parameter are unaffected) - plus 6 new assertions in the existing `describeWorkerEvent` test closing the coverage gap described above. One shape inconsistency self-caught while writing these tests, not left for a user to notice in the exported CSV: the periodic `onActivity` call initially omitted `final` entirely (`undefined`) while the closing call set `final: true` - functionally harmless (`describeWorkerEvent()`'s `evt.final ? ... : ...` already treats `undefined` and `false` identically) but an inconsistent event shape in the exported Activity Log CSV; fixed by explicitly setting `final: false` on the periodic call for symmetry, rather than loosening the test to tolerate the asymmetry. Full suite: **134/134 passing** (128 prior + 6 new).

## Decision 43: A Standalone Audit - Closing a Known-But-Unfixed Risk, and an Alarm That Never Stops Ringing

**Problem: "run another audit."** No new symptom to chase - a deliberate, standalone re-read of `background.js` end to end, looking specifically for the class of bug this project keeps finding: a comment that promises something the code doesn't actually do, and a resource that's created but not guaranteed to be cleaned up on every path.

**Found a real, previously-known-but-never-fixed risk by following a comment's own cross-reference.** `updateKeepAwake()`'s comment (Decision 36) mentions, in passing, "the `DS_SCAN_COMPLETE` mode-loss risk this same incident surfaced" - a real gap that had been *identified* during the lock-screen investigation but never actually closed, and never written up as its own Decision. Traced it fully: `STATE.scanMode` is deliberately never persisted (scanning is explicitly documented as non-resumable - "if the worker dies mid-scan, the scan is simply gone"), so a service-worker restart in the narrow window between a scan starting and finishing resets it to `null` in the fresh worker - but the *content script*, running independently in its own tab, has no idea the worker restarted, and keeps going, eventually sending a real `DS_SCAN_COMPLETE` with real results back to a worker that no longer remembers what kind of scan this was. `DS_SCAN_COMPLETE`'s handler only ever checked `mode === "export"`, with a plain `else` covering everything else - so a lost mode silently fell through to `"start"` behavior. Verified against panel.js (both scan buttons) that `mode` is *always* exactly `"export"` or `"start"` in real operation, never anything else - so `null` here is a reliable, unambiguous signal of exactly this failure, not a legitimate state that needs a third real behavior. The actual consequence is worse than a cosmetic mislabel: a user who only clicked "Export scan list" (expecting a CSV) could instead see the panel's `"Found N rooms... Continue?"` prompt - the one that offers to *start downloading everything* - a real, unintended action, not just a wrong log line. Fixed by giving `mode === "start"` and "anything else" separate branches: the former unchanged, the latter now reports a real `DS_SCAN_FAILED` (`"the extension's background process restarted while it was running... please run the scan again"`) instead of guessing, consistent with this project's standing rule of failing loudly over silently proceeding on an ambiguous outcome (Decisions 36/38/41).

**Found a second, related, real bug by not assuming and instead checking Chrome's own documentation on `chrome.alarms` persistence.** The scan-stall watchdog's whole design relies on `chrome.alarms` surviving a service-worker restart - confirmed correct, but researched further rather than left as "probably also fine": Chrome's own documentation states an alarm defaults to `persistAcrossSessions: true`, surviving not just a worker restart but a *full browser restart*, unless explicitly cleared. That's exactly what makes the watchdog work - and exactly what turns "the worker restarted mid-scan" into a second problem: `STATE.scanning` resets to `false` in the fresh worker (never persisted, by design), so the watchdog's own `!STATE.scanning` guard means it can never *misfire* a false `DS_SCAN_FAILED` - but nothing was ever going to *clear* the now-orphaned alarm either, short of a brand new scan happening to start and overwriting it (`chrome.alarms.create()` with the same name replaces any existing alarm). For a market center whose scan happens to get interrupted by a worker restart and who doesn't run another scan again soon, that alarm would otherwise keep waking the service worker up once a minute, forever - a real, if quiet, resource cost with no natural end. Fixed by clearing `SCAN_WATCHDOG_ALARM` unconditionally at the very top of the service worker's own startup sequence, independent of whether a persisted download-run job was found - this has nothing to do with that resume logic, it's cleanup for a completely different kind of leftover state.

**Found a third, smaller, real gap while re-reading `pendingReportFilenames`' own comment against the code that now uses it.** That comment's stated invariant - "at most 3 entries ever pending at once" - was written before Decision 37's periodic scan checkpoints existed, and before Decision 42 extended that same pattern further. It's still true for the three once-per-run report exports (each cleaned up by `onDeterminingFilename` once consumed), but `DS_SCAN_CHECKPOINT` can legitimately fire many times over one long scan, and none of the four call sites ever cleaned up their `pendingReportFilenames` entry if `chrome.downloads.download()` itself rejected - `onDeterminingFilename` never fires for a download that never started, so nothing would ever consume (and thus delete) that entry. Low practical likelihood (a `data:` URL with `saveAs: false` rarely rejects outright), but each entry is keyed by the *entire CSV content as a string* - a real, if narrow, memory-accumulation risk for a long scan with intermittent write failures, in a service worker whose ephemeral lifecycle already has enough memory pressure to avoid adding to unnecessarily. Fixed the one call site with genuine repeat-invocation risk (`DS_SCAN_CHECKPOINT`) by deleting its own entry inside the failure `.catch()`, and corrected the comment's stated invariant to describe the actual (narrower) guarantee rather than the one that stopped being fully true two decisions ago without anyone updating the comment.

**Tested with 3 new regression tests**, each one deliberately verified to catch its own regression before being trusted - not just written and assumed correct: for each fix, the fix was temporarily reverted (via a throwaway backup, restored immediately after), the test suite re-run to confirm the specific new test failed for the right reason, then the real fix restored and the suite re-confirmed green. `DS_SCAN_COMPLETE` with a lost mode now asserts a real `DS_SCAN_FAILED` fires and no `DS_SCAN_RESULT` is ever sent; a fresh `freshBackground()` load now asserts `chrome.alarms.clear(SCAN_WATCHDOG_ALARM)` was called unconditionally; a `DS_SCAN_CHECKPOINT` whose `chrome.downloads.download()` is mocked to reject now asserts `pendingReportFilenames`'s size is unchanged rather than grown by one - `pendingReportFilenames` itself was added to the test-only export tail specifically to make this last assertion possible, the same reasoning `STATE` itself has always been exported for. Full suite: **137/137 passing** (134 prior + 3 new).

## Decision 44: 0-Byte Documents Silently Blocking the Bulk Download Button - Found and Fixed From Real Captured Markup, Confirmed Live

**Problem, reported directly: "I noticed a fix for failed rooms that fail to show the download button... basically any rooms with documents of a size of 0B will cause it so that when select all is pressed the download button does not show."** `content.js`'s `processCurrentRoom()` already had a generic "Bulk download button was not found" failure (its own reason had been openly documented as usually meaning nothing more than "the button genuinely never existed for this room" - see phase 5q's `HOW_TO_USE.md` rewrite) - but this was a real, specific, previously-unknown root cause for at least some of those failures, not just an explanation of an already-accepted one.

**Verified against real, captured markup before writing a single selector - not guessed.** The user pasted the actual rendered HTML of a real room's Documents page. It confirmed: every document row has exactly 6 `<td>` columns (Checkbox, Type, Document, Owner, Added, Size, in that header order), the last of which holds the file size as a bare `<strong>0 B</strong>` / `<strong>224 KB</strong>` with no `data-qa` of its own, and the checkbox itself carries a real, stable `data-qa="document-checkbox"` - the same kind of anchor `getRoomCardsAndLinks()` already relies on for the room list, just one level down. A follow-up from the user narrowed the actual rule further: **the button only renders if at least one currently-*selected* document is non-zero** - confirming this wasn't just "0-byte documents look weird," it was "a room with a mix of real and 0-byte documents fails completely, even though its real documents are perfectly downloadable on their own."

**Fixed with a narrow-blast-radius design, not a wholesale replacement of a long-proven interaction.** `selectAllViaToggle()` (the original "click the one Select All checkbox" logic, confirmed working via two earlier live corrections) is left completely untouched and still handles the common case - a room with no 0-byte documents at all. A new `getDocumentRows()` reads every document's own size cell and classifies it via `isZeroByteSizeText()` (a new, pure helper in `content/utils.js`, matching only `/^0(\.0+)?\s*b$/i` - deliberately *not* `"0 KB"`/`"0 MB"`, since Docusign shows raw bytes for anything under 1KB in every sample seen, so a non-byte unit attached to a "0" would mean genuine, if small, content). Only when a room actually has at least one 0-byte document does `selectAllDocuments()` switch to selecting every document individually (label-click-then-fallback-MouseEvent, the exact same proven pattern, just applied per-row), skipping the 0-byte ones. If literally every document in the room turns out to be 0 bytes, it falls back to selecting everything anyway (nothing gained by excluding all of them) and reports that specific, honest reason instead of the old generic one.

**First live test failed - not because the underlying theory was wrong, but because the extension hadn't actually reloaded.** The very first attempt did nothing different at all ("it just did select all"). Diagnosed by adding real, targeted `console.log` output (per-row size text and classification) rather than guessing again, and asking directly whether the *Docusign tab itself* - not just the extension - had been refreshed after the extension reload. (MV3 content scripts are injected once per page load; reloading the extension in `chrome://extensions` does not retroactively re-inject into a tab that's still showing the old script.) The second attempt, after a real tab refresh, **worked** - confirmed live by the user against the exact room from the captured markup.

**A real correctness gap found afterward, before declaring this done, not after - raised directly: "make sure that for the failure its now because there is genuinely no documents that can be downloaded."** `getDocumentRows()` runs as soon as `[data-qa="group-name"]` (the group header) is present - but that element existing only proves the *header* rendered, not that every one of its document *rows* has, the exact same class of gap already found and fixed twice for the room list (Decisions 39/40). If `selectAllDocuments()` ran while only some rows had painted in, and those happened to all be 0 bytes, it would have wrongly concluded "every document in this room is 0 bytes" for a room that actually still had real documents loading. Fixed by threading `documentCount` (already read from the same group header, via `getDocumentCount()` - established reliable back in Decision 4) into `selectAllDocuments()`, which now polls (up to 10s) for the row count to actually reach that total before trusting anything about zero-byte-ness at all - falling back to the always-safe toggle path, never a false "genuinely nothing downloadable" conclusion, if the count can't be confirmed complete in time.

**A second real, distinct concern raised the same way, also before declaring this done: "these need to be rechecked... but not cause an infinite loop like last time."** A room that fails because it's genuinely, permanently unfixable (every document confirmed 0 bytes) still needs its own outcome, not a bare "Failed" - `parseUploadedCsv()` (`content/utils.js`) treats "Failed" as always worth retrying on a CSV-upload resume, with no way to tell "might work next time" apart from "will never work, ever." Without a distinct status, a room like this would get silently re-queued and re-attempted on *every single future resume, forever* - a real, reported operational concern, not a hypothetical one. Fixed by giving it its own terminal status, `"Complete (All 0 Bytes)"`, mirroring `"Complete (Empty)"`'s existing treatment exactly: `content.js` returns `ok: true, allZeroByte: true` (a correctly-determined terminal state, not a failure) instead of `ok: false`; `background.js`'s `processRoom()` maps that to the new status and skips the same 15s `waitForDownloadStart()` wait `Complete (Empty)` already skips (there's no download to wait for either way); `parseUploadedCsv()` routes it to `priorResults` alongside `Downloaded`/`Complete (Empty)`, never `rooms`; `panel.js`'s breakdown, "everything already marked" message, and both "Done" status lines all updated to name it explicitly rather than let it hide inside a generic count.

**Refactored `isZeroByteSizeText()` out to `content/utils.js` specifically so it could get real test coverage** - `content.js`'s own top-level IIFE still can't be `require()`'d under Node without a full DOM stub (Decision 13's original boundary, not revisited here), but the *pure text-matching* judgment underneath the DOM read doesn't need one, the same reasoning that already moved `formatDateRangeLabel`/`describeWorkerEvent`/etc. out of `content.js` in Decision 19. Caught and fixed one real oversight before calling this done: `content.js`'s `getDocumentRows()` was still using its own inline copy of the same regex after the extraction, rather than calling the newly-tested function - two copies of the same logic, only one of them actually covered by a test, silently free to drift apart later. Fixed by having `getDocumentRows()` call `isZeroByteSizeText()` directly; confirmed behavior-neutral (both trim the input before matching, so calling `.trim()` twice is a no-op) rather than re-requiring another live round-trip for a provably-equivalent change.

**5 new tests**: 4 in `tests/utils.test.js` (`isZeroByteSizeText`'s exact-match behavior, including the "must not match `0 KB`/`0 MB`" case and safe handling of missing/empty/unrecognized text; `parseUploadedCsv` routing `"Complete (All 0 Bytes)"` to `priorResults`) and 1 in `tests/background.test.js` (`processRoom()` gives the new status, not `"Failed"`, and genuinely skips the 15s download-start wait - verified by timing the test itself, not just asserting the status string, and by the same revert-confirm-restore discipline as Decision 43: reverting the skip condition made the test time out for the right reason before the real fix was restored). Full suite: **142/142 passing** (137 prior + 5 new).

## Decision 45: A Second Real Tab Crash - a Silent Checkpoint-Naming Bug, a Stuck Stop Button, and a Watchdog That Missed a 2-Hour Sleep

**Problem, reported directly: "website crashed again"** - on an account that had, minutes earlier, been directly confirmed holding steady at exactly `DOM_TRIM_KEEP` (500 rendered rows) through 13,700 rooms scanned, well past the ~7,463-room account that originally motivated DOM trimming (Decision 37). Investigated with real evidence at every step, not assumption - the user's own Activity Log transcript and the actual checkpoint files on disk, both requested and read directly rather than guessed at.

**Found a real, silent bug in the checkpoint file itself, unrelated to the crash but caught along the way: ten separate numbered files instead of one being overwritten.** `Downloads/.../_Scan Lists/` showed `"... (in progress - partial) (1).csv"` through `"(10).csv"`, each roughly 1,000 rows bigger than the last - not the one stable, repeatedly-overwritten file Decision 37 built and a prior test already claimed to confirm. Root-caused to `chrome.downloads.onDeterminingFilename`'s own `suggest()` call - the mechanism this project's own Decision 30 already established as the actual source of truth Chrome obeys for a `data:` URL, overriding whatever `conflictAction` was passed to `chrome.downloads.download()` itself - which had *always* hardcoded `conflictAction: "uniquify"` for every entry in `pendingReportFilenames`, regardless of what the original call actually wanted. The three once-per-run exports (Scan List, Download Report, Activity Log) all genuinely want `"uniquify"`, so this was invisible for them; `DS_SCAN_CHECKPOINT` explicitly requests `"overwrite"`, and that request had been silently discarded every single time. The existing test for this ("DS_RUN_SCAN computes a stable scanCheckpointFilename...") only ever asserted on what was *requested* of `download()` - it never simulated `onDeterminingFilename` actually firing, so it had genuine, real confidence in the wrong half of the mechanism the whole time. Fixed by storing `{ filename, conflictAction }` per entry instead of a bare filename string, and having `suggest()` use the stored value - extended the existing test (not just added a new one) to actually invoke the listener and check what it suggests, closing the same kind of test/reality gap Decision 43 and Decision 44 both already found once each this session.

**Found a second, more urgent real bug from the user's own next message: "after the crash i press stop and the extension is stuck again."** `DS_SCAN_STOP` only ever relayed a message to the scan tab and immediately told the panel "ok," with nothing checking whether the tab was actually still there to receive it. Against a genuinely crashed tab, that message goes nowhere, `STATE.scanning` never resets, and the only thing that eventually would (the stall watchdog) can take up to the full 2-minute `SCAN_STALL_THRESHOLD_MS` - far longer than someone who already explicitly clicked Stop should reasonably have to wait, especially right after watching the page crash in front of them. A user clicking Stop has stated their intent unambiguously regardless of whether the tab is alive to hear it. Fixed with a bounded, generous 8-second window (`SCAN_STOP_FORCE_TIMEOUT_MS`) for the common case - a genuinely alive tab finishing its own graceful wind-down and reporting real results normally, which only needs to react within one ~1.5-2s scroll cycle - after which the scan is force-reset regardless, extracted into its own named, directly-testable function (`forceResetStoppedScanIfStillActive()`) rather than left inline inside a `setTimeout` callback, the same shape the alarm-based watchdog's own check already has for exactly this reason.

**Found a third, deeper bug by reading the user's own Activity Log transcript closely rather than only reacting to the crash itself.** Checkpoint timestamps ran ~6-12 minutes apart for eight consecutive checkpoints, then jumped to **over 2 hours** for the ninth - the crash followed shortly after. `chrome.power.requestKeepAwake` (Decision 36) is already documented as unable to override a laptop lid closing; a multi-hour gap between otherwise-consistent checkpoints is the exact shape a system sleep/wake cycle would produce, with the scan's own JS execution simply paused for the duration and resuming right where it left off. The genuinely concerning part: the stall watchdog - built specifically to catch a crashed, unresponsive tab - never fired during that 2-hour gap at all. Traced to a real race in the watchdog's own design: `chrome.alarms` itself can't fire while the system is suspended, but on wake, the scan tab's content script resumes at essentially the same moment the watchdog's next tick does - if the scan's own next scroll iteration sends a `DS_SCAN_PROGRESS`/`CHECKPOINT`/`ACTIVITY` message (refreshing `STATE.lastScanActivityAt` to "now") before the watchdog's callback actually runs and checks that value, the watchdog sees a fresh timestamp and concludes nothing happened - never realizing a multi-hour gap just occurred underneath it. Fixed by tracking the gap between the watchdog's *own* consecutive ticks (`scanWatchdogState.lastTickAt`, a module-level object rather than a bare variable specifically so a test can set it directly instead of mocking `Date.now()` itself, which this file calls constantly for unrelated reasons) as a second, independent signal that can't be raced the same way - a tick gap meaningfully larger than the alarm's own 1-minute period is itself hard evidence of a suspend/resume cycle, regardless of what the activity timestamp reads by the time it's checked. Explicitly reset at every new scan's start, not just at module load - without that, the very first tick of any new scan would be compared against whatever tick a completely unrelated *previous* scan last saw, which could easily be hours earlier through nothing more than normal idle time between two scans, and would have produced exactly the false positive this fix is designed to avoid. The resulting `DS_SCAN_FAILED` message is worded differently for this case ("the computer appears to have gone to sleep... resuming after a long interruption isn't reliable") than the generic stall message, since the actionable advice is genuinely different - not "the tab may have crashed," but "resuming after a long interruption isn't reliable, and may be why it crashed a moment later."

**Tested with 6 new tests**, each verified against its own regression the same way as Decisions 43/44 - reverted, confirmed the specific new test failed for the right reason, restored: the extended checkpoint-naming test now actually drives `onDeterminingFilename` and checks what it suggests, not just what was requested; three cover `forceResetStoppedScanIfStillActive()`'s actual decision logic directly (forces a reset for a genuinely stuck scan, is a no-op for one that already finished normally, and - critically - does not tear down a *different*, newer scan that started in the meantime if a stale timer from an earlier Stop click fires late); one confirms `DS_SCAN_STOP` actually schedules the call at all, by capturing (not executing) the real `setTimeout` invocation, so a future edit that silently dropped the scheduling itself would be caught; two cover the watchdog's new tick-gap detection (fires on a suspicious gap even with fresh-looking activity; does not false-positive on a new scan's first tick against a previous, unrelated scan's last one). `tests/helpers/chrome-stub.js`'s `downloads.onDeterminingFilename` stub was upgraded from a silent no-op to actually capturing its listener, the same pattern already used for `onMessage`/`onAlarm`/`onRemoved`/`onUpdated`. Full suite: **148/148 passing** (142 prior + 6 new).

## Decision 46: Replacing the Scan Entirely - Reading Docusign's Own Internal Rooms API Directly Instead of Scrolling the Page

**Problem, continued from Decision 45's investigation: "the farthest this gets is november 2024," reproducibly, across multiple separate attempts.** Traced to a real structural gap, not a bug in any single fix: scanning has never had a resume mechanism (unlike the download run, which does) - every crashed attempt has to re-scroll through the *entire* account's history from scratch before it can make any new progress, re-accumulating whatever's actually crashing the tab each time. Since DOM row count was already independently confirmed bounded (Decision 37's trimming, verified live at 13,700 rooms holding steady at exactly 500 rows), the crash's real cause had to be something else - almost certainly Docusign's own React app accumulating internal state as it renders each room, entirely outside this extension's visibility or control via DOM manipulation alone. Two paths were raised directly: build real scan resume, or find a way to skip the rendering pipeline that's actually causing the problem.

**Investigated the second path first, since it would eliminate the crash instead of just working around it - and it worked.** Guided the user through Chrome DevTools' Network tab, live, to find what request Docusign's own page makes to load more rooms as you scroll - not guessed at, not reverse-engineered from documentation (none exists for this). Two real attempts grabbed the wrong request first (a DataDog RUM telemetry beacon, an unrelated analytics POST) before landing on the real one:

```
GET https://rooms.docusign.com/restapi/vdev/rooms?count=50&sort=createddate&roomStatus=Active&ownedOnly=False&restrictSides=True&dateRangeType=None&closingStatus=All&startPosition=50
```

A direct browser navigation to that exact URL failed with `{"message":"Could not validate CSRF token."}` - a real, useful failure, not a dead end: it confirmed the endpoint requires a custom `X-DocuSign-Rooms-CSRF-Token` header (a standard double-submit CSRF pattern) that only JavaScript running on the page itself can read from a cookie and attach - exactly the reason this has to run as a content script on the real Rooms page, not from anywhere else. A `fetch()` call from the page's own DevTools Console, reading that cookie and attaching it as a header, succeeded and returned the real response shape: `{ rooms: [...], nextUri, previousUri, resultSetSize, startPosition, endPosition, totalRowCount }`, each room carrying `roomId`, `roomName`, and `createdDate` as a precise ISO 8601 timestamp - confirmed sorted oldest-first, and `nextUri` a complete, ready-to-fetch URL for the next page rather than something requiring manual offset math.

**A real security concern surfaced twice during this investigation, handled directly rather than glossed over.** Early attempts to share DevTools evidence twice included the full **Headers** panel - which always includes the live session `Cookie` header (`X-DocuSign-Rooms-Session-Payload`, `XSRF-TOKEN`, `CartaviSessionId`, etc., real active authentication for the account). Flagged clearly and immediately both times, without repeating or using any of the exposed values, and the approach was changed to avoid it recurring: guided the user to the Console tab specifically, running a snippet that only ever prints the *resulting room data* - never a cookie or token - closing off the same mistake from happening a third time by removing the DevTools panel that kept causing it, not just warning about it again.

**Confirmed the account's actual scope directly before building anything, rather than assuming:** the account has **28,538** total Active rooms (`totalRowCount`, read live) - meaningfully more than the ~18,000 the largest crashed attempt had reached, explaining why full scans had never once succeeded past a certain point. Also confirmed directly, not assumed, that this tool has only ever needed the "Active" tab specifically (Review/Closed were never in scope) - avoiding scope creep into data the tool was never meant to capture.

**Replaced the DOM-scrolling scan entirely** (a deliberate choice, not a default - the alternative of keeping the old scan as an untested fallback was raised and explicitly declined, on the reasoning that an unused fallback nobody's kept exercising is itself a liability, and a clear failure is preferable to silently falling back to something no longer proven to work). `content/scan.js`'s `autoScrollAndCollectRooms()` keeps its exact external signature and contract (same parameters, same checkpoint/activity cadence, same Stop/Pause support, same throw-on-failure semantics for a genuine error) so nothing in `content.js`/`background.js`/`panel.js` needed to change at all - only its internals. Every DOM-scraping function this file used to contain (`getScrollContainer`, `getSortLabel`, `ensureListView`, `ensureOldestSort`, `getRoomCardsAndLinks`, `trimOldRoomRows`) is gone, not left unused - each was specific to a bug class (Decisions 35/36/37/39/40) that's now structurally impossible rather than merely unlikely: there's no more DOM to scroll or trim, no sort-dropdown UI state to trust (the API call controls sort directly via its own query string), and no such thing as a "mid-render" JSON API response the way a virtualized DOM row could be caught incomplete.

**Two real bug classes from the old implementation became structurally impossible, not just less likely** - worth stating plainly rather than just implying: Decision 41's "did the scan stall or genuinely finish" ambiguity is gone, since `nextUri` is either present (proven more data) or empty (structurally, definitively done) - the checkpoint-throw logic built for that ambiguity was removed entirely rather than kept as now-dead defensive code, since a fetch that actually fails now throws immediately and unambiguously from `fetchRoomsPage()` instead. And Decisions 39/40's entire "room glimpsed but never resolved" reconciliation mechanism (`everIncompleteUrls`, tracked across a whole scan) no longer has anything to reconcile - a JSON API response is complete and atomic by construction; there is no render-in-progress state for a room to get stuck in.

**What replaced the old risk isn't smaller, it's different, and worth being honest about:** this is an **undocumented, internal, unofficial API** Docusign has made no commitment to keep stable. `fetchRoomsPage()` validates every response's shape (`Array.isArray(data?.rooms)`) before trusting anything in it, and distinguishes three real failure modes with distinct, actionable messages: a network-level failure, a non-2xx HTTP status, and - confirmed live as a real, distinct case that status codes alone can't catch - a 200 OK response that isn't actually room data (the CSRF-rejection shape came back with a 200, not an error status). A modest, deliberate 200ms pause between page fetches was added as reasonable restraint against an endpoint this project has no formal agreement to call at any particular rate, not because a rate limit was ever actually observed.

**3 new pure helper tests plus 16 new scan tests**, all in `tests/utils.test.js`/`tests/scan.test.js` - and genuinely simpler to write than the DOM-based version's ever were, since the entire testable surface is now `fetch()` and a plain `document.cookie` string, neither of which needs a DOM stub. `tests/helpers/dom-stub.js` (built for Decision 41, used only by the now-rewritten scan tests) was deleted outright rather than left unused. `parseCookieValue()` - the pure cookie-parsing logic underneath the DOM-dependent `getCookieValue()`, split out into `content/utils.js` the same way `isZeroByteSizeText()` was in Decision 44 - has direct test coverage for a real, confirmed-live collision risk: `"XSRF-TOKEN="` appears as a literal substring inside `"X-XSRF-TOKEN=..."` too, and an unanchored search would silently grab the wrong cookie's value. Full suite: **152/152 passing**.

**Live-tested directly against the real account before anything was committed** (the user's own instruction - "wait do not commit first... i need to check this works before considering this is a major redesign"), not just against the mocked test suite: a 131-room scan across a one-year range completed correctly and fast (seconds, not minutes), and a longer in-progress scan was checked twice mid-run to confirm the checkpoint CSV grows in place under one stable filename (2,413 → 4,413 rooms, same file) rather than piling up numbered duplicates - the exact failure Decision 45 had fixed for the old scan, reverified for the new one.

**A requested follow-up audit ("double check the new scanning... error handling") found one real accuracy bug in the checkpoint-failure reminder message, fixed before committing.** The reminder (added earlier the same session, when a fetch fails after real checkpoint progress exists) originally decided whether to show itself using `collected.length >= CHECKPOINT_EVERY` and reported a room count derived from that same total - but `collected` counts every room scanned regardless of date range, while the checkpoint CSV only ever contains in-range rooms (`background.js`'s `DS_SCAN_CHECKPOINT` handler silently no-ops on an empty rooms array). Since the scan pages ascending from position 0, an account with years of history outside a narrow requested range will scan large numbers of too-old rooms before ever reaching the range at all - meaning a checkpoint boundary can be crossed, and the reminder can fire, while the actual CSV is empty or has far fewer rows than the message implies. Covered by a new regression test (`autoScrollAndCollectRooms's thrown error does NOT falsely claim a checkpoint exists when 1,000 rooms were scanned but all of them were outside the requested date range`) proving the old logic's specific failure mode is closed.

## Decision 47: Stale "In Progress" Checkpoint Files Left Behind After a Successful Scan

**Problem, reported directly right after the first real large scan completed under Decision 46's new API-based scanner:** "im very pleased... it finally completed but it left a lot of inprogress scans is that meant to happen?" - not a hypothetical, a real file-system observation from actually using the tool.

**Traced to a real gap, not a misunderstanding to be explained away.** `DS_SCAN_CHECKPOINT` (background.js) periodically overwrites one stable file per scan - `Scan List (...) (in progress - partial).csv` - every 1,000 rooms, exactly as designed since Decision 37. What was missing: nothing, anywhere in the codebase, ever deleted that file once the scan it belonged to actually finished. Confirmed by grepping the whole file for `removeFile` - zero matches. Two distinct ways this showed up:
- **"Export Scan List" mode** does write a proper final CSV (`handleExportScanList()`, no "in progress - partial" in its name) - but the checkpoint file that led up to it was simply abandoned on disk afterward, sitting there forever alongside the real export.
- **"Start" mode (scan then download) is worse** - it never wrote any Scan List CSV of its own at all, `handleExportScanList()` is only ever called from the `"export"` branch of `DS_SCAN_COMPLETE`. So for the tool's main everyday flow, the *only* Scan List CSV that ever existed for a scan crossing 1,000 rooms was the checkpoint file - permanently stuck with a name claiming it was still "in progress," even after both the scan and the entire download run that followed it had genuinely completed. This is exactly what the user saw: real, finished scans, each leaving one misleadingly-labeled leftover file behind.

**Fixed by tracking the checkpoint file's actual `chrome.downloads` download ID and removing it from disk once (and only once) its scan is confirmed to have finished successfully.** `STATE.lastCheckpointDownloadId` records the ID from the most recent successful `DS_SCAN_CHECKPOINT` write (previously discarded - the handler only ever `.catch()`'d the promise, never used its resolved value). `DS_SCAN_COMPLETE` now calls `chrome.downloads.removeFile()` against that ID:
- On `mode: "start"`, unconditionally once the scan itself reports no error - the download run about to begin has its own independent resume mechanism (`STATE.queue`/`chrome.storage.local`), so nothing depends on this CSV surviving.
- On `mode: "export"`, only *after* confirming `handleExportScanList()`'s own response reports `ok: true` - deleting the backup before its replacement is confirmed written would risk leaving the user with neither.
- **Never** when `message.error` is set - on a genuine scan failure, the checkpoint file is the *only* surviving record of whatever progress was actually made, and deleting it there would turn a partial loss into a total one.

**A real gap in test infrastructure surfaced while writing this fix's regression tests, fixed alongside it.** `tests/helpers/chrome-stub.js`'s `chrome.downloads.download` stub resolved with a bare `{}` (harmless only because nothing had ever read the resolved value before this), and `chrome.downloads.removeFile` didn't exist on the stub at all - calling it would have thrown under test. Fixed by having the stub resolve with a real, distinct incrementing integer (matching what real Chrome's API actually resolves with - a plain download ID, not an object) and adding a `removeFile` stub that records every call in `removeFileCalls`, the same "capture, don't no-op" pattern already used for `onMessage`/`onAlarm`/`onDeterminingFilename`.

**Tested with 6 new regression tests**, each verified against its own regression the same way as Decisions 43/44/46 - reverted (the two `removeFile()` call sites replaced with a no-op), confirmed the specific two tests asserting cleanup actually happened failed for the right reason (the four asserting cleanup must **not** happen still correctly passed, since they were never exercising the reverted code path), then restored and the full suite reconfirmed green: `DS_SCAN_CHECKPOINT` records a real download ID on success; `DS_SCAN_COMPLETE` (`mode: "start"`) removes the stale file; `DS_SCAN_COMPLETE` (`mode: "export"`) removes it only after a successful export; does **not** remove it on a failed export; does **not** remove it on a scan failure (`message.error` set); and never calls `removeFile` at all when no checkpoint was ever written for that scan (a short scan under 1,000 rooms). Full suite: **158/158 passing** (152 prior + 6 new).

## Decision 49: A Real Room-Processing Timeout, Traced to a 180-Document Room the Original Budget Never Accounted For

**Problem, reported directly from a real Download Report:** a room ("Elizabeth Nunez - Buyer", room ID 6574729) showed `Failed - Room processing timed out - no response from the room tab after 90s`, but the user confirmed directly that the room genuinely has a working download option - this wasn't a room the automation could never handle, something just took too long.

Re-uploading the same report to retry (per this project's standing design - a `Failed` room is always safely re-queued on resume) succeeded on the second attempt. Checked the actual downloaded file: **180 documents, ~144MB** - confirmed by unzipping it and counting, not guessed.

**Traced to a real gap in the original timeout budget's own reasoning (Decision 34).** The 90s bound on `processRoom()`'s `chrome.tabs.sendMessage()` call was sized against `processCurrentRoom()`'s *fixed* waits - up to 45s for the documents list, up to ~22s more across selecting/clicking Download - a budget that implicitly assumed the "select all documents" step takes roughly constant time regardless of room size. It doesn't: `content.js`'s `selectAllDocuments()` clicks every single document's checkbox in a plain `for` loop, one dispatched click event at a time, each one potentially costing Docusign's own React app a real re-render. That cost scales with document count and was completely invisible in the original 90s budget's math - a room with 180 documents pays for that loop 180 times over, something a typical smaller room never would have exposed.

**Fixed by doubling the bound to 180s**, not by finely tuning it to this one data point - deliberately generous rather than precisely calculated, the same reasoning Decision 37's checkpoint-interval choice used: comfortably covers a room several times larger than the one that actually triggered this, while a room that's genuinely stuck (not just large) still can't hang the rest of the run indefinitely. Also updated `withTimeout()`'s own neighboring comment and `content.js`'s matching comment, both of which cited the old 90s figure as current behavior rather than history.

**Deliberately not built: a timeout that scales with document count.** This would be a more precisely "correct" fix, but `background.js` doesn't know a room's document count until `content.js` reports it *after* processing starts - scaling the bound in advance would need a two-phase message protocol (report count, then process) that doesn't exist today. A flat, generous constant solves the actual reported problem without that added complexity, consistent with this project's standing preference for the simplest fix that actually closes the gap found, not the most theoretically complete one.

**No test changes needed** - no existing test asserted the literal `90000`/"90s" value (the `withTimeout()` unit tests use their own small literal deadlines), so the bump required no test updates; the full suite's unchanged pass count is itself confirmation nothing broke. Full suite: **159/159 passing** (no change from Decision 48).

## Engineering Concepts Demonstrated

- **Producer-consumer / work-queue parallelism** vs. divide-and-conquer, and why task-duration variance determines which one is actually faster.
- **Critical sections and atomicity without explicit locks**, using a single-threaded event loop's natural serialization as the mutual-exclusion mechanism.
- **Event-driven design vs. fixed-delay polling**, and matching timeout length to what's actually being waited for (network-bound vs. UI-reaction-bound).
- **Platform lifecycle awareness** — designing persistence around Manifest V3's deliberately ephemeral service worker model, not just around user-initiated pauses.
- **Feedback-based adaptive control vs. upfront estimation** — recognizing when a parameter can only be tuned from real measurements, not calculated in advance.
- **Constraint-driven architecture** — a stronger technical solution (the official API) correctly abandoned once it hit a real permissions boundary, rather than pursued around it.
- **Revisiting an earlier decision** (streaming scan/download) when a new requirement (resumability) changed the cost-benefit calculation.
- **Matching code organization to actual runtime boundaries** — rejecting OOP not on stylistic grounds but because of how the platform's message-passing serializes data across execution contexts.
- **Decoupling a request from its response across an asymmetric message-passing topology** — brokering communication between two execution contexts that can each reach a third (a background service worker) but not each other directly, and acknowledging long-running work immediately rather than holding a channel open for the minutes it actually takes to complete ([Decision 24](#decision-24-moving-the-panel-out-of-the-page--a-detached-window)).

## Development Process: Human-Authored, AI-Guided

In the interest of an accurate record, not a polished one: this project was built through an ongoing conversation with Claude (Anthropic's Claude Code), and the two roles involved were kept deliberately separate throughout.

**What the human (Miguel Chica) did:** wrote every line of implementation logic by hand — relocating and rewriting functions, choosing and typing the `data-qa` selectors, splitting files, renaming `findBestScrollContainer` to `getScrollContainer` once its behavior was no longer a guess, and running the actual DevTools investigation (element inspection, `getComputedStyle` checks in the Console) that determined the page has no internally-scrolling wrapper. The AI was explicitly instructed not to write feature code, so that the process would build real, transferable understanding of the codebase rather than trust in unread output.

**What the AI did:** explained unfamiliar language and browser concepts on request (`async`/`await` and Promises, optional chaining, `querySelector` vs `querySelectorAll`, CSS `overflow` and computed styles, why content scripts can't use ES module `import`/`export`); reviewed each hand-written change before the next step began, catching concrete bugs along the way — a duplicate `function getRoomCardsAndLinks` declaration that silently made the fixed version dead code, a missing `return`/dedupe block, a case-sensitive folder-naming risk (`Content/` vs `content/`); and designed the DevTools verification steps (which selectors to check, which `getComputedStyle` properties would answer the question) without performing the check itself, since only the human had the live page open.

**Where the AI wrote directly into files, by explicit request only:** the JSDoc-style documentation comments throughout `content/utils.js`, `content/scan.js`, and `content/room.js`, and one confirmed-dead-code removal (the `try/catch` scroll fallback, after the human agreed it was no longer reachable). Both were requested outright, distinct from the feature logic itself, and are called out here rather than left unattributed.

This distinction is recorded here on purpose: "AI-assisted" can mean anything from autocomplete to fully autonomous code generation, and those are very different claims about who understands the resulting system. Through Decision 11, the person who can explain any line of this codebase is the person who typed it.
