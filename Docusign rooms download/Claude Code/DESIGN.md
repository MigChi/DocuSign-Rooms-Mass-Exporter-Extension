# DocuSign Rooms Mass Exporter — Architecture & Design Case Study

## Overview

A Chrome extension (Manifest V3) that bulk-exports documents from a DocuSign Rooms account to a local folder structure — one folder per room, containing that room's documents. The project started as a small working extension and was redesigned to reliably handle **10,000+ rooms**, a scale where naive approaches (single-tab, fixed delays, no persistence) become impractical — the original design projected to **55-70 hours** of runtime.

This document walks through the problem in the order it was actually solved: what each step addressed, which options were considered, why the chosen option won, and where an earlier decision was later reversed as new requirements surfaced. For what the extension actually does today and how to use it, see the top-level [`README.md`](../../README.md) — this document is the reasoning behind it, not a user guide.

## Starting Point: Auditing the Existing Extension

The original extension used a single worker tab, processed rooms strictly sequentially, and relied on fixed `sleep()` delays (~11.5 seconds of pure dead time per room, not counting page load) to wait for DOM state to settle before clicking the next button. Its download-renaming trick — intercepting `chrome.downloads.onDeterminingFilename` to route each ZIP into `Docusign Rooms/<Room Name>/<Room Name>.zip` — was sound, but it depended on tracking exactly **one** active room globally, which meant the whole design could never be parallelized without a rework.

Doing the math on 10,000 rooms against that sequential design (~20-25s/room including page load) put the runtime at 55-70 hours — the actual number that motivated everything below.

## Decision 1: Official API vs. Continued Browser Automation

**Problem:** Is there a faster way to get this data than clicking through the UI at all?

**Option considered:** DocuSign's real Rooms REST API (`GetRooms`, `GetDocuments`, per-document `base64Contents` retrieval — verified directly against DocuSign's published OpenAPI spec, not assumed from memory). This would return individual files per room (a good match for "one folder per room," no unzipping needed) and remove browser automation entirely.

**Why it was attractive:** no scrolling, no clicking, no DOM fragility, real pagination and filtering, dramatically faster in principle.

**The blocker:** creating the OAuth credentials (an "Integration Key") required for API access sits behind DocuSign's **Account Administrator** permission — a different privilege tier from being able to use the Rooms product day-to-day. Verified in practice: attempting to reach `admin.docusign.com` produced a sign-in loop rather than a dashboard, confirming no admin rights on the account, and no admin was readily reachable.

**Decision:** abandon the API path for now and invest in making browser automation itself fast, resilient, and observable. This is a real-world instance of **a technically superior solution being inaccessible due to organizational/permission constraints** — the right engineering response is to redesign within the actual constraints, not to look for a workaround around an access-control boundary.

## Decision 2: Parallelism Model — Work Queue, Not Divide-and-Conquer

**Problem:** how do multiple browser tabs process 10,000 independent rooms faster than one tab?

**Option initially proposed:** a binary-tree / divide-and-conquer split — two tabs start at the middle of the list, each spawning further splits.

**Why it doesn't fit:** divide-and-conquer earns its complexity reduction from a *recursive subproblem structure with a combine step* (mergesort's split + merge). Downloading room #4,317 has no relationship to room #8,921 and produces no result that needs combining — each room is an independent, variable-cost task. That's the definition of an **embarrassingly parallel** workload, not a divide-and-conquer one.

**Why a shared work queue wins concretely:** with a static split (e.g., two tabs, 5,000 rooms each), if one tab's half happens to contain heavier rooms, that tab runs long while the other sits idle after finishing early — total time is bounded by the *slowest* partition, not the average. A shared queue where any free worker claims the next unclaimed item guarantees no worker is ever idle while work remains; total time approaches `total_work / N`, the theoretical best case for N workers. This dominates static partitioning whenever task duration is variable, which it is here (rooms differ wildly in document count).

**Decision:** one shared queue (an array + a pointer) with a pool of N tabs each claiming work greedily — the classic **producer-consumer / bag-of-tasks** pattern.

**Implemented.** `STATE.pending` is the queue, `claimNextRoom()` is the pointer read/increment (see Decision 3 below for why it's safe), and `runWorker(tabId)` is one worker's whole lifetime — claim, process, repeat, until `pending` is exhausted or Stop ends it. `runQueue()` starts `WORKER_TAB_COUNT` (currently a hardcoded `3` — see [Decision 8](#decision-8-adaptive-concurrency--a-feedback-loop-not-a-formula)) of these concurrently via `Promise.all()` and doesn't resolve until every worker's loop has exited on its own.

**Correction, found in live testing immediately after this landed:** `processRoom()` originally navigated each worker tab with `active: false`, specifically to stop several tabs fighting over focus on every room. Live testing showed every room's DOM steps (Select All, Bulk Download, confirm) reporting success, but `chrome.downloads.onDeterminingFilename` never firing for any of them — empty `Download ID`, status permanently stuck at `Success/Attempted` in the report. The actual browser-level download was never registering at all. Hypothesized cause at the time: Chrome's protection against a page silently triggering multiple automatic downloads treating a background-tab-triggered download as the abuse pattern it exists to catch. Fixed by reverting to `active: true`.

**Second correction — the `active` hypothesis above was wrong, or at least not the real cause.** The exact same symptom (every row, empty `Download ID`, no folder ever created) persisted in the next live test *after* the `active: true` revert, with the files confirmed landing directly in the flat Downloads root instead of `Docusign Rooms/<Room Name>/`. That ruled out tab-focus state entirely and pointed at `onDeterminingFilename`'s matching logic itself. The actual cause, found by re-checking markup captured earlier in the project: the download-confirmation form is `<form id="formDownloadDocuments" method="post" target="_blank" ...>` - submitting it opens a **new browsing context** to receive the response, so the resulting `DownloadItem.tabId` belongs to that new (often instantly-closed) tab, never the worker tab that actually triggered it. `STATE.currentRooms[downloadItem.tabId]` was therefore never going to match, and since the listener's gate was `if (!currentRoom || ...) return;`, it bailed out before ever reaching the `looksLikeDocusign`/`looksLikeZip` fallback checks that existed specifically to catch a case like this. Fixed with `findCurrentRoomForDownload()`: try the tab-based lookup first, then fall back to parsing a room ID out of the download's own `referrer`/`url`/`finalUrl` (which points back to `.../rooms/<id>/documents`) and matching that against whichever rooms are currently in flight - correct regardless of which tab Chrome attributes the download to. A `console.warn` was added for the still-unmatched case, logging the download's actual identifying fields, in case the referrer/url fallback doesn't cover every real-world case either.

This is recorded as two separate corrections rather than editing the first one away, in keeping with this document's practice of showing wrong turns rather than erasing them - the `active: true` revert wasn't wrong to try given the evidence at the time (every symptom was consistent with it), it just wasn't the actual root cause once more evidence came in.

**Third correction — the diagnosis was right, the first fix's regex wasn't.** The `console.warn` added above did its job: a real captured `DownloadItem` showed `referrer: ''` (empty - the `target="_blank"` navigation doesn't appear to carry one over) and `url: 'https://rooms.docusign.com/transaction/2977525/documents/download'`. The room ID *was* right there in the URL - just under DocuSign's internal `/transaction/<id>/` path, not `/rooms/<id>/` like the room's own page and `documentsUrl` use. `findCurrentRoomForDownload()`'s regex only matched `rooms`, so it silently missed the ID in every real download despite being right next to it. Fixed by matching either segment: `/\/(?:rooms|transaction)\/(\d+)/i`. Both are confirmed (via this same captured evidence) to carry the identical numeric ID for a given room.

**Fourth correction, once folder routing was actually working — two different rooms with the same name were silently merged into one folder.** With the fix above landed, a live run confirmed 12 attempted downloads across the account but only 11 folders on disk. Row-by-row comparison of the report against room IDs found the cause: two distinct rooms (IDs `2977526` and `2977529`) both happened to be named "Ponchak - Listing", and folder naming was purely `cleanName(roomName)` — no room ID involved — so both targeted `Docusign Rooms/Ponchak - Listing/`, and the second one's files landed inside the first one's folder via `conflictAction: "uniquify"` instead of getting their own. That flag only disambiguates *filenames* within a folder; it was never going to create a second folder for a same-named room. Fixed by adding `computeFolderNames(queue)`, which counts room-name occurrences across the full run's queue once and returns a `roomId -> folderName` map, appending `(roomId)` to the name only for rooms whose name actually collides with another room's in that run — most rooms keep a plain, readable folder name. Computed once per run (in the `DS_START_QUEUE` handler and the startup resume block, both places `STATE.queue` gets set) rather than per-download, so it's O(n) instead of O(n²) at scale. Both places that had been building the folder path directly from `cleanName(roomName)` — `processRoom()`'s `result.downloadedFilename` and the `onDeterminingFilename` listener's actual `suggest({filename, ...})` call — were switched to read from `STATE.folderNames.get(roomId)` instead, so the reported filename in the CSV and the real folder Chrome creates can't drift apart.

**Fifth correction — a worker tab dying mid-run had no recovery, confirmed live by simply closing one.** Raised first as a theoretical gap while assessing whether the extension was actually ready for 10,000 rooms (see [Current Implementation Status](#current-implementation-status)): `ensureWorkerTabs()` only ever checks tab health once, at the very start of `runQueue()` - nothing re-checks afterward. If a worker tab dies mid-run (closed by the user, reclaimed by Chrome, a crash), every subsequent `chrome.tabs.update()` against it in `processRoom()` rejects near-instantly; the resulting error is caught and recorded as a `Failed` result, but `runWorker()`'s loop just claims the next room and tries again - and since `claimNextRoom()` pulls from one queue shared across all workers, a dead-tab worker can claim and instantly-fail through the remaining queue far faster than the healthy workers can do real 20-60s work, potentially mass-marking a large fraction of a big run "Failed" for a reason unrelated to those rooms. Confirmed directly: closing a worker tab mid-run left it permanently dead for the rest of that run, exactly as predicted. Fixed by moving the liveness check into `runWorker()`'s own loop, run before every claim (not after, and not just once) - `chrome.tabs.get(currentTabId)` is checked each iteration; if the tab is gone, a replacement is created (`active: false`, so it doesn't steal focus), `STATE.workerTabIds` is updated in place so the panel's "Worker N" labeling stays stable, and the loop continues with the new tab. If a replacement tab can't even be created, that worker exits cleanly (logged, not thrown) - the other workers keep going with one fewer.

## Decision 3: Concurrency Safety Without Explicit Locks

**Problem:** multiple tabs claiming from one shared queue is a textbook shared-resource race condition. How is that avoided without a mutex?

**Key insight:** a Chrome extension's background service worker is **single-threaded**, and Chrome serializes all incoming `chrome.runtime.sendMessage` calls through its `onMessage` dispatcher — no two tabs' messages are ever processed truly simultaneously. Additionally, tabs are separate execution contexts with no shared memory at all — the queue can *only* live in the one place that's inherently single-threaded. The "lock" is structural, not something that has to be built.

**The one way to reintroduce the race:** an `await` between reading the queue pointer and advancing it creates a gap where JS can switch to a different tab's claim request mid-operation, letting two tabs read the same pointer value before either increments it.

**Decision:** the claim function must read-and-increment the queue pointer as a single synchronous operation with zero `await` inside it. Everything expensive (navigation, clicking, waiting for a download) happens *after* the claim, fully in parallel across tabs — only the trivial, fast part needs to be a protected critical section.

**Implemented exactly as designed.** `claimNextRoom()` in `background.js` is a plain synchronous function - no `async`, no `await` anywhere in its body:

```js
function claimNextRoom() {
  if (STATE.index >= STATE.pending.length) return null;
  const room = STATE.pending[STATE.index];
  STATE.index++;
  return room;
}
```

Everything that actually takes time - `chrome.tabs.update`, waiting for the page to load, messaging the content script, waiting for the download to start - lives in `processRoom()`, called *after* the claim returns, once each worker already has its own room and nothing left to race over.

**A correctness issue this exposed in the persistence design (Decision 6):** the original resume model saved `STATE.index` and resumed by continuing the loop from that saved value - safe under single-tab, where only one room was ever claimed-but-unfinished at a time. Under concurrency, several tabs can each claim a room (advancing `index` past all of them) before any of them finish - if the service worker dies in that window, an index-based resume would treat all of those already-claimed rooms as done and silently skip them, not just fail to retry the one that was in flight. Fixed as part of building this decision, not as an afterthought - see the persistence-model note in [Decision 6](#decision-6-persistence--the-mv3-service-worker-lifecycle).

## Decision 4: Scope Reduction via Date-Range Filtering

**Problem:** not all 10,000 rooms are needed — only a target date range. Filtering during the scan can save both scan time (stop scrolling early) and total processing time (fewer rooms queued).

**A key sub-question that shaped the design:** can "is this room empty" be determined for free (e.g., a visible document count on the room card), or does it require opening the room (the same cost as processing it)? Confirmed: not free. This ruled out an upfront "filter out empty rooms" pass entirely — that check was pushed into the per-room worker logic instead (see Decision 7), where a short, targeted timeout distinguishes "nothing to select" from a real failure, without wasting a full processing cycle on it.

**DOM verification (not assumed):** inspected the actual rendered room list and found a real `<table>` structure with explicit `data-qa` attributes (`room-list-row`, `room-name` with a `title` attribute holding the untruncated name, `room-date`) — far more reliable than the original code's generic link-scraping-plus-DOM-climbing fallback chain.

**Decision:** sort the list oldest-first, then apply a three-way branch while scrolling — skip (before range), collect (inside range), stop entirely (past range, since the list is sorted, everything after is guaranteed out of range too) — with a small consecutive-miss buffer before actually stopping, to tolerate any lazy-load ordering noise.

**Correction (later, once real per-room markup was captured):** "confirmed: not free" was correct for the *scan* phase — the list page genuinely has no per-room document count visible without opening each room. It does not hold for the *processing* phase. Once a room's Documents page is actually open (which the pipeline does for every queued room regardless), `[data-qa="group-name"]` renders its document count directly in text — `"Room Docs (0)"` for an empty room, `"Room Docs (11)"` for a room with 11 documents — present whether the room is empty or not. The original per-room code never checked this; it wasted a full 45-second timeout waiting for the Select All checkbox on every empty room, since that checkbox never renders at all when there's nothing to select. Fixed in `processCurrentRoom()`: wait on `group-name` instead (present in both states) and short-circuit immediately if the parsed count is `0`, before ever attempting Select All. Open caveat, not yet verified either way: this reads only the *first* `group-name` element on the page; a room with multiple document folders/groups would need the counts summed, and no multi-folder room has been inspected yet to confirm whether that's a real scenario in this account.

**Critical correction, this decision's central assumption was unverified until now:** the entire skip/collect/stop algorithm above depends on the list being sorted oldest-first. That was never actually enforced or checked at runtime — only assumed, based on one earlier snapshot that happened to show `"Created (Oldest)"` selected. A later markup capture of the same list showed the sort dropdown reading **`"Created (Newest)"`** instead, with rooms rendering newest-to-oldest. Under that ordering, the "stop once several rooms are found past `SCAN_DATE_END`" logic breaks completely: with `SCAN_DATE_END` far in the past relative to real (2026-dated) rooms, *every* room on initial page load is already "past the end date," tripping the stop condition on the very first tick, before scrolling even once — a silent, empty-result failure, not a crash. Since the sort direction is apparently not a fixed account property (it differed between two observed sessions), it cannot be assumed at all — it has to be checked every time. Fixed with a new `getSortLabel()` function reading `[data-qa="filter-sort-drop-down-button"] span[title]`, called at the top of `autoScrollAndCollectRooms()`: if it doesn't read exactly `"Created (Oldest)"`, the function stops immediately, reports the problem through `updateStatus`, and returns an empty array rather than proceeding on a false assumption. This is the same honesty principle applied earlier to empty-room detection ("likely empty" instead of a confident wrong assertion) — a loud, clear failure instead of a silent wrong one.

## Decision 5: Batch Scan-Then-Process vs. Streaming (a reversed decision)

**Initial idea:** overlap scanning and downloading — start feeding the queue as rooms are discovered, rather than waiting for the full scroll to finish, to reclaim the scan phase's wall-clock time.

**Why it was reversed:** once "resume after a long pause or crash" became a hard requirement, the streaming approach exposed a correctness problem — the Rooms list is *live* data, and if it's sorted by recent activity, any activity during a partial scan can reorder rooms underneath an in-progress scan, making "diff against a partial checkpoint" unreliable. Meanwhile, the time saved by overlapping (scanning is minutes; processing is hours) was a small fraction of total runtime.

**Decision:** scan once, in full, and save the result as a fixed, immutable list before any processing begins. Resumability is then trivial — track completed indices against a list that never changes — instead of needing reconciliation logic against a moving target. This is a case of **choosing correctness and simplicity over a marginal performance gain**, once the real requirements were fully known.

## Decision 6: Persistence & the MV3 Service Worker Lifecycle

**Problem discovered, not assumed upfront:** Manifest V3 background service workers are deliberately ephemeral — Chrome can terminate and restart them independent of any user action, resetting all in-memory state. This isn't a rare edge case for a job running many hours; it's close to guaranteed to happen at least once.

**Decision:** persist the scanned room list (once), the results/status per room (incrementally), and the queue position to `chrome.storage.local` — not just at the end, but as the run progresses — and have the service worker check for an in-progress job on startup before assuming a fresh run.

**Implemented, single-tab era.** `background.js` snapshots `{queue, index, results, paused, startedAt}` under one `chrome.storage.local` key (`persistJob()`), called at every point that changes resumable state: run start, after each room's result is recorded (success, failure, or the page-didn't-load case), and on pause/resume. (This field list is the original, single-tab version - the third correction below changes it once concurrency lands; `persistJob()` today saves only `{queue, results, paused, startedAt}`, no `index`.) Not called from `broadcastStatus()`, which fires roughly once a second while paused — that would be a lot of redundant writes for no benefit. A top-level async block at the bottom of `background.js` runs on every service-worker startup, checks for a job that was still `running` when memory was lost, and calls `runQueue()` directly to pick it back up.

One subtlety this exposed: `runQueue()`'s `for` loop used to force `STATE.index = 0` in its own initializer, which would have silently turned every resume into a full restart. Fixed by removing the initializer entirely (`for (; STATE.index < STATE.queue.length; STATE.index++)`) and requiring each call site to set `STATE.index` itself first — `DS_START_QUEUE` sets it to `0` for a genuinely new run, the startup resume block sets it to whatever was persisted. Similarly, `STATE.startedAt` is only set inside `runQueue()` if it's currently falsy, so a resumed run keeps its real original start time instead of the elapsed-time display silently resetting; `DS_START_QUEUE` explicitly nulls it first so a truly new run doesn't inherit a stale timestamp left over from an earlier run in the same service-worker lifetime.

Two limitations, both accepted rather than solved here: (1) there's no periodic self-wake (`chrome.alarms`) — resume only fires the next time *something* wakes the service worker: originally the panel's own status check whenever the user reopened a Docusign Rooms tab (true back when the panel auto-injected into every such page); since [Decision 24](#decision-24-moving-the-panel-out-of-the-page--a-detached-window) moved the panel to a standalone window that only opens on a toolbar click, it's more often a content script's `DS_ROOM_PAGE_INFO` message firing automatically on any room page. Either way: not instant on crash. (2) if the crash lands mid-room — after the download's already been clicked but before that room's result gets persisted — the resumed run reprocesses that same room from the top. `conflictAction: "uniquify"` on downloads means the worst case is a duplicate ZIP in its own folder, not overwritten or corrupted data, so this was judged an acceptable tradeoff against the complexity of tracking finer-grained per-room progress (e.g. "selected but not yet confirmed downloaded").

**A second, complementary resume path added afterward: CSV upload.** `chrome.storage.local` only survives inside the same browser profile — it's gone if the user clears browser data, reinstalls the extension, or moves to a different machine. The download report CSV, by contrast, is a real file already sitting in Downloads, independent of anything browser-internal. The panel's new "Upload CSV to Run/Resume" button reads that file back in (via a small hand-written `parseCsv()` in `content/utils.js`, since there's no CSV library and the format is simple enough not to need one), skips the live scan entirely since the room list is already known, and — if the CSV has a `Status` column, meaning it's a download report rather than a plain scan list — separates rows already marked `Downloaded` from everything else before queueing. This isn't a replacement for the `chrome.storage.local` path above; it's a fallback for exactly the cases that one can't cover, plus it doubles as a way to hand-edit and split a room list into smaller batches.

**Correction, found immediately by trying to actually use the feature above:** `createReport()` built its CSV from `STATE.results`, which only gets an entry once a room is *processed* — so a run stopped partway through produced a report covering only the rooms it had reached. Everything still sitting in the queue was simply absent from the file, not marked as pending. Re-uploading that report therefore could only ever resume rooms already touched, never the untouched remainder — which broke the CSV-upload resume path for precisely the scenario it exists for (an interrupted run). Fixed by having `createReport()` walk `STATE.queue` (the complete original list, restored in full on a resumed run too) instead of `STATE.results`, looking up each room's outcome by `roomId` and writing `Status: "Waiting"` for anything without one.

**Second correction, made alongside adding concurrency:** the CSV-upload path originally just *dropped* rows already marked `Downloaded` and queued the rest — which meant the resumed run's own new report only covered whatever it reprocessed, silently losing the record of everything that had already succeeded. `roomsFromCsvRows()` in `content.js` was replaced with `parseUploadedCsv()`, which splits parsed rows into `rooms` (still need work) and `priorResults` (already-`Downloaded`, carried over with their full original result data - reason, filename, download ID, timestamp). `DS_START_QUEUE` accepts this as an optional `priorResults` field and seeds `STATE.results` with it directly, so the resumed run's report - and its live progress counter - shows the true complete picture instead of restarting the count from zero against a shrunk total.

**Third correction, made alongside adding concurrency - the persistence model itself changed:** the original resume logic persisted `STATE.index` and resumed by continuing from that saved value, which was safe under single-tab (only one room was ever claimed-but-unfinished at a time, so a crash mid-room just meant reprocessing that one room - see the second limitation noted above). Once multiple tabs can claim concurrently, `index` can already be advanced past several rooms that were claimed but never finished at the moment of a crash - resuming from that saved index would treat all of them as done and silently drop them, not retry them, which is a worse failure mode than the single-tab version's "maybe a duplicate ZIP." Fixed by no longer persisting `index`/`pending` at all: `persistJob()` now saves only `queue` (the full list) and `results` (what's actually finished), and the startup resume block rebuilds `pending` as `queue` filtered down to rooms with no entry in `results` - "claimed but never finished" and "never reached at all" both naturally fall into that filter and get retried, no bookkeeping needed to tell them apart. See [Decision 3](#decision-3-concurrency-safety-without-explicit-locks) for where this was actually caught.

**Note on build order:** the [Final Build Plan](#final-build-plan-deliberately-risk-ordered) below originally sequenced persistence as step 4, after single-tab processing but before the multi-tab worker pool. In practice it was built and shipped ahead of the multi-tab step it was ordered after, once it became clear a crash losing an hours-long single-tab run was already a real, live problem worth fixing on its own — see [Current Implementation Status](#current-implementation-status) for where each step actually stands.

## Decision 7: Replacing Fixed Delays with Real Signals

**Problem:** the original ~11.5 seconds of fixed sleeps per room were pure guesswork, and guesswork scales badly across 10,000 iterations.

**Insight:** `chrome.downloads.onDeterminingFilename` (already used for the folder-renaming trick) fires the moment Chrome registers a new download — a real, already-available signal for "this room's download has started," rather than something to guess at with a timer. Navigating the tab away immediately after is safe, because Chrome's download manager operates independently of the originating tab once a download is underway — an assumption the *original* single-tab design already depended on implicitly.

**Two distinct wait categories identified:**
- Page becoming interactive after navigation — legitimately network-bound, needs a long timeout.
- A button appearing after a client-side click (e.g., the download button appearing after Select All) — a fast UI reaction, not a network wait, and doubles as the fast signal for "this room has nothing to select" if it *doesn't* appear quickly.

**Decision:** replace every fixed sleep with either a real event (with a timeout fallback, so a genuine failure doesn't hang a worker forever) or a short poll sized to what's actually being waited for.

**Critical correction, found during live single-room testing:** replacing the fixed `sleep(2500)` before the bulk-Download-button check with a real poll (per the decision above) did not fix the "Bulk download button was not found" failure every live room was hitting — because the poll was never the problem. The selector (`button[data-qa="Download"][data-dd-action-name="Bulk Action - Download"]`) was already correct, confirmed against captured markup. Diagnostic `console.log`s added to `selectAllDocuments()` revealed the real cause one layer down: `checkbox.click()` on the Select All input left `checkbox.checked` at `false` and left every `input[data-qa="document-checkbox"]` unchecked — the click was having *no effect at all* on the page's real state, so the bulk-actions toolbar (which only renders once something is selected) never appeared, and the wait was correctly timing out on a button that could genuinely never show up. Root cause: the site's custom checkbox component cancels the native click's default toggle unless the event is a real, trusted user click — `.click()` in a content script produces a synthetic event (`isTrusted: false`), which the page's own handler appears to reject silently (no error, no exception — the toggle is just reverted). This is also where `selectAllDocuments()` itself was quietly wrong independent of the trust issue: it returned `true` unconditionally the moment it found the checkbox element, never verifying the click actually changed anything — a case of the same "confident wrong assertion" failure mode this project had already corrected once for empty-room detection (Decision 4's earlier correction) and once for sort order, now showing up a third time in a different form. Fixed by making `selectAllDocuments()` `async` and self-verifying: it tries the native `checkbox.click()`, then a click on the associated `<label data-qa="select-all-docs-label">`, then a manually dispatched `MouseEvent`, checking after *each* attempt whether any real document checkbox actually shows as checked in the DOM — and only returns `true` once that's observably true, rather than assuming success from the absence of a thrown error.

**Follow-up, confirmed via console logging in live runs:** the native `checkbox.click()` attempt failed identically on two separate rooms, while `label.click()` succeeded both times — the label and input are markup siblings (not label-wrapping-input), and the page's actual click handler is bound to the `<label>`, not the `<input>`, which is why a click dispatched straight at the input never reached it. `selectAllDocuments()` was trimmed to try `label.click()` first (the manually dispatched `MouseEvent` remains only as a fallback for any room where the label element isn't found), removing a guaranteed-wasted ~400ms per room. Separately, the three fixed sleeps this Decision's original text flagged as guesswork were replaced in the same pass: the pre-processing `sleep(3500)` (redundant — `processCurrentRoom()` already polls for readiness itself) dropped to a small `sleep(500)` listener-attachment buffer; the post-processing `sleep(4500)` replaced with `waitForDownloadStart()`, a real poll against `chrome.downloads.onDeterminingFilename`'s output instead of a flat guess; the inter-room `sleep(2000)` dropped to `sleep(500)`. Confirmed faster in live testing. This closes out the "Real event-based waits" item that was sitting in the Planned list.

## Decision 8: Adaptive Concurrency — A Feedback Loop, Not a Formula

**Problem:** how many parallel tabs should run, and can that number be suggested automatically?

**Key realization:** average time-per-room can't be known before any rooms have actually completed — it depends on document counts, server load, and network conditions, none of which are predictable from the room count alone. This ruled out a one-shot calculation.

**Decision:** start conservative, measure real completion times from the first batch of processed rooms (made materially more accurate by Decision 7 removing artificial delay from that measurement), and use the *measured* rate to project remaining time and suggest — not silently apply — a concurrency change within fixed min/max bounds. The bounds themselves are set by practical limits (memory/CPU, avoiding load patterns that look like abuse to DocuSign's servers), not derived mathematically.

**Partially implemented, later, out of build order:** [Decision 17](#decision-17-user-configurable-worker-tab-count-bounded-not-unlimited) landed the bounds half of this plan (1-8, `clampWorkerTabCount()`) and manual user control via the panel - ahead of the *measured, suggested* half described above, which is still not built. The bounds' specific values (1-8) came from the same practical-limits reasoning as planned here, not from measured timing data, since that data still doesn't exist yet for this purpose.

## Decision 9: Code Organization — Why Not OOP

**Instinct considered:** convert the growing codebase to class-based OOP for better separation of concerns.

**The concrete, mechanical reason against it:** background.js, each tab's content.js instance, and the panel UI are separate JS realms connected only by `chrome.runtime.sendMessage`, which serializes all data through JSON — stripping any class instance down to a plain object with no methods on the receiving end. A class meant to represent "a worker and its behavior" can't actually span the boundary where the interesting behavior happens, because the platform itself cuts that object in half on every message. Additionally, the design has exactly one queue and one shared state object — OOP's main value (many independent instances with encapsulated state) doesn't apply to a singleton.

**Decision:** organize by splitting into focused files by concern (scan/filter logic, queue/claim logic, persistence, filename routing) using real ES modules in the MV3 service worker (`"type": "module"`, no bundler needed) and multiple shared-scope content script files — solving the actual "keep functions separated" need without fighting the platform's message-passing model.

**Correction, once `background.js` was actually built — the ES-module half of this plan didn't happen.** `manifest.json`'s `background` block never declares `"type": "module"`; `background.js` pulls in `content/utils.js` via `importScripts()`, the classic-script mechanism, not an ES `import`. This is deliberate, not an oversight: `content/utils.js` is written as plain global function declarations specifically so the identical file works unmodified as both a content script (loaded via `manifest.json`'s `content_scripts` array) and inside the service worker (loaded via `importScripts()`) — switching to real ES modules would have meant either two copies of that file or a build step to reconcile the two loading mechanisms, for a shared-utilities file with barely a hundred lines. `background.js` itself was also never split into separate scan/filter, queue/claim, persistence, and filename-routing files as planned above — `claimNextRoom()`, `processRoom()`, `persistJob()`, and the `onDeterminingFilename` listener all still live in the one file, organized by section rather than by separate loaded modules. The "split by concern" half of this decision landed only on the content-script side (`content/utils.js` / `content/scan.js` / `content/room.js`, see Decision 10) — `background.js` staying a single file hasn't caused a real problem yet, so splitting it further hasn't been worth doing for its own sake.

## Final Build Plan (Deliberately Risk-Ordered)

Rather than building all of the above simultaneously, the plan builds and tests in increasing order of risk, so a bug is always isolated to the one new layer just added:

1. **Scanning + filtering + list export**, tested alone — no download logic touched yet.
2. **Single-tab processing with event-driven waits** replacing fixed sleeps — verify speed and correct empty-room detection before adding concurrency.
3. **Full per-room lifecycle status + panel UI** (queued → in progress → done/failed/empty), still single tab.
4. **Persistence and resume**, tested by deliberately killing/reloading the extension mid-run.
5. **The worker-tab pool** (claim-based queue, per-tab filename routing) — introduced last, once everything underneath it is proven solid on one tab.
6. **Min/max bounds + adaptive concurrency suggestion**, which depends on real timing data from step 5.

A small, narrow-date-range dry run (a few dozen rooms) is run through the entire pipeline before trusting it against the full 10,000-room set.

## Build Step 1: Scanning + Filtering + List Export (Complete)

This section records Step 1's actual implementation decisions as they happened, separately from the pre-implementation planning above — kept in its original, in-the-moment voice (including the "in progress" framing of the notes within it) rather than rewritten in hindsight, since that's an honest record of the order things were actually found and fixed. ### Decision 10: Splitting content.js by Dependency, Not by File History

**Problem:** `content.js` originally held every scan/scroll/utility/room-page function in one file behind a single IIFE. Once real logic (date filtering, later a worker-tab pool) started landing, that made it hard to see which functions were actually related to which concern.

**Constraint carried over from the planning phase:** content scripts aren't real ES modules — every file listed in `manifest.json`'s `content_scripts` array shares one execution scope, in load order. No IIFE wrapper per file (it would hide top-level declarations from the other files); the only thing enforcing correctness is getting the array order right.

**Decision:** three files, grouped by actual call relationships rather than by where the code originally sat in the single file:
- `content/utils.js` — generic string/URL helpers with no DOM/page context (`sleep`, `cleanName`, `normalizeText`, `getRoomIdFromUrl`, `roomUrlToDocumentsUrl`). The deciding signal for what belongs here: functions called from *more than one* of the other groups (`normalizeText` and `cleanName` are each used by both the scan flow and the room-page flow) — a shared dependency shouldn't be owned by either consumer.
- `content/scan.js` — the Rooms-*list*-page flow: `getScrollContainer`, `getRoomCardsAndLinks`, `autoScrollAndCollectRooms`.
- `content/room.js` — Rooms-*page* concerns, currently just `getRoomNameFromPage`. Named ahead of need: the original plan was for Build Step 2 to move `clickElement`, `selectAllDocuments`, `findBulkDownloadButton`, `findFinalDownloadButton`, `waitForSelector`, and `processCurrentRoom` out of `content.js` into this same file later, since they're the same category of concern — avoiding a rename/re-split later for one function that would otherwise sit alone. **That move never happened, by deliberate choice, not oversight:** `content/room.js`'s own header comment records the decision explicitly — those functions are a pure reorganization with no functional benefit, so time went to the roadmap items that actually change behavior (date-range filtering, concurrency, folder-uniqueness) instead. They still live in `content.js` today.

Load order requirement: `utils.js` must load before `scan.js` and `room.js` (both depend on it); those two don't depend on each other, so their relative order doesn't matter; `content.js` still loads last.

### Decision 11: Replacing Two DOM Heuristics with DevTools-Confirmed Behavior

**Problem:** two functions in the original code (`getRoomCardsAndLinks` and `findBestScrollContainer`) were built on *guesses about DOM shape* rather than confirmed structure — the same category of fragility already flagged conceptually in Decision 4, now actually being resolved during implementation.

**`getRoomCardsAndLinks`:** the original climbed up from any `a[href]` via `.closest()` through a fallback chain of ancestor types and guessed the room name from the first line of the row's rendered text. Verified against the live page's actual markup instead: a real `<table>` with explicit `data-qa` attributes — `tr[data-qa="room-list-row"]` for each row, `strong[data-qa="room-name"]` (its `title` attribute holds the untruncated name; the extension previously risked failing on CSS-truncated names by reading rendered text instead), and `strong[data-qa="room-date"]`. Rewritten to query these directly. This also adds a `createdDate` field to each room record, which the still-pending date-range filter (Decision 4) depends on.

**`findBestScrollContainer`:** the original queried every `div`, `main`, `section`, `body`, and `html` on the page and picked whichever had the largest `scrollHeight - clientHeight`, on the theory that the room list was probably "the tallest scrollable thing." Verified instead of assumed: selected the Rooms-list container and the table's wrapper in DevTools and ran `getComputedStyle(el).overflowY` against each, plus `document.documentElement` and `document.body` directly. All four returned `"visible"` — confirming this page has **no internally-scrolling wrapper at all**; it's plain document/page scrolling. Replaced the entire heuristic with a one-line `getScrollContainer()` returning `document.scrollingElement || document.documentElement`, and removed the `try/catch` fallback around the scroll call in `autoScrollAndCollectRooms` — it existed only to hedge against the old heuristic possibly returning an element without a working `.scrollTo`, which is no longer a reachable failure mode now that the returned element is guaranteed to be the document's own scrolling element.

**Caveat recorded deliberately, not glossed over:** this is confirmed for the current page rendering at the row counts tested. If DocuSign later switches to a virtualized/windowed list for very long lists (rendering only on-screen rows inside a scrolling wrapper, a common technique at this kind of scale), this assumption would need re-verifying — the symptom to watch for is the scanned room count plateauing while more rooms are known to exist.

**Status (superseded below):** at this point Step 1 had the file split and the selector/scroll fixes in place, with the date-range logic, CSV export, and manifest wiring still outstanding. The date-range skip/collect/stop logic (Decision 4's design) was subsequently implemented by hand — including catching and fixing a real bug during review, where the streak counter was tripping on rooms that were merely too *early* rather than only rooms past the end date, which would have silently returned zero results on any account whose earliest rooms predate the configured start date.

### Decision 12: Closing Out Build Step 1 Under Time Pressure — CSV Export, Manifest Wiring

**Problem:** with a real deadline approaching, finishing the remaining Build Step 1 items by hand (CSV export of the scanned list, the manifest fix) would cost more time than was available, but abandoning the guided, human-typed approach silently would misrepresent how the codebase was actually built (see the process note below).

**Decision:** made explicitly, not by default — asked directly which of three modes to use (AI writes it, a boilerplate/logic hybrid split, or continuing fully guided at a faster pace) and went with full AI implementation for the remainder of Build Step 1, under human review, given the time constraint. This is recorded as a decision with a real tradeoff, not a neutral implementation detail.

**What this covered:**
- Fixed a bug introduced while manually wiring `manifest.json`'s `content_scripts` array by hand: the paths were written as `"utils.js"`, `"scan.js"`, `"room.js"` instead of `"content/utils.js"`, `"content/scan.js"`, `"content/room.js"` — the files live in the `content/` subfolder, so Chrome would have failed to load them.
- Added CSV export for the scanned/filtered room list. Content scripts have no access to `chrome.downloads` (confirmed in Decision 4's era of planning) — only the background service worker does — so this required a new message type, `DS_EXPORT_SCAN_LIST`, sent from `content.js` to `background.js`, which builds the CSV (reusing the existing `csvEscape`/`nowStamp` helpers already used by `createReport()`) and saves it to `Docusign Rooms/_Scan Lists/`.
- Added a dedicated "Scan & Export List (CSV)" button to the panel, deliberately kept **separate** from the existing Start button rather than merged into it — preserving the Build Step 1 philosophy of testing scanning/filtering/export in isolation, with zero risk to the already-working single-tab download flow (`DS_START_QUEUE` → `runQueue`), which needed no changes at all.

**Correction to the paragraph above, once real room-page markup was captured:** `selectAllDocuments()` did need a change after all. The original function only located the Select All *label's text span* (`[data-qa="select-all-docs-label-text"]`) and then guessed at a clickable ancestor via a fallback chain (`label.closest("label") || label.closest("[class*='select']") || label.parentElement?.parentElement?.parentElement || ...`) — the same category of DOM-shape guesswork already replaced with confirmed selectors in Decision 11. Verified against the room Documents page's actual markup: the checkbox itself carries its own `data-qa="select-all-docs"` attribute, directly clickable with no ancestor-climbing needed at all. Replaced the ~25-line guess-chain with a direct `document.querySelector('input[data-qa="select-all-docs"]')` lookup.

**Second correction:** the room's group header, `[data-qa="group-name"]`, was also captured in both an empty room (`"Room Docs (0)"`) and a populated one (`"Room Docs (11)"`) — present in *both* states, unlike the Select All checkbox, which never renders at all when a room is empty. This directly overturns Decision 4's "confirmed: not free" conclusion, but only for the *processing* phase, not the scan phase — the room list still has no visible document count, so scanning still can't skip empty rooms upfront. What it does fix: the original `processCurrentRoom()` waited on the Select All checkbox specifically, which meant every empty room burned the full 45-second timeout before failing. Fixed to wait on `group-name` instead (present either way) and short-circuit immediately if the parsed count is `0`. Caveat, not yet verified: this reads only the first `group-name` element on the page; a room with multiple document folders would need the counts summed, and no such room has been inspected yet.

**Third correction, closing out the last guesswork in single-room processing:** real markup for the post-Download confirmation modal was captured. Two findings: (1) its confirm button, `<button class="btn-action" type="submit">Download</button>` inside `<form id="formDownloadDocuments">`, carries no `data-qa` at all — unusual for this app, a sign this particular modal is an older jQuery-driven component (`ctv.documents.initDownload(...)`) bolted onto the otherwise React-based UI. The original `findFinalDownloadButton()` worked around the missing `data-qa` by scanning every visible button/link on the page for text matching "download" — functional by coincidence, fragile in principle, since any other visible "download"-labeled control anywhere on the page would collide with it. Replaced with a selector scoped to the form's own stable `id`: `#formDownloadDocuments button[type="submit"]`. (2) The original code also did `await sleep(3500)` after clicking Bulk Download, gambling the modal would be open by then, before ever checking for it — the same fixed-delay guesswork Decision 7 eliminated elsewhere. Replaced with `waitForSelector('#formDownloadDocuments button[type="submit"]', 10000)`, resolving the instant the modal actually appears instead of always waiting the full guessed amount. `findBulkDownloadButton()` needed no change — its existing selector matched the captured markup exactly, the one place in this whole pass where prior guesswork happened to already be correct.

**Fourth correction:** the full room detail page (Details tab, not just Documents) was captured, revealing `<strong data-qa="room-name">` as the room's own confirmed name element — the same fix pattern applied to `getRoomNameFromPage()`, replacing a 6-selector guessing chain (`[data-qa*='room-name']`, `[data-qa*='room-title']`, `h1`, three class-name heuristics) plus a `document.title`-scrubbing fallback with one direct, confirmed lookup. This had a side effect worth recording: `normalizeText()` in `content/utils.js` (documented in Decision 10 as shared by both the scan and room-page flows) was only ever called from two places — this function, and the text-matching branch of `findFinalDownloadButton()` removed in the correction above. With both callers gone, it became genuinely dead code and was deleted rather than left in `utils.js` unused. Decision 10's original text describing it as a shared dependency is left as-written above (an accurate record of the reasoning *at the time*); this note is the correction, not a rewrite of that history.

## Decision 13: Automated Testing Strategy

**Problem:** every fix in this project so far had been verified by live testing against a real DocuSign account — real, but slow, and it can't catch a regression until someone happens to click through the affected path again. Worth automating what can be, without pretending DOM automation and timing-dependent browser behavior can be unit tested the same way.

**Constraint discovered before any test could be written:** this machine had no Node.js, npm, or Homebrew installed at all — none of the usual JS testing tooling existed yet. Installing Node's official `.pkg` from nodejs.org needed `sudo`, which needs an interactive password prompt this environment's shell doesn't have; worked around with `osascript -e '... with administrator privileges'`, which triggers macOS's native GUI credential dialog instead of a terminal prompt. Installed: Node.js v24.19.0 (the current LTS release, "Krypton").

**What's actually testable vs. not:** `content/utils.js`'s string/URL/CSV helpers (`cleanName`, `getRoomIdFromUrl`, `roomUrlToDocumentsUrl`, `parseCsv`) and several of `background.js`'s functions (`computeFolderNames`, `csvEscape`, `nowStamp`, `claimNextRoom`, `findCurrentRoomForDownload`) are pure or close to it — no real DOM, no live `chrome.*` calls, no timing dependence. Everything else - `content.js`'s DOM-scraping and click-simulation logic, `background.js`'s tab orchestration and download-waiting - is fundamentally about *driving a real browser against a real page*, which a unit test can't meaningfully fake without testing the fake instead of the real risk. That code stays covered by live testing against the real account, as it always has been - automated testing here targets what changed this session for a reason (the pure-logic bugs: `computeFolderNames`' collision handling, `findCurrentRoomForDownload`'s URL matching), not blanket coverage for its own sake.

**Update:** this line was originally accurate but became a trap for later features - `content.js`'s per-feature helper functions (date-range labeling, worker-tab-count validation, activity-log formatting) got written *inside* `content.js`'s closure by default, since that's where they were used, silently falling into the "untestable DOM-heavy code" bucket even though they touched no DOM at all. [Decision 19](#decision-19-pre-real-run-review-pass) caught and fixed this - the actual boundary was never "which file," it was "does this function touch the DOM," and several functions had been on the wrong side of that line purely by accident of where they were first written.

**Why Node's built-in `node:test` instead of a framework (Jest/Vitest/Mocha):** zero dependencies to install, audit, or update — genuinely appropriate for a project this size, where the entire test surface is a handful of pure functions, not a reason to reach for tooling built for much larger test suites. `node --test` (glob: `node --test tests/**/*.test.js` — `node --test tests/` alone doesn't reliably recurse) needs no `node_modules` at all.

**The real obstacle: these files were never written to be `require()`-able.** `content/utils.js` and `background.js` are plain global function declarations by design (see `content/utils.js`'s own header comment and [Decision 9](#decision-9-code-organization--why-not-oop)) - the right shape for a content script / `importScripts()`-loaded service worker, but `module` and `require` don't exist in either of those real runtimes, and conversely `background.js`'s literal `importScripts("content/utils.js")` call throws immediately under Node (`importScripts` doesn't exist there either). Solved with a guard at each boundary rather than restructuring the files: `content/utils.js` gets an export tail — `if (typeof module !== "undefined" && module.exports) { module.exports = {...}; Object.assign(globalThis, module.exports); }` — that's a no-op in the browser (`module` is never defined there) and, under Node, both exports the functions *and* attaches them to `globalThis`, reproducing the same shared-global-scope behavior the browser gives content scripts for free via `manifest.json`'s load order. `background.js`'s `importScripts` call became `if (typeof importScripts === "function") { importScripts(...) } else if (typeof require === "function") { require("./content/utils.js") }`, and it gets its own export tail exposing `{ STATE, computeFolderNames, csvEscape, nowStamp, claimNextRoom, findCurrentRoomForDownload }`. None of this changes what ships to Chrome — both branches are permanently unreachable in that environment, confirmed by the fact the guards are already exactly how `content/utils.js` was written before any of this: the file already needed to detect "am I being loaded as a content script or via `importScripts()`" for reasons unrelated to testing (see its header comment) - this is the same category of guard, one more case added to it.

**`background.js`'s top-level side effects** (`chrome.runtime.onMessage.addListener(...)`, the two `chrome.downloads.*` listener registrations, and the startup-resume IIFE that calls `chrome.storage.local.get`) all run immediately the moment the file is loaded — including under `require()`. `tests/helpers/chrome-stub.js` provides a minimal fake `chrome` object (no-op `addListener`s, `storage.local.get` resolving to `{}` so the resume IIFE finds nothing and returns immediately) assigned to `global.chrome` before each `require()` - just enough that loading the file doesn't throw, not a behavioral mock of Chrome itself. `tests/helpers/load-background.js` clears both `background.js`'s and `content/utils.js`'s entries from Node's `require.cache` on every call, so each test gets a fresh, isolated `STATE` object instead of leaking mutations across tests through the module cache (`STATE` is exported by reference, and `claimNextRoom`/`findCurrentRoomForDownload` both read and write it directly rather than taking it as a parameter — correct for production, where there's exactly one `STATE`, but it means tests must reset it explicitly rather than relying on pure-function isolation).

**What's actually covered**, 24 tests across `tests/utils.test.js` and `tests/background.test.js`: `cleanName`'s character-stripping/whitespace-collapsing/length-capping/empty-fallback behavior; `getRoomIdFromUrl` and `roomUrlToDocumentsUrl`'s regex matching including the non-matching case; `parseCsv`'s quoted-field/embedded-comma/doubled-quote/CRLF handling; `csvEscape`'s null/undefined handling; `nowStamp`'s format; `claimNextRoom`'s ordering and its refusal to advance past `pending.length`; and, as direct regression tests for two of this session's real live-testing bugs, `computeFolderNames` given two same-named-but-different-ID rooms (the "Ponchak - Listing" incident, [Decision 2](#decision-2-parallelism-model--work-queue-not-divide-and-conquer)'s fourth correction) and `findCurrentRoomForDownload` given a `DownloadItem` shaped like the real captured one that exposed the `target="_blank"`/`/transaction/` bug (the same decision's second and third corrections). Run via `npm test` (or `node --test tests/**/*.test.js`) from inside `Docusign rooms download/`.

## Decision 14: Per-Worker-Tab Status Breakdown

**Problem:** the panel's live status, since the worker pool landed ([Decision 2](#decision-2-parallelism-model--work-queue-not-divide-and-conquer)), showed only an aggregate count and a flat list of room names ("Running: 3 active (Room A, Room B, Room C)") - real information, but not which *tab* had which room, or how long it had been stuck there, which matters once something is actually running slow and you want to know if it's one straggling worker or the whole pool.

**What was missing to build this:** `broadcastStatus()` and the `DS_GET_STATUS` handler already sent `currentRooms` (an array built from `STATE.currentRooms`, keyed internally by tab ID but flattened to an array on the wire) - tab identity was there in the *keys* of the source object but got dropped the moment `Object.values()` flattened it for the message. Worker *identity* (a stable "Worker 1/2/3" label, not Chrome's own meaningless-to-a-user tab ID) wasn't sent at all - `STATE.workerTabIds` existed only inside `background.js`.

**Decision:** send both pieces of missing information rather than reconstructing them client-side from something else. `processRoom()`'s `STATE.currentRooms[tabId] = {...}` now includes `tabId` (redundant with the object's own key, but the array shape sent over the wire needs it explicitly once flattened) and `claimedAt` (an ISO timestamp, for computing elapsed time). Both `broadcastStatus()` and `DS_GET_STATUS` now also send `workerTabIds: STATE.workerTabIds` - the tab-creation-order array already used internally, now exposed so the panel can label rows "Worker 1", "Worker 2", etc. consistently across updates instead of by raw tab ID.

**Panel side (`content.js`):** two new render functions, both driven off the same status payload both existing call sites (`DS_BULK_STATUS` listener and the initial `DS_GET_STATUS` fetch on panel load) already received - `renderWorkers(s)` builds one row per entry in `s.workerTabIds`, looking up that tab's current room (if any) in a `Map` built from `s.currentRooms`, and showing "Worker N: idle" for a tab between rooms or with no work left; `renderBreakdown(s)` tallies `s.results` by `.status` (`Downloaded`, `Failed`, `Download Error`, the transient `Success/Attempted`) plus a derived `Waiting` count (`total - results.length`) for rooms not yet reached - a result-by-outcome summary that previously required opening the final CSV report to see.

**Built with DOM APIs (`createElement`/`.textContent`), not `innerHTML`, deliberately:** room names reaching the panel have already been through `cleanName()` (see `background.js`'s `DS_ROOM_PAGE_INFO` handler), which happens to strip `<`/`>` among other characters - but that's a filename-safety guarantee, not a security one, and leaning on it as the only defense against a room name breaking out of an `innerHTML` string would be fragile against `cleanName()` ever changing for unrelated filename reasons. `.textContent` per row costs nothing extra here and doesn't depend on that staying true.

**Elapsed time is recomputed from `claimedAt` on every incoming status message, not a live client-side ticking clock.** `broadcastStatus()` already fires reasonably often while a run is active (every room claim, every pause-loop tick, every completion) - a `setInterval` in the panel for second-by-second accuracy would be real added complexity (a timer to create, clear on panel teardown, and reason about across the run's start/stop/pause transitions) for a gain barely visible to a person glancing at the panel.

**Scope, recorded explicitly rather than left ambiguous:** this is a per-*worker* breakdown (bounded by `WORKER_TAB_COUNT`, currently 3 rows), not the full per-*room* queued/in-progress/done/failed/empty breakdown originally scoped for [Build Step 3](#final-build-plan-deliberately-risk-ordered) - see the [Current Implementation Status](#current-implementation-status) table for why a full 10,000-row version is being treated as a separate, not-yet-scoped feature rather than a small extension of this one.

## Decision 15: Worker/Service-Worker Lifecycle Event Log

**Problem:** a live persistence test - deliberately terminating the service worker via `chrome://serviceworker-internals` (the reliable way to do this; the "service worker" link on `chrome://extensions` only opens an inspector, it doesn't kill anything) and then reopening a Rooms tab to see if the run picked back up - reported "it did not resume." With no visibility into *why*, the only options were re-guessing at the same three hypotheses [Decision 6](#decision-6-persistence--the-mv3-service-worker-lifecycle) already reasoned through (no persisted job, nothing pending, or a race with `STATE.running`) with no way to tell which one actually happened - and STATE itself, the only place that information could have lived, gets wiped by the very event (a service worker restart) most worth investigating.

**Decision:** add a lightweight lifecycle event log - not a general-purpose logging framework, specifically the handful of events needed to answer "did the service worker restart, did resume even attempt to run, and if not, why not" plus the worker-tab equivalent from [Decision 2](#decision-2-parallelism-model--work-queue-not-divide-and-conquer)'s fifth correction ("did a worker tab die, did it get replaced").

**Implemented.** `logWorkerEvent(type, detail)` appends a `{time, type, ...detail}` object to `STATE.workerEvents`, trimmed to the most recent `MAX_WORKER_EVENTS` (300) so a very long run can't grow it unboundedly, and `console.log`s it immediately (visible in the service worker console without needing the panel open at all). Persisted as part of `persistJob()`'s snapshot specifically so it survives a restart - the one event most worth seeing is also the one that wipes an in-memory-only log, so persisting anything less than this would have missed the exact case this was built for.

Events logged: `service_worker_started` (unconditionally, at the very top of the startup resume IIFE, before any of its early-return checks - this alone answers "did the service worker even restart" regardless of what happens next); `resume_skipped` with a `reason` string for each of the three ways resume can decline to run (no persisted job / persisted job has nothing pending / `STATE.running` already true); `run_resumed` with the pending/total counts when it does proceed; and, from the worker-tab recovery fix, `worker_tab_created`, `worker_tab_dead`, `worker_tab_replaced`, and `worker_tab_replace_failed`.

**Ordering matters and was easy to get backwards:** the startup IIFE now restores `STATE.workerEvents = job.workerEvents` *before* calling `logWorkerEvent("service_worker_started", ...)` - restoring after would have overwritten the freshly-logged entry with the (older) persisted array a few lines later, silently dropping the very event this was built to capture.

**Panel side:** `broadcastStatus()` and `DS_GET_STATUS` both send `STATE.workerEvents.slice(-20)` (recent-only; the full history stays in `STATE`/storage, the panel doesn't need the entire run's log in every message). Rendered in a collapsed-by-default `<details>` element ("Activity Log") so it doesn't add visual weight to the panel's default state, newest-first, each event turned into a short line by a `describeWorkerEvent()` switch (originally written as `content.js`'s own local `describeEvent()`, later moved to `content/utils.js` - see [Decision 19](#decision-19-pre-real-run-review-pass) - the event objects themselves stay plain/serializable, since they also have to survive a `chrome.storage.local` round-trip).

**What this does and doesn't fix:** this is diagnostic infrastructure, not a fix for the "did not resume" report that motivated it - that investigation is still open. What it changes is that the *next* time it's tested, the event log will show exactly which of the three `resume_skipped` reasons applied (or that `service_worker_started` never even fired at all, which would point at `chrome://serviceworker-internals`'s "Stop" not having actually terminated the worker) instead of it being an unanswerable "nothing happened."

**Tested for the parts that are pure/deterministic:** `logWorkerEvent`'s shape and trimming behavior, and the startup IIFE's three logged outcomes (no job / nothing pending / resumed) via a `storageLocalGet` override in the test helper - see `tests/background.test.js`. Not tested: the worker-tab replacement path itself, which needs real `chrome.tabs` behavior to mean anything (consistent with this project's whole testing scope - see [Decision 13](#decision-13-automated-testing-strategy)).

**Extended, once the panel's Activity Log proved useful in live testing - saved to a file too, not just shown live.** The panel truncates to the most recent 20 events and only exists while that specific tab is open; `chrome.storage.local`'s copy is cleared the moment a run's job is (`clearPersistedJob()`, right before the reports are written). Without a file, the history behind a given run's outcome couldn't be inspected after the fact - exactly the situation Decision 15 was built to avoid in the first place, just one step further down the pipeline. `createEventLogReport()` mirrors `createReport()`'s shape (same `csvEscape`/`nowStamp` helpers, same `chrome.downloads.download()` call, same `Docusign Rooms/_<category>/` folder convention - here `_Activity Logs/`) and is called from the same `runQueue()` completion point, right after `createReport()`, which already covers both a natural finish and an explicit Stop. Exports the *entire* accumulated `STATE.workerEvents`, not just what happened during this specific run - it's a lifecycle log of the service worker and its worker tabs, and slicing it to one run would lose the cross-restart picture that's the whole point. Each event's varying `detail` fields (different keys depending on `type`) are kept as one JSON-stringified column rather than forced into a fixed set of CSV columns most rows wouldn't use.

## Decision 16: Every content.js → background.js Message Needs Error Handling, Not Just Some

**Problem, found live:** "Scan & Export List (CSV)" got stuck on "Exporting CSV..." forever. The page console showed `content.js:724 Uncaught (in promise) Error: Extension context invalidated` - the same root cause as an earlier session's fix (reloading the extension orphans any content script already injected in an open tab; the orphaned instance's `chrome.runtime.sendMessage` calls can't reach the new background instance). That earlier fix added `.catch(() => {})` to `DS_STOP`/`DS_PAUSE`/`DS_RESUME`'s `sendMessage` calls - but missed `DS_START_QUEUE` (in `beginRun()`) and `DS_EXPORT_SCAN_LIST`, both of which use the two-argument `sendMessage(message, callback)` form instead of the one-argument promise form the fixed calls use. Same failure mode, inconsistently patched.

**The fix itself had a bug on the first attempt, caught immediately by checking Chrome's actual API contract rather than assuming the fix worked:** the instinct was to chain `.catch()` onto the existing two-argument calls directly - `chrome.runtime.sendMessage({...}, callback).catch(...)`. This is wrong: per Chrome's documented API contract, `sendMessage` returns `undefined` when a callback argument is supplied, and only returns a Promise when called with *no* callback. Chaining `.catch()` onto `undefined` throws a `TypeError` synchronously, on every single call - which would have made the Start button and CSV export both fail immediately, unconditionally, a strictly worse bug than the one being fixed. Caught before landing by checking the API contract against the already-correct `DS_STOP`/`DS_PAUSE`/`DS_RESUME` calls, which use the single-argument promise form specifically because that's what makes `.catch()` meaningful.

**Fixed correctly:** `DS_START_QUEUE`, `DS_EXPORT_SCAN_LIST`, and `DS_GET_STATUS` (the initial status fetch on panel load - same gap, not yet reported live but the same class of bug) were all converted to the single-argument `sendMessage(message).then(...).catch(...)` form, matching the pattern already proven correct elsewhere in the file. Every `chrome.runtime.sendMessage` call in `content.js` now has explicit error handling for a stale/invalidated context - none silently hang or throw an uncaught rejection anymore. The user-facing message on failure ("Could not reach the extension - reload this page and try again") turns a silent, indefinite hang into an actionable instruction.

## Decision 17: User-Configurable Worker Tab Count, Bounded Not Unlimited

**Problem:** `WORKER_TAB_COUNT` had been a hardcoded `3` since [Decision 2](#decision-2-parallelism-model--work-queue-not-divide-and-conquer) - a deliberate first-pass choice, not a permanent one, and the [Roadmap](../../../README.md#roadmap) always scoped a follow-up. Asked directly whether to build this now: yes, on the reasoning that it's a small, additive change (one `STATE` field, one message field, one UI input) that doesn't touch any of the currently-tested pure logic, and it gives a real dial to help the ongoing 10k-scale investigation (dropping to 1 tab would help isolate whether tab count itself contributes to the worker-tab-death pattern under active investigation) rather than waiting on the fuller adaptive-suggestion feature in [Decision 8](#decision-8-adaptive-concurrency--a-feedback-loop-not-a-formula).

**Decision: bounded, not an open number field.** `MIN_WORKER_TAB_COUNT` (1) and `MAX_WORKER_TAB_COUNT` (8) cap what the panel's "Worker Tabs" input will accept - several 10k-scale risks (worker tabs dying, `chrome.storage.local`'s quota, DocuSign rate-limiting) are still open questions at the current default of 3; letting someone dial this to 20 before those are resolved would compound the exact risks being chased down, not help diagnose them. This is explicitly a stepping stone toward Decision 8's original plan (suggest a value from measured timing, don't just accept any manual number forever), not a replacement for it.

**Implemented.** `clampWorkerTabCount(value)` in `background.js` is the single source of truth for validation - coerces arbitrary input into `[MIN, MAX]`, rounding a non-integer to the nearest whole tab count. `STATE.workerTabCount` (default `DEFAULT_WORKER_TAB_COUNT`, 3) replaces the old constant everywhere it was read (`runQueue()`'s tab-count calculation). Set from `message.workerTabCount` in the `DS_START_QUEUE` handler, and persisted via `persistJob()` so a resumed run keeps using the same count it started with rather than silently reverting to the default - the startup resume IIFE restores it through the same `clampWorkerTabCount()` call, which also covers a job persisted by an older version of the extension that didn't have this field at all (missing input and invalid input get identical, deliberate treatment: fall back to the default, don't guess). `content.js` mirrors the same three bounds as local constants (content scripts and the service worker are separate JS contexts, per [Decision 9](#decision-9-code-organization--why-not-oop)'s reasoning) purely for the input's UI bounds - `clampWorkerTabCount()` on the `background.js` side re-validates regardless, so a mismatch between the two copies couldn't let an out-of-range value through even if it happened.

**A real bug, caught by the tests written for this feature, not found live:** the first version of `clampWorkerTabCount()` checked only `Number.isFinite(Number(value))` before clamping. `Number(null)` is `0` - a real finite number, which `Number.isFinite` accepts - so `clampWorkerTabCount(null)` clamped *up* to `MIN_WORKER_TAB_COUNT` (1) instead of falling back to the default, silently treating "no value was ever provided" the same as "the user asked for zero tabs." The equivalent gap existed in `content.js`'s `readWorkerTabCount()`, where an emptied `<input type="number">` has `.value === ""` (never `null`), and `Number("")` is *also* `0` for the same reason. Both fixed with an explicit check for `null`/`undefined`/`""` before the numeric coercion, returning the default directly rather than letting them fall through to be clamped as if they were real (if extreme) numbers. Caught while writing `tests/background.test.js`'s coverage for this function, before it ever reached live testing - the value of writing the fallback-behavior test *before* trusting the implementation matched its own doc comment.

**Tested:** `clampWorkerTabCount()`'s full behavior (in-range pass-through, clamping below `MIN` and above `MAX`, rounding non-integers, the `null`/`undefined`/non-numeric/`NaN`/`Infinity` fallback, and a numeric string as arrives from an HTML input) plus the startup resume path restoring `workerTabCount` from a persisted job, clamped, and falling back to the default for a job that predates this field. Not tested: the `content.js` UI input itself or the full `DS_START_QUEUE` message-handling path, consistent with this project's established testing scope (see [Decision 13](#decision-13-automated-testing-strategy)) - `readWorkerTabCount()`'s logic is simple enough, and mirrors the now-tested `clampWorkerTabCount()` closely enough, that the risk left uncovered here is small relative to the DOM-heavy code this project has consistently left to live testing instead.

## Decision 18: Date-Range Labels in Exported CSV Filenames

**Problem, raised directly by live testing across many test runs the same day:** every scan list, download report, and activity log export used only a raw timestamp for a filename (`Scan List 2026-08-11_16-43-05.csv`) - after several test runs in one session, the Downloads folder fills with files distinguishable only by generation time, not by what date range or account state they actually cover. Requested explicitly: make all three identifiable by filename alone, without opening them.

**Decision:** thread a human-readable date-range label through to all three exports rather than inventing a separate identifier - the scan's own From/To range is already the thing a user would think of a given export "as." `content.js`'s `formatDateRangeLabel(dateRange)` turns the panel's date inputs into `"2026-01-01 to 2026-03-01"`; `background.js`'s `labeledFilename(baseName, dateRangeLabel)` wraps it in parentheses and appends the existing timestamp (`"Scan List (2026-01-01 to 2026-03-01) 2026-08-11_16-43-05"`), used by all three export functions (`createReport()`, `createEventLogReport()`, and the `DS_EXPORT_SCAN_LIST` handler) so they share one naming convention instead of three ad hoc ones.

**Graceful degradation for CSV-upload-based runs, not an edge case bolted on afterward:** a run started by uploading a CSV (rather than a live scan) has no date range at all - the rooms came from a file, not a From/To scan. `beginRun()`'s `dateRangeLabel` parameter defaults to `null` and is simply omitted at that call site; `labeledFilename()` treats `null` as "no label" and falls back to the exact plain-timestamp filename these exports always used, rather than requiring every caller to fabricate a label that doesn't semantically exist. The alternative - inventing a label for the CSV-upload case too - would have implied a date range that was never actually scanned, which would have been actively misleading rather than merely incomplete.

**Persisted, not recomputed:** `STATE.runDateRangeLabel` is set once in the `DS_START_QUEUE` handler (from `message.dateRangeLabel`) and saved via `persistJob()`, so a run that gets interrupted and resumed after a service-worker restart still produces a report carrying its *original* run's label - not `null` (the resumed instance's fresh `STATE` would otherwise have no way to know what the original scan's range was) and not a fabricated new one. Restored in the startup resume IIFE the same way `workerTabCount` is, with the same fallback (a job persisted before this field existed, or one with no label at all, resolves to `null` - the plain-filename case, exactly as intended).

**Sanitized the same way every other filename-building path in this file already is:** `labeledFilename()` runs the label through `cleanName()` before using it, even though the only real producer of this string (`formatDateRangeLabel()`) only ever emits digits, hyphens, spaces, and the word "to" and could never contain a forbidden filesystem character. Defensive, not load-bearing for the expected case - consistent with how every other value that ends up in a `chrome.downloads.download()` path in this codebase is treated, not a special exception for this one.

**Tested:** `labeledFilename()`'s label-present and label-absent (`null`) shapes, and that a deliberately-adversarial label (forbidden filesystem characters) can't survive into the output despite not being a realistic input; the startup resume path restoring `runDateRangeLabel` from a persisted job and falling back to `null` for a job that predates this field. `formatDateRangeLabel()` itself was originally written inline inside `content.js` and left untested (there being no way to test it there) - moved to `content/utils.js` and given real coverage in [Decision 19](#decision-19-pre-real-run-review-pass), once that was recognized as an accident of where it was first written rather than a deliberate scope decision.

## Decision 19: Pre-Real-Run Review Pass

**Problem:** asked directly to go over the whole codebase - code, logic, documentation, tests - before committing to a real (larger than ~25-room) run, rather than continuing to find things one live-testing cycle at a time. A deliberate shift from the pattern used everywhere else in this log (fix what live testing surfaces) to reviewing code for correctness *before* it's exercised.

**A real, previously-undiscovered bug found this way, not live: `ensureWorkerTabs()` only ever grew the worker-tab pool, never shrank it.** The function's loop was `while (STATE.workerTabIds.length < count)` - nothing handled the case where more *alive* tabs already existed than the current run wanted. Combined with `DS_START_QUEUE` never resetting `STATE.workerTabIds` between runs (worker tabs are deliberately never auto-closed - see the `runQueue()` completion comment), this meant: start a run with Worker Tabs = 5, stop it (tabs stay open, by design), then start a *second* run in the same service-worker session with Worker Tabs = 2 - `ensureWorkerTabs(2)` would find all 5 previous tabs still alive, and since `5 < 2` is false, return all 5 unchanged. The second run would silently use 5 workers, not the 2 actually requested, with no error or indication anything was wrong. This is exactly the scenario the worker-tab-count feature was built partly *for* (dialing concurrency down to isolate the 10k-scale worker-tab-death investigation, per [Decision 17](#decision-17-user-configurable-worker-tab-count-bounded-not-unlimited)'s own stated motivation) - a bug that would have specifically undermined the feature's most likely real use. Fixed by adding a shrink step after the existing grow loop: `if (STATE.workerTabIds.length > count) { STATE.workerTabIds = STATE.workerTabIds.slice(0, count); }` - the excess tabs are left open, not closed, consistent with this file never closing worker tabs on its own; they're just no longer tracked as workers for that run.

**The Stop-race fix from live testing, written up here since it hadn't been documented yet:** a user report ("when I stopped it just kept opening new tabs") traced to a narrow window in `runWorker()`'s loop - a worker's tab could die in the instant *between* passing the `waitIfPausedOrStopped()` gate at the top of the loop and reaching the tab-liveness check just after it, and if `STATE.stopped` became true in exactly that gap, the worker would still open a replacement tab for a run that was already ending. Fixed with a second `if (STATE.stopped) break;` check placed right before `chrome.tabs.create()` in the replacement path, so a worker never opens a new tab once Stop has been registered, no matter how narrow the timing.

**Testability audit: three functions were untestable by accident, not by design.** Reviewing what actually has test coverage against everything that reasonably could turned up `formatDateRangeLabel()`, the clamping logic inside `readWorkerTabCount()`, and `describeEvent()` (as it was then named) - all three pure (no DOM access at all) but written as local functions nested inside `content.js`'s `injectPanel()` closure, simply because that's where they were first needed. `content.js` can't safely get a `module.exports` test tail the way `content/utils.js` and `background.js` can (its top-level IIFE touches `window`/`document` unconditionally from its very first line - `require()`-ing it under Node would need a full DOM stub, a bigger lift than the narrow `chrome`/`window.location` stubs this project has stuck to per [Decision 13](#decision-13-automated-testing-strategy)). Moved all three into `content/utils.js` instead - not because they're shared across multiple content scripts (they aren't; only `content.js` calls them), but because that file already has the safe export tail, and the real dividing line was always "does this touch the DOM," not "which file does it happen to live in." `describeEvent()` was renamed to `describeWorkerEvent()` in the move, since a generic name became a real global shared across every content script once it left its private closure, not just a name scoped to one file's own concerns. `readWorkerTabCount()` itself stays in `content.js` (it does touch the DOM, reading `panel.querySelector(...).value`), now just calling the extracted `parseWorkerTabCountInput()` for the pure part.

**A mistake caught by `node --check`, not a test - worth recording as its own small incident, matching this project's practice of not hiding the process behind the result:** while writing the header comment explaining why these functions moved, the comment literally contained the two-character sequence `*/` (as part of "the narrow `chrome.*`/`window.location` stubs") - which is the block-comment close token. It happened twice, in two different comments, each one prematurely closing the surrounding `/** ... */` block and leaving the rest of the intended comment sitting as bare, syntactically invalid text below it. `node --check` caught both immediately, before either reached the browser or even a test run - a reminder that even documentation-only edits need the same verification pass as logic changes, since a broken comment block is still a syntax error.

**Net result of this pass:** two real behavioral fixes (the tab-shrink bug, the Stop-race tab), one testability fix (9 new tests: `formatDateRangeLabel`, `parseWorkerTabCountInput`, `describeWorkerEvent`), bringing the suite from 44 to 53 tests, and this write-up closing the gap where the Stop-race fix had already shipped in a previous turn but never made it into `DESIGN.md`.

## Decision 20: The First Real-Scale Bug — CSV Export Hanging Forever on an 8000-Room Scan

**Problem, found live at the scale this whole project was built for:** an 8000-room scan finished, and "Scan & Export List" got stuck on "Exporting CSV..." forever - no error, no timeout, nothing. This is a different symptom from [Decision 16](#decision-16-every-contentjs--backgroundjs-message-needs-error-handling-not-just-some)'s stuck-CSV bug (stale content script after an extension reload), which *does* show an error via the `.catch()` added there. A true, silent, indefinite hang with zero error surfaced anywhere is a different failure class entirely - it means neither the message's `.then()` nor its `.catch()` ever fired.

**Root cause: `encodeURIComponent()` throws on a lone (unpaired) UTF-16 surrogate, and the `DS_EXPORT_SCAN_LIST` handler's `try/catch` didn't cover the code that could throw it.** `chrome.runtime.sendMessage()` only *rejects* when the message channel itself closes (e.g. the receiving context is gone) - not merely because the handler on the other end threw an uncaught exception internally while still holding the channel open. The handler's `try` block wrapped only the `chrome.downloads.download()` call; building `rows`, the CSV string, and the `data:` URL all happened *before* that `try`, unguarded. At a 25-room test scale, the odds of any single room name containing a malformed lone surrogate are low enough to never come up. At 8000 real room names pulled from a live account, they're high enough to actually hit - and once one did, the whole handler threw, `sendResponse()` was never called, and the content script's `sendMessage()` promise just sat there forever, since the channel technically never closed either.

**Fixed two ways, not one - error-visibility isn't a substitute for the actual fix, and vice versa:**
1. `safeEncodeURIComponent(str)` tries the real `encodeURIComponent()` first (byte-identical output for every normal string, including valid surrogate pairs like an emoji in a room name); only on a genuine `URIError` does it fall back to replacing *just* the unpaired surrogates (U+FFFD) via `/[\uD800-\uDBFF](?![\uDC00-\uDFFF])|(?<![\uD800-\uDBFF])[\uDC00-\uDFFF]/g` and retrying - a valid pair elsewhere in the same string survives untouched, since the regex's lookahead/lookbehind specifically distinguish "high surrogate not followed by its low partner" and "low surrogate not preceded by its high partner" from a real pair. Used in place of `encodeURIComponent()` everywhere a CSV becomes a `data:` URL: `createReport()`, `createEventLogReport()`, and the `DS_EXPORT_SCAN_LIST` handler - all three built their `dataUrl` the identical way, so all three had the identical vulnerability, confirmed live for one and fixed for all.
2. The `DS_EXPORT_SCAN_LIST` handler's `try` now wraps the entire body, not just the download call - *any* future throw in that handler, for any reason, now reaches `sendResponse({ok: false, ...})` instead of leaving the caller hanging indefinitely. Belt-and-suspenders deliberately: fixing only the specific `encodeURIComponent` cause and leaving the narrow `try` in place would have left the same *class* of bug (a hang with zero error, for whatever the next unforeseen throw turns out to be) waiting for the next 8000-room-scale surprise.

**A related, previously-silent failure mode found while fixing this - `createReport()`/`createEventLogReport()` had the identical vulnerability, but failing there was worse: completely invisible.** Both are called from `runQueue()`'s completion path as `await createReport().catch(() => "")` - a bare catch that discards the error entirely. At real scale, the same lone-surrogate throw there wouldn't hang anything (the run still completes, `STATE.running` still resets), but the download report or activity log for an entire 8000+ room run would simply never get written, with no trace anywhere that it happened. Fixed alongside `safeEncodeURIComponent()`: both `.catch()` calls now log via `console.error` and a new `report_failed` worker event (with a `stage` of `"download_report"` or `"activity_log"`), so a failure here shows up in the Activity Log and its exported CSV instead of vanishing.

**Tested:** `safeEncodeURIComponent()`'s happy path (byte-identical to `encodeURIComponent()`), that it preserves a valid surrogate pair untouched, that it doesn't throw where the real function would (the actual regression), and that a string with *both* a valid pair and a lone surrogate keeps the pair intact while only replacing the lone one. `describeWorkerEvent()`'s new `report_failed` case, for both `stage` values. Not tested: the widened `try/catch` boundary itself or the `runQueue()` wiring, consistent with this project's scope (chrome.\* orchestration - see [Decision 13](#decision-13-automated-testing-strategy)).

## Decision 21: Stop/Pause/Resume for Scanning, Not Just the Download Run

**Problem, raised directly after the same 8000-room test that surfaced Decision 20's bug:** scanning had zero user control once started - no Stop, no Pause, nothing. The download-run phase already has all three (Decision 6, Decision 3); the scan phase (`autoScrollAndCollectRooms()`, called from either the Start button or "Scan & Export List") never got the same treatment, because every scan tested before this was small enough (~25 rooms, well under a minute) that the gap never mattered. At 8000 rooms - `totalScrolls` capped at 400, ~1.5-2s per scroll - a scan can run for several minutes with the user unable to do anything but wait it out or close the tab.

**Decision: extend the same Start/Stop and Pause/Resume buttons to control scanning too, rather than adding separate scan-only controls** - one set of buttons, whose meaning depends on what's currently happening (idle → start a scan; scanning → stop/pause *that* scan; running → stop/pause the download run), driven by a new client-side-only `scanControl` object (`{ stopped, paused }`) that's `null` whenever nothing is scanning.

**Deliberately NOT crash-persistent, and said so rather than left ambiguous:** the download run's Stop/Pause/Resume survives a service-worker restart because `background.js` persists its state to `chrome.storage.local` (Decision 6). Scanning happens entirely inside `content.js`/`content/scan.js` - a single content-script execution, with no service worker involved at all until the scan finishes and hands its results to `background.js` via `DS_START_QUEUE`. Building true crash-safe scan resumption would mean adding a whole new persistence layer for partial scan progress - a bigger, separate feature, not a natural extension of this fix. What Stop/Pause *do* give: control within one page session, and a Stop still returns whatever rooms were already collected (same `getRoomCardsAndLinks().filter(...)` call runs whether the loop finished naturally or was interrupted) - a stopped scan's partial results are still usable for Export or Start, not thrown away.

**Implemented.** `content/scan.js` gained `waitIfScanPausedOrStopped(scanControl, updateStatus)`, deliberately mirroring `background.js`'s `waitIfPausedOrStopped()` shape (same spin-wait-while-paused, return-false-if-stopped pattern) - the same problem at the scan layer gets the same solution shape, not a reinvented one. `autoScrollAndCollectRooms()` takes `scanControl` as a new optional third parameter (default `null`, so any caller that doesn't pass one - none currently, but the signature stays backward-compatible - behaves exactly as before) and checks it once per loop iteration, before the next scroll. `content.js`'s `updateButtonStates(s)` reads `scanControl` directly as a closure variable rather than requiring every call site to thread a `scanning` field through `s` - the existing `DS_BULK_STATUS` broadcast listener and initial `DS_GET_STATUS` fetch needed no changes at all, since background.js has no concept of scanning and was never going to send one.

**Scope note on "Scan & Export List" sharing the same buttons as Start:** both call the identical `autoScrollAndCollectRooms()`, so both create a `scanControl` and are controlled by the same Stop/Pause - there's no scan-specific behavior that would justify separate controls per entry point. What's *not* addressed here, left as a pre-existing and unchanged behavior rather than silently scope-creeped into this fix: "Scan & Export List" can still be clicked while a download run (`isRunning`) is active, starting a scan concurrently with an active run - the Start/Stop button already correctly refuses to do this (its `if (isRunning)` branch takes priority), but the separate Export button has no equivalent guard. Not reported as a live problem; not fixed here.

## Decision 22: Making CSV-Upload Resume Actually Reliable

**Problem, raised directly mid-run: "I've seen CSVs where the room downloaded but the status was Success/Attempted"** - during an in-progress 8000-room run (~2500 done, going well), asked whether Stop-then-reupload would correctly resume. Tracing the code confirmed the mechanism itself was sound (Decision 6, [Decision 12](#decision-12-closing-out-build-step-1-under-time-pressure--csv-export-manifest-wiring)'s CSV-resume path), but surfaced two real gaps that would make it *unreliable* rather than broken outright - both flagged as open risks earlier in this project ([Decision 19](#decision-19-pre-real-run-review-pass)'s 10k-readiness assessment mentioned the first one as untested) and now confirmed live.

**Gap 1 - the report-timing race: `createReport()` ran the instant every worker ran out of rooms to claim, not once every started download had actually finished.** `processRoom()` only waits for a download to *start* (`waitForDownloadStart()`, watching for `chrome.downloads.onDeterminingFilename`) before moving on to claim the next room - the file itself keeps downloading in the background, tracked independently by the `chrome.downloads.onChanged` listener, which is what actually flips a result's status from `"Success/Attempted"` to `"Downloaded"` once Chrome reports completion. If the run ended (naturally or via Stop) while a download was still in flight, `createReport()` could run before that `onChanged` "complete" event arrived - the room's ZIP would finish fine moments later, but the report already froze its status at `"Success/Attempted"`. Since `parseUploadedCsv()` only treats a literal `"Downloaded"` status as already-done, re-uploading that report would re-download a room that had actually already succeeded - not data loss, but wasted work and a report that undersold what had really finished.

**Fixed with `waitForInFlightDownloadsToSettle(timeoutMs = 20000)`**, called in `runQueue()`'s completion path right before `createReport()`/`createEventLogReport()` (the same shared point that already covers both natural completion and Stop, per the existing `clearPersistedJob()` comment there). Polls `STATE.downloads` for entries with neither `completedAt` nor `error` set yet; returns immediately if none exist (the common case - most downloads finish well before the last room is even claimed), otherwise waits up to `timeoutMs`. Bounded deliberately, not an unlimited wait - a single genuinely stalled download (a real possibility, not just a race) must not hang run completion forever; whatever hasn't settled by the deadline is still reported as-is, exactly as before this fix existed, not worse. Logs a `waiting_for_downloads_to_settle` event (with a count) only when there's actually something to wait for, so the Activity Log doesn't fill with noise for the normal case.

**Gap 2, raised in the same conversation, same underlying goal - empty rooms were marked `"Failed"`, so every CSV-upload resume re-visited and re-confirmed every empty room from scratch.** `content.js`'s `processCurrentRoom()` correctly detects an empty room via `[data-qa="group-name"]`'s document count (Decision 4's correction) and returns immediately - but the result fed into `background.js` as `{ok: false, reason: "Room is empty..."}`, which `processRoom()` folded into the same `"Failed"` status as a genuine failure (button not found, page didn't load, tab error). `parseUploadedCsv()` only skips re-processing for `"Downloaded"` rows, so every empty room got re-navigated to and re-checked on every resume - wasted time that scales with how many empty rooms an account has, which can be a lot at real scale.

**Fixed by giving "confirmed empty" its own outcome, not folding it into "failed."** `processCurrentRoom()` now returns `{ok: true, empty: true, reason: "Room is empty (0 documents)"}` - `ok: true` because nothing actually went wrong, `empty: true` as the distinct signal. `background.js`'s `processRoom()` branches on `response?.empty` to set `result.status = "Complete (Empty)"` instead of the generic ok/not-ok branch, **and** skips the `waitForDownloadStart()` call for empty rooms specifically (`response?.ok && !response?.empty`) - simply flipping `ok` to `true` without that second change would have made every empty room burn up to 15 extra seconds waiting for a download that can structurally never start, worse than the original bug. `parseUploadedCsv()`'s already-done check became `status === "Downloaded" || status === "Complete (Empty)"`. The panel's results breakdown gained its own `Empty N` bucket so these rooms are counted distinctly instead of silently falling through every existing bucket uncounted.

**Testability found and fixed along the way, not a separate initiative - `parseUploadedCsv()` was pure (no DOM access) but sitting untested inside `content.js`'s closure**, the exact same class of gap [Decision 19](#decision-19-pre-real-run-review-pass) closed for three other functions. Moved to `content/utils.js` alongside them, given real coverage - directly exercising the changed behavior (a `"Complete (Empty)"` row routing to `priorResults` alongside `"Downloaded"`) rather than trusting a read-through of the code alone.

**Tested:** `waitForInFlightDownloadsToSettle()` - immediate return with nothing in flight (and no log noise), returning promptly once the one in-flight download settles rather than waiting out the full timeout, and giving up at the timeout when nothing ever settles. `describeWorkerEvent()`'s `waiting_for_downloads_to_settle` case. `parseUploadedCsv()` - empty/malformed input, a `"Complete (Empty)"` row correctly routing to `priorResults` (the actual regression under test), `"Downloaded"` still working as before, `"Failed"`/`"Success/Attempted"`/`"Waiting"` still queued for reprocessing, and a plain Scan List CSV (no `Status` column) treating everything as needing work. Not tested: the `processRoom()`/`processCurrentRoom()` wiring itself, consistent with this project's scope (chrome.tabs orchestration - see [Decision 13](#decision-13-automated-testing-strategy)) - the logic there is a straightforward two-branch `if`, low-risk relative to what's already covered by the DOM-driving code this project has always left to live testing.

## Decision 23: The Second Real-Scale Bug — Trailing Periods Silently Breaking Folder Routing

**Problem, found live: "some files did not get saved to the Docusign Rooms folder."** Initially investigated as a possible size limit (ruled out quickly - `chrome.downloads.download()` has no meaningful size cap for a normal HTTP-served file; the only size-sensitive `data:` URLs in this codebase are the CSV exports, an unrelated code path) or a residual `findCurrentRoomForDownload()` timing race. Neither guess was needed once real evidence arrived: the user's own DevTools console showed repeated `Unchecked runtime.lastError: Invalid filename` entries, and separately confirmed exactly 7 rooms (out of thousands) had landed in the flat Downloads root instead of their own folder.

**Root cause: `cleanName()` never stripped a trailing period or space, and Chrome's downloads API rejects a suggested filename whose path segment ends in either - a real, enforced rule inherited from Windows, applied by Chrome cross-platform regardless of the user's actual OS.** `background.js`'s `onDeterminingFilename` listener calls `suggest({filename, conflictAction: "uniquify"})` with no callback to check for an error - when Chrome rejects the suggestion (as it silently does for a trailing `.` or space), the only trace is exactly the `Unchecked runtime.lastError` the console showed, and the download falls through to Chrome's own default location instead of the intended `Docusign Rooms/<Room Name>/` folder. Business names ending in an abbreviation - "LLC.", "Inc.", "Jr.", "St." - are common enough in a real account that this reliably produces a small, nonzero fraction of misrouted files at real scale (7 out of thousands here), while a small hand-picked test set of ~25 rooms had simply never happened to include one.

**A red herring worth recording, not silently dropped:** the same console dump included several `[DSBD] Unmatched download - no current room found` warnings - but for `data:text/csv;...` URLs, not room ZIPs. These are the CSV report exports themselves (the Download Report and Activity Log) triggering the same `onDeterminingFilename` listener that watches every download, correctly finding no matching room (because they aren't room downloads), and correctly doing nothing - this is expected, already-understood behavior from much earlier in the project, not a second bug. Confirmed by inspecting the `url` field directly rather than assuming: it began with `data:text/csv;charset=utf-8,` and contained recognizable CSV header text.

**Fixed at the source - `cleanName()` in `content/utils.js`, the single choke point every folder/file name in this codebase passes through** (room folder names, the disambiguated `(roomId)` suffix already appends safely since it always ends in `)`, and the date-range label used in every exported CSV's filename via `labeledFilename()`), rather than patching each call site separately. Strips a trailing run of periods/spaces (`/[.\s]+$/`, handling any interleaving of the two in one pass) - applied *after* the existing 120-character length cap as well as before, since truncation itself could expose a new trailing period/space that wasn't in the original string. Falls back to `"Unnamed Room"` if stripping leaves nothing, same as the existing empty-input fallback. Also added a guard for Windows' reserved device names (`CON`, `PRN`, `AUX`, `NUL`, `COM1`-`9`, `LPT1`-`9`) as an exact match only - cheap to add once the trailing-period case proved Chrome really does enforce Windows path rules regardless of platform, even though an exact collision with a real room name is far less likely than the trailing-period case that was actually confirmed.

**Tested:** the exact confirmed scenario (`"Smith Properties LLC."` → `"Smith Properties LLC"`), a bare trailing space, interleaved trailing periods and spaces, a non-trailing period left untouched (`"St. James Properties"` correctly unaffected), the length-cap interaction (a trailing period newly exposed by truncation is still stripped), the all-punctuation fallback to `"Unnamed Room"`, and the reserved-device-name guard (exact match only - `"CONstruction Room"` is correctly left alone). All of `cleanName()`'s previously-existing tests (character stripping, whitespace collapsing, length capping, empty-input fallback) still pass unchanged, confirming this was a strict addition, not a behavior change to the cases already covered.

**Extended afterward with the actual confirmed data, not just the invented example above** - once the user pulled the exact five room names out of the real Download Report CSV (`"NJ-77, Bridgeton, NJ, USA."`, `"124 Rosman Rd."`, `"Greenberg - 156 Pine St."`, `"1 Landmark Sq."`, `"693 Squaw Brook Rd."`, found by cross-referencing the CSV's *Room Name* column - the *Downloaded Filename* column was a red herring the first time through, since Chrome overwrites it with its own fallback name once it rejects the suggested one, which looks nothing like the original room name), two more tests were added: one confirming `cleanName()` itself fixes all five real names, and a second, more end-to-end one confirming `computeFolderNames()` - the function `background.js` actually calls to build the real download path, not `cleanName()` directly - also produces a safe result for all five. The second test exists because `cleanName()` being correct in isolation doesn't by itself prove nothing downstream (e.g. the `(roomId)` disambiguation suffix logic) could reintroduce the same problem a different way.

## Decision 24: Moving the Panel Out of the Page — A Detached Window

**Problem, raised as a design question, not a bug: "since [the panel is] tied to the web page anytime the page is refreshed or it moves from tab to tab it becomes super hard to press any of the buttons or accurately see progress."** True from the very first panel (README's phase 3, predating this document's Decision log), but never actionable until a real multi-thousand-room run made it matter: `content.js`'s `injectPanel()` built the entire control panel as DOM injected into the live Docusign page. A refresh, a navigation, or simply clicking to a different tab either destroyed the panel outright or made it invisible/unreachable, even though the run itself (owned by `background.js`'s service worker, not the page) kept going unaffected. Explicitly authorized to build immediately ("do it now"), with the standing instruction from earlier the same conversation to keep testing and verifying existing functionality throughout.

**Decision: extract the panel into `panel.html`/`panel.js`, a standalone Chrome extension window opened via the toolbar icon (`chrome.action.onClicked`), independent of any Docusign tab - rather than, say, trying to keep the panel alive across navigations with more injection tricks.** A separate extension page is a stable execution context Chrome doesn't tear down on a page refresh or tab switch, which is the actual property being chased here; patching the in-page approach further would still leave it fundamentally tied to a DOM that legitimately needs to reload sometimes.

**The core design problem this created: the download run and the room scan need fundamentally different capabilities, and no single execution context has both.** The download run (`runQueue()`, `processRoom()`) already lived entirely in `background.js` and needed no DOM access - `chrome.tabs.sendMessage()` to worker tabs was always how it drove them, so moving its *controls* into a standalone window changed nothing about how the run itself worked. Scanning (`autoScrollAndCollectRooms()`) is different: it's DOM automation, scrolling and reading the room list directly off a live Docusign page - it must run inside a content script, in an actual Docusign tab, and a standalone panel window structurally cannot do that work itself no matter how it's built.

**The asymmetry that shaped the whole relay protocol: `chrome.tabs.sendMessage(tabId, msg)` reaches a specific tab's content script but not other extension pages; `chrome.runtime.sendMessage(msg)` (no tabId) reaches the background worker and other extension pages (panel.html included) but not content scripts.** Neither call reaches both destinations - there is no single message that goes straight from the panel to a content script. `background.js` sits in the middle of every hop by necessity, not by choice: `panel.js` sends `DS_RUN_SCAN` (a `chrome.runtime` broadcast, since the panel doesn't know or care which tab is running Docusign); `background.js` finds the right Docusign tab and relays `DS_BEGIN_SCAN` to it via `chrome.tabs.sendMessage`; `content.js` runs the actual scan and reports back via `DS_SCAN_PROGRESS`/`DS_SCAN_COMPLETE` (`chrome.runtime` broadcasts, since content scripts can't address a specific extension page either); `background.js` relays the final result to the panel as `DS_SCAN_RESULT`. Four hops for one logical operation, but each hop is doing something the other three structurally can't.

**Decoupling the request from its (much later) response, the same pattern already used for the download run itself:** a scan across thousands of rooms can take minutes - `DS_RUN_SCAN`'s handler in `background.js` and `DS_BEGIN_SCAN`'s listener in `content.js` both acknowledge synchronously (`sendResponse({ok:true})` before any `await`) that the scan *started*, then deliver the real result later via a separate `DS_SCAN_COMPLETE`/`DS_SCAN_RESULT` message. Holding one message channel open for a multi-minute operation was never how this codebase did long-running work (the download run doesn't either), so the scan relay didn't invent a new pattern here, just reapplied the existing one across an extra hop.

**Preserving the pre-existing UX deliberately, not by accident:** `DS_SCAN_COMPLETE` for mode `"start"` does *not* auto-launch the download queue - `background.js` relays the room list back to the panel via `DS_SCAN_RESULT`, and `panel.js` shows the exact same `confirm()` dialog the old in-page code always showed before calling `beginRun()`. A user who has run this tool before sees the same confirmation step they always have; only the wiring behind it changed.

**Two gaps found during my own review, not reported live, and fixed before considering this done - per the standing "verify nothing broke, test what you can" instruction:**

1. **A synchronous-guard race in `DS_RUN_SCAN`**, the same class of bug this project already fixed once for `STATE.running`/`DS_START_QUEUE` (Decision 3): the `STATE.scanning` guard was being checked before an `await chrome.tabs.query(...)` but only set to `true` after it returned, leaving a window where two overlapping `DS_RUN_SCAN` calls could both pass the guard and start two scans at once. Fixed by moving `STATE.scanning = true` to immediately after the guard check, before any `await` - closing the window the same way the earlier fix did.
2. **No recovery if the Docusign tab running an active scan gets closed mid-scan.** Scanning has no service-worker involvement until it finishes (unlike the download run, which persists to `chrome.storage.local` and can resume after a restart - Decision 6) - if the tab closes, the content script's whole execution context disappears with it, and no `DS_SCAN_COMPLETE` can ever arrive to reset `STATE.scanning`, which would otherwise stay stuck `true` forever, permanently blocking every future scan behind an "already in progress" guard even though nothing is actually running. Fixed with a `chrome.tabs.onRemoved` listener that checks `STATE.scanTabId === tabId`, resets `STATE.scanning`/`scanTabId`/`scanMode`/`scanDateRangeLabel`, logs a new `scan_tab_closed` worker event, and broadcasts `DS_SCAN_FAILED` so `panel.js` can reset its own `scanInProgress` flag and show the reason instead of being left stuck showing "scanning" with no way to start another one.

**`broadcastStatus()` simplified as a direct consequence, not a separate cleanup:** it used to `chrome.tabs.query()` for every Docusign tab and `chrome.tabs.sendMessage()` to each one, because the in-page panel living inside those tabs was the only thing listening. With the panel now a standalone page reachable by `chrome.runtime.sendMessage()` like any other extension surface, that whole tab-enumeration loop collapsed into a single broadcast call - simpler code that fell out of the architecture change rather than being pursued on its own.

**A design tradeoff accepted, not hidden: a reopened panel can't recover whether a scan-in-progress was paused.** `background.js` has no persisted concept of "paused" for a scan the way it does for a run (scanning was never meant to survive a service-worker restart at all - see the gap above); `DS_GET_STATUS`'s response includes `scanning: STATE.scanning` so a reopened panel correctly shows a scan as in-progress, but always assumes not-paused even if it actually was. Narrow and documented rather than silently wrong: `content.js` is what's actually enforcing pause/stop either way, so clicking Pause/Resume from the reopened panel still works correctly against the real state regardless of what the panel initially displayed.

**Not tested by the automated suite, consistent with this project's established scope (Decision 13): the message-relay wiring itself** - `DS_RUN_SCAN`/`DS_BEGIN_SCAN`/`DS_SCAN_COMPLETE`/`DS_SCAN_STOP`/`DS_SCAN_PAUSE`/`DS_SCAN_RESUME`/`DS_SCAN_FAILED` handlers, the `chrome.action.onClicked` and `chrome.tabs.onRemoved` listeners, and `panel.js` end-to-end - all chrome.\*-orchestration code this project has always left to live testing rather than mocking Chrome's message-passing behavior. **What *is* tested:** `describeWorkerEvent()`'s new `scan_tab_closed` case (a pure formatting function, the same category of thing every other worker-event type already has coverage for). Every change to `background.js`'s exported pure functions and the test infrastructure itself (`tests/helpers/chrome-stub.js` needed `chrome.action`, `chrome.windows`, and `chrome.tabs.onRemoved` stub entries added as each new top-level API call was introduced, or the whole suite fails at `require()` time) was verified against the full existing suite after every edit - 78/78 passing throughout, confirming this refactor didn't regress any previously-covered behavior.

## Engineering Concepts Demonstrated

- **Producer-consumer / work-queue parallelism** vs. divide-and-conquer, and why task-duration variance determines which one is actually faster.
- **Critical sections and atomicity without explicit locks**, using a single-threaded event loop's natural serialization as the mutual-exclusion mechanism.
- **Event-driven design vs. fixed-delay polling**, and matching timeout length to what's actually being waited for (network-bound vs. UI-reaction-bound).
- **Platform lifecycle awareness** — designing persistence around Manifest V3's deliberately ephemeral service worker model, not just around user-initiated pauses.
- **Feedback-based adaptive control vs. upfront estimation** — recognizing when a parameter can only be tuned from real measurements, not calculated in advance.
- **Constraint-driven architecture** — a stronger technical solution (the official API) correctly abandoned once it hit a real permissions boundary, rather than pursued around it.
- **Revisiting an earlier decision** (streaming scan/download) when a new requirement (resumability) changed the cost-benefit calculation.
- **Matching code organization to actual runtime boundaries** — rejecting OOP not on stylistic grounds but because of how the platform's message-passing serializes data across execution contexts.
- **Decoupling a request from its response across an asymmetric message-passing topology** — brokering communication between two execution contexts that can each reach a third (a background service worker) but not each other directly, and acknowledging long-running work immediately rather than holding a channel open for the minutes it actually takes to complete ([Decision 24](#decision-24-moving-the-panel-out-of-the-page--a-detached-window)).
